# 면접 준비 (`/interview-prep`)

학생이 **자기 생기부에서 나온 면접 질문**에 하루 한 번 답하고, 루브릭 피드백을 받아
기록으로 쌓는 기능. 교사는 **생기부 분석 › 면접 준비 탭**에서 그 답변을 읽는다.

2026-09-18 신설. 별빛 탐구 아카데미에 있던 두 기능을 합쳐 **로판 컨셉 없이** 옮긴 것이다.

---

## 1. 왜 "옮기기"가 아니라 "합치기"인가

| | 아카데미 · 오늘의 만남 | 아카데미 · 교수 면담 | **면접 준비** |
|---|---|---|---|
| 주기 | 하루 1회 (KST) | 아무 때나 | 하루 1회 + 연습 |
| 질문 | 탐구·진로·**일상 상식** 중 하나 | 활동 기반 면접 질문 | 활동 기반 면접 질문 |
| KG 사용 | `entity_id` 순 **앞 35개**를 통째로 | 학생이 고른 별 + 연결 활동 | **코드가 고른 활동 1개** |
| 평가 | 없음 | S1–S4 + STAR+F (0~4) | 같은 루브릭 |
| 저장 | 대화 전체 | **없음**(화면을 떠나면 사라짐) | 질문 1 : 답변 N(버전) |

면접 대비라는 목적에서 보면 **오늘의 만남은 습관만 있고 평가가 없고, 교수 면담은
평가만 있고 축적이 없다.** 그래서 이식이 아니라 둘을 합쳤다 —
하루 한 번 → 루브릭 평가 → 누적.

**표를 공유하지 않는 이유 3가지**: ①`academy_daily_conversations` 의 PK 가
`(user_id, day)` 라 하루에 여러 질문(연습·꼬리)을 가질 수 없다 ②이미 저장된 `turns` 에
로판 대사가 섞여 있어 일반 화면이 그대로 그릴 수 없다 ③그쪽은 대화, 이쪽은 질문 1 : 답변 N.

**로판 컨셉은 세 곳에 있었다** — 두 핸들러의 시스템 프롬프트 첫 줄, `academy_daily_claim`
RPC 안의 대기 대사("리아, 잠깐 함께 걸을까?"), 그리고 DB 에 저장된 `turns` 자체.
회귀가 새 프롬프트에 `로맨스·판타지·아카데미·리아·별자리·교수·별빛` 이 없는지 검사한다.

**루브릭은 공유한다.** `_shared/academyInterview.ts` 의 S1–S4·STAR+F·파서는 원래부터
로판 요소가 없다. 복사해 두면 평가 기준이 두 갈래로 갈라지는데, 그 어긋남은 오류를
내지 않고 "화면마다 점수가 다른" 형태로만 드러난다.

## 2. 화면

### 학생 — 홈 카드 (진입점)

`StudentHome` 의 `InterviewPrepHomeCard`. **하루 한 번짜리 기능은 메뉴 안에만 있으면
학생이 오지 않는다** — 질문이 먼저 보여야 답한다. 상태 3종(대기 / 질문 있음 / 답변 완료)이
색으로 갈린다(슬레이트 · 블루 · 에메랄드).

- **홈에서 질문을 생성하지 않는다.** 재학생 630명이 홈을 열 때마다 LLM 이 돌면
  비용도 대기 시간도 감당되지 않고, 대부분은 그날 답하지 않는다. 생성은 **누를 때**.
- 조회도 `interview_prep_state()` **한 번**뿐이다. 점수까지 보여주려면 질문·답변을
  통째로 받아야 해서 홈이 무거워진다 — 점수는 본체 화면에 있다.
- 숫자는 **연속 일수가 아니라 누적 답변 일수**다. 연속은 하루만 빠져도 0이 되어
  벌점처럼 읽힌다.

### 학생 — 본체 `/interview-prep`

`PageContainer width="narrow"`(긴 글을 쓰고 읽는 화면). 툴바 카드 + 세그먼트 3탭.

- **[오늘]** 질문 카드(질문 · 의도 · **근거 기록 칩**) → 답변 → 루브릭 → 꼬리 질문
- **[연습]** 공통 질문 줄 + 활동 카드(학년별, `전체 / 아직 질문 안 받은 활동`)
- **[기록]** 커버리지 · 약한 기준 · `날짜순 / 활동별` · 이전 버전 보기

**근거 기록 칩은 같은 화면에서 펼친다.** 면접 준비는 "내 생기부에 뭐라고 적혔더라"를
확인하는 데서 시작한다. 새 탭·모달로 빼면 모바일에서 맥락이 끊기고 데스크톱에서는
모달 안 모달이 된다.

**점수는 숫자가 아니라 점 4개다.** 0~4 는 서열 척도라 숫자로 적으면 학생이 성적으로
읽고 합산하려 든다. 총점은 어디에도 표시하지 않는다. 색만으로 구분되지 않도록
`aria-label` 에 "4점 중 3점"을 싣는다.

**답변칸은 모달이 아니다.** 학생이 쓰는 긴 입력은 휴대폰이 정상 경로이고, 좁은 화면에서
모달은 키보드가 올라오는 순간 못 쓴다(CLAUDE.md §6). 초안은 질문 id 별로
`safeLocalStorage` 에 자동 저장한다.

### 교사 — 생기부 분석 › 면접 준비 탭

`EvaluationPanel` 의 `interview-prep` 탭(`{!isStudent && …}` — **트리거와 `TabsContent` 를
같은 조건으로** 막는다). 본체는 `StudentInterviewRecord` 이고 **학생의 [기록] 탭과 같은
부품**(`RecordTab readOnly`)이다.

- **기본 정렬이 활동별**이다. 교사는 "이 세특을 면접에서 방어할 수 있나"를 본다 —
  활동축으로 봐야 활동 타임라인·역량분석과 맥락이 이어진다.
- **AI 피드백은 기본으로 접는다.** 교사가 먼저 봐야 할 것은 학생의 답변이고
  AI 평가는 참고 자료다.
- **"아직 질문 안 받은 활동"** 토글이 있다. 학생이 **피하고 있는 활동**이 상담 실마리다.
- 1차는 **읽기 전용**. 교사 코멘트·질문 출제는 넣지 않았다(알림·권한 설계가 따라온다).

### 교사 체험 모드 — 테스트 학생(00-00001)으로 (2026-09-23 사용자 결정)

교사·관리자도 이 화면을 연다(교사 사이드바 [학생 메뉴] › 면접 준비, 라우트
`['student', ...TEACHER_ROLES]`). **질문은 고정된 테스트 학생 `00-00001` 의 생기부에서**
나오고, 화면 머리에 그 사실을 상시 알린다. 학생 답변 열람은 여전히 생기부 분석 탭이다.

- **학적 코드는 서버가 역할에서 유도한다** — 단일 출처 `interviewPrepStudentIdFor(role, email)`
  (`_shared/interviewPrep.ts`, 엣지 함수·화면이 같이 쓴다). 요청 본문으로 받지 않으므로
  교사가 다른 학생의 생기부로 질문을 만들 수 없다. DB 의 `interview_prep_claim_question`
  도 `role in ('teacher','admin') and p_student = '00-00001'` 로 **한 번 더** 막는다
  (마이그레이션 `20260923130000`). 실측: 교사+테스트 학생 = 통과 / 교사+다른 학생 = 거부 /
  직원 = 거부.
- **기록은 교사 본인 계정(`user_id`)에 쌓인다.** 연습 한도·오늘의 질문도 교사별이다.
  `student_id` 는 `00-00001` 이라 **생기부 분석의 00-00001 [면접 준비] 탭에 교사들의
  체험 기록이 섞여 보인다** — 테스트 학생이라 의도된 결과다. 실제 학생으로 바꾸지 말 것.
- **화면은 실제 `profile.role` 로 판정한다**(미리보기 `effectiveRole` 이 아니다) — 서버는
  JWT 의 실제 계정으로 학적 코드를 정하므로, admin 이 학생 미리보기 중이어도 테스트 학생의
  활동을 보여 줘야 서버와 어긋나지 않는다.
- **직원은 닫힌다** — `STAFF_BLOCKED_PREFIXES` 에 `/interview-prep`(메뉴 관리의 직원 스위치
  기본 = 꺼짐). 켜도 엣지 함수·DB 가 직원을 거부하므로 열지 말 것.
- **메뉴 관리** — 교사 사이드바에 들어가면서 관리 화면에 교사·직원 스위치가 생겼다(학생
  네비 쪽 학생 스위치와 별개).

- **`interview_prep_answers`** — `(question_id, version)` 유니크. **버전이 곧 다듬어 온 과정**이다.

**쓰기는 service_role RPC 전용**(두 표에 INSERT/UPDATE/DELETE 정책이 **없다**).
읽기는 `본인 ∨ is_teacher_or_admin(auth.uid())`.
**`is_staff_teacher_or_admin` 이 아니다** — 학생 개인 기록이고 직원은 학생 정보에서
차단된 역할이다.

RPC 5종: `interview_prep_state()`(클라이언트 전용, `authenticated`) +
`claim/finish_question`, `claim/finish_answer`(**service_role 전용**).
아카데미 daily 와 같은 **임대 패턴**이다 — claim 이 임대를 끊고 즉시 커밋 → LLM →
finish 가 결과를 쓴다. 네트워크 호출이 SQL 잠금을 쥐지 않고, 엣지 함수가 중간에 죽으면
임대가 만료돼 다음 시도가 이어받는다.

**하루의 기준은 서버가 정한다**(`now() at time zone 'Asia/Seoul'`). 기기 시계로 날짜를
만들면 자정 전후로 하루가 갈리거나 오늘의 질문이 두 번 생긴다.

## 4. 무엇을 물을지는 **코드가 고른다**

`pickInterviewActivity()` — ①덜 물어본 것 ②오래전에 물어본 것 ③(학생,날짜) 해시.
셋 다 결정적이라 같은 날 새로고침해도 같은 활동이 나오고, 날짜가 바뀌면 순서가 돈다.

**왜 모델에게 맡기지 않는가**: 아카데미의 "오늘의 만남"은 `entity_id` 순 앞 35개를 매일
통째로 넘긴다. 그러면 모델이 늘 앞쪽 활동만 묻고 뒤쪽 활동은 **영원히 질문을 받지
못한다**. 면접 대비의 핵심은 "생기부 전체를 골고루 방어할 수 있는가"라서 **무엇을
물을지는 코드가 정하고 모델은 그 활동으로 문장만 쓴다**(창체 GraphRAG 의 "모델은 번호만
고르고 판정은 코드"와 같은 갈래).

**공통 질문 트랙**(지원 동기·학업 계획·성장 경험·공동체·독서)이 **폴백을 겸한다**.
1학년은 엔티티 평균 11개이고 문턱을 넘는 활동이 0건인 학생도 있다
(`docs/features/kg-extraction-v8.md`) — 활동 질문만 두면 그 학생들에게 이 기능은 빈 화면이다.

**꼬리 질문은 LLM 을 부르지 않는다.** 후속 질문은 직전 평가가 이미 `followUp` 으로
만들어 두었다. 다시 생성하면 학생이 화면에서 읽은 질문과 **다른 문장**이 저장돼,
눌렀더니 딴 걸 묻는 상태가 된다. 깊이는 2단에서 끊는다(더 내려가면 원 질문과 멀어진다).

## 4-2. 루브릭 **바깥**의 두 가지 확인 (2026-09-18 사용자 요청)

루브릭은 답변의 *구조*(S1–S4 · STAR+F)만 잰다. 그것만으로는 두 가지를 놓친다.

### ① 기록 대조 — `recordCheck`

**종전 구멍**: 평가 payload 에 기록 발췌를 실어 보내면서도 프롬프트가 **대조하라고
말하지 않았다.** 자료를 주고 쓰라고 하지 않으면 모델은 쓸 수도 안 쓸 수도 있다 —
비결정적이다. 그러면 학생이 **기록에 없는 이야기로 좋은 점수를 받고** 실제 면접에서
막힌다. **면접관은 생활기록부만 보고 묻기 때문이다.**

판정은 셋뿐이고 **뭉뚱그리면 안 된다**:

| 값 | 뜻 | 화면 |
|---|---|---|
| `consistent` | 기록과 어긋나지 않는다 | 에메랄드 |
| `unsupported` | 기록으로 **확인되지 않는** 내용이 있다 | 앰버 |
| `conflict` | 기록과 **어긋난다**(무엇이 어떻게 다른지) | 로즈 |

**`unsupported` 를 오답처럼 칠하지 말 것.** 발췌는 기록의 일부라 학생이 그 바깥을
덧붙이는 것은 정상이고 좋은 답변일 수도 있다. 다만 "문서로는 증명되지 않는다"를
알아야 한다 — 그래서 색과 문구가 `conflict` 와 갈라져 있다.

`record` 가 없는 공통 질문에서는 `null` 이다.

### ② 학술 참고 — `academicNote`

기록이나 답변에 **학술적으로 부정확한 설명**이 있으면 알린다. 확신할 수 없거나 사소한
표현 차이면 `null`.

**점수 항목으로 만들지 않았다.** 루브릭은 구조를 재는 자이고 학술 정확성은 다른 축이다.
게다가 모델의 학술 판단은 구조 판단보다 덜 믿을 만해서, 점수로 만들면 **없는 정밀도**가
생긴다. 화면에도 "AI 참고 의견"으로 표시한다.

**생활기록부는 학생이 고칠 수 없는 문서다.** "선생님이 틀리게 썼다"는 말은 학생이 할 수
있는 것이 없고 관계만 해친다 — 그래서 `suggestion` 은 항상 **면접에서 그 대목을 물었을 때
어떻게 보완해 설명할지**로 쓴다. `concern` 만 있고 `suggestion` 이 없으면 **버린다**.

### 파싱은 선택 항목에 느슨하다

`parseInterviewPrepEvaluation()` 은 루브릭은 엄격히(없으면 throw), **두 참고 항목은
느슨하게**(모양이 어긋나면 `null`) 읽는다. 선택 항목이 깨졌다고 30~90초 걸린 평가
전체를 버리면 안 된다.

**아카데미의 `parseInterviewEvaluation` 은 건드리지 않았다** — 교수 면담이 같은 파서를
쓰므로, 새 필드는 그것을 감싸는 별도 파서에 둔다.

## 5. 조용히 틀리는 자리

아래는 **하나도 오류를 내지 않는다.** 화면은 멀쩡히 그려지고 값만 틀린다 —
회귀 `npx tsx scripts/interview-prep-test/run.mts`(137건)가 유일한 방어선이다.

1. **서버와 화면이 다른 KG 버전을 고른다** → 학생이 고른 활동을 서버가 못 찾아
   "선택한 활동을 찾을 수 없어요"가 뜬다. 데이터는 멀쩡한데 기능만 막힌다.
   → 선택 규칙은 `loadActivityCandidates()` **한 함수**에만 두고 양쪽이 조회기만 꽂는다.
   `KG_VERSION_SCAN_LIMIT` 도 공유한다.
2. **발췌를 원문 표에서 되찾으면 엉뚱한 기록이 붙는다.** `act:<기록id>#<n>` 의 `#n` 은
   GraphRAG 파이프라인의 **원본 활동 번호**라 배열 위치와 다르다(실측 일치율 **37%**).
   → **`student_detailed_activities` 를 읽지 않는다.** KG 의 `evidence[]` 가 이미 그
   기록에서 따온 문장이므로 그것을 쓴다(회귀가 핸들러에 그 표 참조가 없는지 검사).
3. **연습 횟수·버전 상한이 SQL 과 TS 에서 갈라진다** → 화면은 "2개 남음"인데 서버가 거절.
   → 회귀가 마이그레이션에서 숫자를 읽어 `PRACTICE_DAILY_LIMIT`·`ANSWER_VERSION_LIMIT`·
   `FOLLOWUP_MAX_DEPTH` 와 대조한다.
4. **실패한 생성을 이력으로 세면** 그 활동이 영원히 뒤로 밀린다 →
   `askHistoryOf` 가 `status='failed'` 를 건너뛴다.
5. **커버리지를 질문 수로 세면** 한 활동만 열 번 물은 학생이 "열 개 다뤘다"로 보인다 →
   **활동 수**로 센다. 이 지표가 답해야 할 질문은 "무엇이 아직 준비되지 않았나"다.
6. **KG 버전을 한 번에 여러 개 조회하면** PostgREST 1000행 상한에 조용히 잘려
   "활동이 있는 최신 버전"을 틀리게 고른다 → **버전 하나씩** 좁혀 묻는다.
7. **KG 관계·엔티티 id 가 두 종류다** — 관계는 `acti_…`, `properties.sources[].activity_id`
   는 `act:<기록id>#<n>`. 섞으면 조용히 빈 결과다(`docs/features/evalog.md`).
8. **탭 트리거와 `TabsContent` 를 한쪽만 막으면** 조건이 어긋난다(evalog 의 기존 규약).
9. **평가 `key` 를 빼면** 다시 평가받았을 때 펼쳐 둔 항목이 이전 평가 기준으로 남아
   "가장 낮은 항목"을 더 이상 가리키지 않는다.
10. **저장된 평가는 JSONB 다** — 루브릭이 바뀌면 옛 기준 id 가 섞여 들어온다. 라벨 조회
    맵의 키를 `string` 으로 넓혀 두지 않으면 타입에서 막힌다.
11. **자료를 payload 에 싣기만 하고 "쓰라"고 하지 않으면 모델은 쓸 수도 안 쓸 수도 있다** —
    기록 발췌를 넣어 두고도 대조 지시가 없어 실제로 쓰이지 않았다(§4-2 ①). 프롬프트에
    새 자료를 더할 때는 **그 자료로 무엇을 하라는 문장**이 함께 있는지 확인할 것.
12. **선택 출력이 필수 출력을 죽이지 않게 할 것** — 참고 항목 하나가 모양을 어겼다고
    평가 전체를 버리면 30~90초가 사라진다. 루브릭은 엄격히, 참고는 느슨하게 읽는다.

## 6. 기각한 것

- **아카데미 표 재사용** — §1 의 3가지 이유. PK 구조부터 맞지 않는다.
- **교사용 열람 메뉴** — 교사가 필요한 것은 학생 하나의 기록이고, 그건 이미 학생을 고른
  화면(생기부 분석) 안에 있어야 의미가 있다. 별도 메뉴는 학생을 다시 고르게 만든다.
  (2026-09-23 에 교사 메뉴가 생겼지만 **열람이 아니라 체험용**이다 — 위 "교사 체험 모드".)
- **홈 카드에서 질문 자동 생성** — 630명 × 매일. 대부분은 그날 답하지 않는다.
- **홈 카드에 점수 표시** — 질문·답변을 통째로 받아야 해서 홈이 무거워진다.
- **연속 일수(streak)** — 하루 빠지면 0. 벌점으로 읽힌다.
- **총점·합산 점수** — 0~4 서열 척도라 더하면 없는 정밀도가 생긴다.
- **말하기 STT** — 한국어·모바일 편차가 커서 먼저 재야 한다. 1차는 글자 수 →
  말하기 시간 **어림**만(분당 약 330자, 화면도 "약 1분"으로만 적는다).
- **수시 지원 연동 모의 면접**(대학별 `interview_blocks.factors` 기반 5문항 세트) —
  3학년 2학기용이라 다음 단계. 1·2학년에게는 지원 목록이 비어 있다.
