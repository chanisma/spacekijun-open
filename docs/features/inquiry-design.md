## 그래프 캔버스 크롬의 색은 `--kg-*` 변수 한 벌 (2026-10-02)

`InquiryGraphCanvas` 의 크롬(확대·검색·선택 목록·필터·범례·버전 선택기)은 같은 캔버스를 **탐구 설계**(슬레이트·인디고)와 **별빛 아카데미 망원경**(자주·황금)이 함께 쓴다. 종전엔 JSX 에 `slate-900`·`brand-400` 이 박혀 있어 아카데미 안에서만 지도가 다른 앱처럼 보였고, 아카데미 CSS 가 선택자로 덮어쓰려다 검색창 폭·패딩까지 함께 깨뜨렸다. 지금은 JSX 가 `bg-[color:var(--kg-surface)]` 처럼 **변수만** 쓰고 값은 `CHROME_THEMES[inquiry|constellation]` 이 루트 `style` 로 준다 — 탐구 설계 쪽 값은 종전 클래스와 1:1 이라 보이는 것이 같다. `--kg-sky` 는 `starfield.css` 의 바탕, 선택 고리·선택 엣지·엣지 라벨 바탕은 `constellation` 일 때 cytoscape 스타일에서 황금으로 바꾼다. **포털로 나가는 요소(버전 목록)는 변수가 닿지 않아** `KgVersionPicker` 의 `contentClassName` 으로 색을 직접 받는다. 새 화면이 이 캔버스를 쓰면 표에 행 하나를 더한다 — 클래스에 색을 다시 적지 말 것. 아카데미 쪽 상세 = `docs/features/academy.md` 2026-10-02.

## 삭제한 설계가 «설계가 완성됐어요»로 남던 문제 (2026-09-23)

**증상** — 이력에서 설계를 지웠는데도 탐구 설계 화면의 의뢰 카드가 «설계가 완성됐어요»를
계속 말한다. [설계 열기]를 누르면 «설계를 불러오는 중입니다. 잠시 후 다시 눌러 주세요»가
뜨는데, **아무리 기다려도 열리지 않는다.**

**원인 — 카드와 설계가 다른 표에 살고, 둘을 잇는 것이 없다.** 카드는
`academy_generation_jobs`, 설계는 `student_inquiry_designs` 다. 이어 주는 `draft_id` 는
**FK 가 없는 `text` 컬럼**이다(실측: 이 표의 FK 는 `owner_id` 하나뿐 · `uuid` 조인에
명시 캐스팅이 필요할 만큼 타입도 다르다). 그래서 설계를 지워도 의뢰 행은 그대로 남고,
`job.status === 'completed' && job.draft_id` 만 보던 필터가 유령을 계속 그렸다.
실측 2026-09-23: 완료 3건 중 **1건이 이미 유령**(학생 00-00494 — 그 화면에는 정상 카드 1개와
유령 1개가 나란히 떠 있었다).

**초안이 사라지는 길은 둘이고 둘 다 정상 동작이다** — 사용자가 본 것은 ①이지만 ②가 더 흔하다.
- ① 이력에서 설계 삭제(`delete_inquiry_design`).
- ② **저장으로 승격.** `saveInquiryDesign` 이 초안을 지우고(`draftDesignId` 로) 화면은
  `setDraftDesignId(null)` 을 한다 — 그 null 이 곧 카드를 감추던 `draft_id !== openedDraftId`
  조건을 **풀어 버려** 저장 직후 유령이 되살아난다.

**고친 방식 — 화면이 존재를 직접 확인한다.** 판정은 `inquiryGenerationVisible(job, {
openedDraftId, draftIds })` 한 곳(`services/inquiryGenerationService.ts`, `inquiryGenerationActive`
옆)이고, `draftIds` 는 `workspace.savedDesigns` 의 id 집합이다(`fetchSavedDesigns` 는 status 로
거르지 않으므로 draft 도 들어온다 = 존재 판정에 그대로 쓸 수 있다). 두 길이 한 번에 막히고,
**이미 생긴 유령 행도 마이그레이션 없이 사라진다**. 진행 중·실패 카드는 초안과 무관하므로
그대로 둔다 — 실패 카드를 존재로 감추면 [다시 시도] 수단이 함께 사라진다.

**열기 실패의 안내도 고쳤다.** 초안이 목록에 없는 이유는 둘이고 **안내가 정반대**다 —
완료 직후의 짧은 시차(곧 온다) vs 초안이 사라짐(영영 안 온다). 종전 코드는 앞의 것만
상정해 «잠시 후 다시 눌러 주세요»라고 단정했고, 그건 ②인 사용자에게 **성공할 수 없는 행동을
반복시키는** 안내였다. 둘을 가르는 방법은 다시 읽어 보는 것뿐이라 `workspaceQuery.refetch()`
의 **반환값**으로 판정한다(클로저의 `workspace` 는 이 시점에 낡았고, `getQueryData` 는 키
모양(버전 포함)을 여기서 다시 맞춰야 해서 조용히 어긋난다).

**하지 않은 것** — `delete_inquiry_design` 이 의뢰 행의 `draft_id` 를 함께 비우게 만드는 것.
화면 쪽 판정만으로 증상이 전부 사라지고 이미 생긴 유령까지 낫는 반면, 그쪽은 DB 변경이고
공유 표(`academy_generation_jobs`)에 쓰기를 더하는 일이라 따로 확인받을 사안이다.
지금 남는 비용은 **유령 의뢰 1건당 세션당 워크스페이스 재조회 1회**뿐이다.

## 실행 단계 제목의 번호가 두 번 보이던 문제 (2026-09-23)

**증상** — 실행 단계를 4개 만들면 화면이 동그라미로 1·2·3·4 를 그리는데, 제목에도
`1. 개념을 조작적으로 정의하고…` 처럼 번호가 붙어 **두 번 매겨진 것처럼** 보인다.
탐구 설계 탭·분석 이력 탭 양쪽에서 같다(아카데미 관측소는 `<ol>` 이라 **브라우저가** 번호를
매기므로 같은 결함이 있었다 — 함께 고쳤다).

**표시 단계에서 다룬다 — 프롬프트 규칙이 아니라 (사용자 판단, 근거 3가지).**
- ①**빈도가 확률이다.** 실측 2026-09-23 plan_steps **53건 중 12건(23%)** 만 번호가 붙어 있다.
  모델은 이미 대부분 지키고 있고, 지시를 더해도 0% 가 되지 않는다 — 가끔 나타나는 결함은
  가끔 나타나는 채로 남는다.
- ②**이미 저장된 12건은 프롬프트로 고쳐지지 않는다.** 표시 단계면 과거 설계도 함께 낫는다.
- ③**되돌릴 수 있다.** 저장할 때 지우면 원문이 사라져 규칙이 틀렸을 때 복구할 수 없다.

**안전장치 = «번호가 제 자리와 같을 때만» 지운다.** 실측 12건은 전부 제 위치와 같은 번호였다
(1번 단계에 `1.`). 이 조건 덕분에 `2026. 1학기 자료 수집` 같은 제목이 잘리는 사고가
**구조적으로 불가능**하다(2026 은 어떤 단계 번호와도 같을 수 없다). 번호가 자리와 어긋나면
손대지 않는다 — 그건 모델이 순서를 잘못 붙였다는 신호이고, 조용히 지우면 그 사실이 감춰진다.
구분자(`.` `)` `：` `-` …)도 **반드시 요구**한다 — 없으면 `3 학년 대상 설문` 의 `3` 까지 번호로 읽힌다.

단일 출처 = `utils/planSteps.ts` 의 `planStepTitle(title, index)`(index 는 0-based).
질문 목록은 **손대지 않았다** — 실측 `inquiry_questions` 53건·`student_prompt_questions` 56건
중 번호가 붙은 것이 **0건**이라 고칠 것이 없다.
⚠️ **React key 로 쓰지 말 것** — `1. 자료 수집`·`2. 자료 수집` 이 번호를 떼면 같은 값이 된다
(호출부는 지금처럼 원문 `step.title` 을 key 로 쓴다. 회귀가 검사한다).

**회귀**(두 문제 공통) = `npx tsx --tsconfig tsconfig.app.json scripts/inquiry-status-title-test/run.mts`
(35건). 둘 다 **빌드도 타입 검사도 통과**하므로 순수·정적 검사가 유일한 방어선이다.

## 설계가 그린 엣지의 «관계 세부사항» (2026-09-23)

**증상** — 탐구 설계로 만들어진 새 엣지를 눌러도 **아무 일도 일어나지 않았다.** 기존 KG 엣지는
누르면 아래쪽에 «관계 세부사항» 패널이 뜨는데, 방금 설계가 그린 엣지만 반응이 없다. 오류도
경고도 없어서 "관계 설명은 애초에 안 만들어지나 보다"로 읽힌다.

**그러나 세부사항은 처음부터 만들어져 저장까지 되고 있었다.** 생성 스키마
(`supabase/functions/_shared/inquiryGraph.ts` 의 `relations.required`)가 `evidence`·`confidence`·
`properties.{status,notes}` 를 **필수**로 요구하고, graph 단계 프롬프트도 `모든 연결은 근거가
있어야 한다` 로 못 박는다. 라이브 실측(2026-09-23, `student_inquiry_design_relations` 14행):
**evidence 14/14 · confidence 14/14 · status 14/14 · notes 12/14**. 즉 만들어야 할 것이 아니라
**닿을 길이 없었던 것**이다.

**원인은 둘이고 둘 다 오류를 내지 않는다.**
- ① 캔버스의 엣지 tap 핸들러가 `if (data.scope !== 'existing') return` — 설계(`saved`)·
  미리보기(`preview`) 엣지의 클릭을 **조용히 삼켰다**.
- ② 그 가드를 풀어도 패널이 `workspace.kgRelations` 만 뒤진다. 설계 관계는 그 표에 없으므로
  (`student_inquiry_design_relations` · 아직 저장 전 미리보기) 영영 `null` 이고, 패널은 뜨지 않는다.

**고친 방식**
- **엣지 tap 은 scope 로 거르지 않는다.** 노드 tap 은 그대로 `existing` 만 받는다 — 둘은 다른
  일이다. 노드 선택은 **분석 출처 선택**(기존 기록만 고를 수 있어야 한다)이고, 엣지 탭은
  **열람**이다. 이 비대칭이 의도라는 것을 캔버스 주석과 회귀가 함께 못 박는다.
- **엣지 id 빌더·파서를 `utils/inquiryGraph.ts` 한 곳에 모았다**(`kgEdgeId`/`designEdgeId`/
  `previewEdgeId`/`parseDesignedEdgeId`). 패널이 이 id 를 되풀어 관계를 되찾으므로 형식이
  한쪽에서만 바뀌면 **오류 없이 "패널이 안 뜨는"** 상태가 된다. 종전에는 `InquiryDesignPage`
  가 `kg::${id}` 를 따로 만들고 있었다(지금은 삭제).
- **설계·미리보기 id 에 배열 위치를 쓴다.** 종전 형식
  `design::<설계id>::<출발>::<도착>::<술어>` 는 같은 두 노드를 같은 술어로 잇는 관계가 둘이면
  **같은 id** 가 되어 ①cytoscape 가 뒤엣것을 버리고 ②id 로 되찾을 때 **엉뚱한 근거**를
  보여준다. 위치는 그 배열 안에서 유일하다.
- **해석기는 순수 함수** `utils/relationDetail.ts` 의 `resolveDesignedRelation()`. 여기 떼어 둔
  이유는 **끝점 라벨이 scope 마다 다른 표에서 오기** 때문이다 — `planned` 는 그 설계가 만든
  엔티티 목록, `existing` 은 KG 엔티티. 화면 안에 두면 한쪽만 고쳐져도 라벨이 **id 로 보일 뿐**
  오류가 나지 않는다.

**패널에 무엇이 더 보이나** — 기존 KG 관계와 같은 자리(출발 → 술어 → 도착 · 신뢰도 · 근거)에
두 가지가 붙는다. ①**어느 설계에서 나온 관계인지**(저장된 설계는 제목, 미리보기는 `미리보기 설계`)
②`properties.notes` 를 **«메모»로 근거와 따로** 보여준다 — 근거는 "이 연결이 성립하는 이유"이고
메모는 "왜 이 연결을 골랐는가"라서 서로 다른 정보다(실측 예: 근거 `기존 수학-기술 융합 경험이
카메라 거리 추정과 자율주행 해석 탐구를 직접 뒷받침함.` / 메모 `수학 개념을 기술 원리로 확장하는
기존 역량을 활용`). 설계 제목은 평균 34자·최대 51자(실측)라 머리글 칩은 폭을 막고 `title` 로 넘긴다
— `shrink-0 truncate` 는 서로 모순이라(줄지 않으니 자를 일도 없다) 아무것도 자르지 못한다.

**바꾸지 않은 것** — 엣지를 눌러도 **선택 하이라이트는 생기지 않는다.** 기존 KG 엣지도 그렇다
(`EMPTY_EDGE_SET` 을 캔버스에 넘기는 것이 의도된 설계 — 엣지는 분석 출처 집합에 참여하지 않는다).
어느 엣지인지는 패널 본문의 `출발 → 술어 → 도착` 이 말한다.

**회귀** = `npx tsx --tsconfig tsconfig.app.json scripts/inquiry-edge-detail-test/run.mts`(32건 —
id 왕복·중복 관계 id 분리·scope 별 끝점 라벨·캔버스 배선). 이 결함은 **빌드도 타입 검사도
통과하므로** 정적·순수 검사가 유일한 방어선이다. 패널의 모양 규약은 종전대로
`node --test scripts/inquiry-design-detail-panel.test.mjs`(6건).

## 탐구 설계 패널 UI (2026-09-12)

- **2단 확장 배치**: 카드 순서를 두 열로 나누지 않는다. `PanelColumns`가 역할별 영역을 유지하며 실제 패널 폭 760px 이상에서 각 영역을 독립 스크롤한다. 폭 전환 때 입력 컴포넌트를 재생성하지 않아 작성 중인 이유·메모가 유지된다.
  - 탐구 설계: 왼쪽은 대상·근거·방향·대화, 오른쪽은 설계 결과·나의 이유.
  - 종합 분석: 분석 전에는 소개/방향 입력, 방향 검토 시에는 보완 방향 목록/과목·메모 설정, 결과에서는 추천 목록/선택한 추천 상세.
  - 분석 이력: 왼쪽 목록을 유지하며 오른쪽에서 선택 항목의 상세·생명주기 작업을 진행한다. 좁은 화면은 목록 → 상세 → '이력 목록으로' 흐름으로 전환한다.
- 넓은 패널의 하단은 안내와 적정 너비 실행 버튼을 나란히 배치한다. 브라우저 회귀 검증과 예시 화면은 `scripts/inquiry-panel-layout-test` 참조.
- 상단에 활동 선택 → 탐구 설계 → 이유·저장 진행 상태를 표시하고, 입력 영역을 번호가 있는 카드로 구분한다. 탐구 연결은 선택 항목으로 표시하며 근거 없이 시작할 수 있음을 안내한다.
- 기존 '추가 컨텍스트 / 방향성'은 '탐구 방향'으로 표시한다. 질문은 Q 번호, 실행 계획은 단계 번호와 기대 결과로 구분한다.
- 저장 버튼과 안내는 패널 하단에 고정한다. 학생·교사의 기존 저장 조건과 대화 우선순위는 유지한다. 좁은 화면에서는 설계 버튼을 세로로 배치한다.
- 입력창에 연결된 레이블·도움말, AI 공급자 버튼의 선택 상태를 제공한다. 학생 화면에서는 토큰 정보를 표시하지 않는다.

## 코치 대화가 «학생이 고른 노드»를 못 보던 문제 (2026-09-18)

**증상** — 학생이 지식 지도에서 근거 노드를 골라 두고 «대화로 설계하기»를 눌러도, 코치에게 물어보면
그 노드들의 **존재를 전혀 몰랐다**. 오류도 경고도 없고 코치는 그럴듯한 일반 질문("어떤 주제에 관심이
있니?")을 계속 던진다. 결과적으로 그 대화에서 나온 요약이 «탐구 방향»에 병합되고 설계까지 그대로
흘러가므로, **설계 전체가 선택 노드와 무관해 보인다**.

**원인은 프롬프트도 모델도 아니고 «첫 메시지를 누가 쓰느냐» 한 군데였다.**
엣지 함수 `inquiryDesignConversation` 은 `messages` 와 `target` 만 받는다 — 선택 노드가 들어갈
파라미터가 애초에 없다. 그래서 opener 본문이 유일한 통로인데,

| 화면 | opener | 결과 |
|---|---|---|
| 아카데미 연구대 `DesignConversation.tsx` | `…제가 고른 지식 별자리의 기록: ${JSON.stringify(records.map(s => s.snapshot))}` | ✅ 정상 |
| 탐구 설계 `InquiryDesignPage.startConversation` | `안녕하세요. "<과목>" 활동을 위한 새 탐구를 설계하려고 합니다.` | ❌ 과목 이름 하나뿐 |

학생이 «탐구 방향» 칸에 직접 적어 둔 글도 같은 이유로 코치에게 보이지 않았다(대화가 끝난 **뒤에야**
`buildConversationContext` 가 그 칸에 합류시킨다 — 순서가 거꾸로였다).

**수정** — 단일 출처 `utils/conversationPrimer.ts`(순수 함수)가 선택 노드·기록과 수기 방향을 코치가
읽을 수 있는 블록으로 만들고, `requestInquiryConversation` 이 **첫 메시지의 사본**에만 덧붙인다.

- **본문이 아니라 사본이어야 한다** — 탐구 설계의 `InquiryConversationBox` 는 `messages` 를 **전부**
  렌더하므로(아카데미는 `slice(1)` 로 opener 를 감춘다) 아카데미식으로 본문에 JSON 을 박으면
  학생의 첫 말풍선이 원시 JSON 덩어리가 된다. 사본 방식은 `achievementContext` 가 이미 쓰던 것이다.
- **매 턴 다시 보낸다** → 대화 도중 별을 더 고르거나 방향을 고쳐 적으면 **다음 턴부터 반영된다**
  (아카데미는 opener 가 얼어붙어 있어 반영되지 않는다 — 이쪽이 개선된 형태다).
- **스냅샷을 날것으로 싣지 않는다** — 신 KG 의 `properties` 는 한 겹 더 감싸여 있고 근거 키 이름도
  세대마다 다르다(`did` vs `evidence`). `kgProperties.ts` 정규화 창구를 거치지 않으면 **빈 객체가
  열 개** 실리고, 역시 오류는 나지 않는다.
- **개수(`selectedSourceCount`)는 따로 서버로 보낸다** — 사용자 메시지에 "고른 것을 짚어 달라"고
  적어도 시스템 프롬프트의 "관심 주제부터 물어라"가 **그것을 이긴다**. 1턴 지시 자체가 갈라져야 한다.

**설계(analysis) 단계도 함께 고쳤다** — `selectedSources` 는 **원래도** `stagePrompt('design')` 의
JSON 에 실려 있었지만 **그게 무엇인지 말한 적이 없어서** 모델이 목적 없는 부속 데이터로 취급했다.
이름을 들어 호명하는 지시문 한 줄을 넣었다(`_shared/inquiryStages.ts`). graph 단계는 종전에도
`선택 출처의 relation_hint` 라고 언급하고 있어 이 결함이 덜했다.

> **⚠️ 엣지 함수 재배포가 필요하다** — `openai-proxy`(대화 1턴 분기 + `_shared/inquiryStages.ts`
> 설계 지시문). 클라이언트 쪽만 배포해도 코치는 선택 노드를 **보게 되지만**, 1턴 질문이 여전히
> 일반 질문으로 나갈 수 있다.

**아카데미 연구대는 손대지 않았다** — 이미 정상 동작하고, 그쪽 opener 는 «리아/카시안» 서사 문구와
뉴스·연구 수첩 3종 분류가 얽혀 있어 바꾸면 얻는 것보다 잃는 것이 크다. 통합한다면 `conversationPrimer`
에 그 3종 분류를 흡수시키는 쪽이다(현재는 `selectedSources` 미전달 → primer 가 빈 문자열이라 **무영향**).

회귀 = `npx tsx scripts/inquiry-conversation-test/run.mts`(22건 → **59건**). 이 결함은 오류를 내지
않으므로 **배선을 정적으로 검사하는 것이 유일한 방어선**이다 — 두 호출부의 인자, opener 에 JSON 이
없다는 것, 서버가 개수로 갈린다는 것, 설계 지시문이 `selectedSources` 를 호명한다는 것.

## 개념 노드를 소속 활동 곁에 — 공유 개념은 예외 (2026-10-02)

개념 노드가 부모 활동에서 멀리 떠 있었다. 원인은 `classifyEdge` 의 판정 순서다 — 활동↔개념 엣지가
`leaf`(0.55) 에 닿기 전에 `concept`(1.0) 에 먹혀, 차수 1.01 의 잎인데 골격 수준의 길이를 받았다.

**변경** = 활동↔개념을 `conceptAnchor`(길이 0.65 · 탄성 0.55) 로 분리. 단 **그 개념이 활동 둘 이상에
걸려 있으면 종전 `concept` 힘을 쓴다**(`isSharedConcept`). 공유 개념은 두 활동을 잇는 숨은 스프링이라
(거리 상한 ≈ 2 × 길이) 짧게 하면 단어가 겹쳤을 뿐인 활동이 서사 엣지(1.6)보다 바싹 붙는다.
판정은 `degree()` 가 아니라 **활동 이웃 수**(`neighborhood('node[type = "Activity"]')`) — degree 는
개념↔도서·개념↔개념까지 센다. 개념↔도서·개념↔개념 엣지와 반발력은 그대로다. 두 화면(탐구 설계 ·
아카데미 관측소)이 같은 캔버스를 쓰므로 함께 바뀐다.

**라이브 실측** (학생별 최신 KG, 활동 이웃 2개 이상 = 공유): v8 개념 10,255개 중 0.3%(최대 6) ·
도서 1.0% · 역할 3.8% · 인물 0.9% · 역량·성취 0.0% · 구 파이프라인 역량 2.4%. **허브형은 다르다** —
관심분야 1,269개 **전부** 공유(평균 활동 4.37 · 최대 20), 흐름 평균 4.30 · 최대 23. 관심분야↔활동은
`other`(1.0 · 0.45) 로 분류돼 흐름(1.2 · 0.50)과 거의 같은 세기로 활동을 묶는다 — 조정 여부는 미결.

회귀 = `npx tsx scripts/graph-layout-forces-test/run.mts`(28건 — 분류 순서 · 공유 판정 · 실제 cytoscape 선택자).
수치(0.65)는 실측 근거가 아니라 출발점이다.

## 새 노드 빈자리 배치 + 미리보기 강조 (2026-09-14)

**증상** — 새 별 찾기(academy)·탐구 설계의 미리보기 노드가 기존 노드 위에 겹쳐 떠서 점선 테두리·페이드인이
무의미했다. **원인** — 캔버스는 미리보기마다 전체 레이아웃을 다시 돌리지 않는 **증분 갱신**이라
새 노드를 놓을 힘이 없는데, 종전 `seedNewNodePositions` 는 ①이웃들의 **무게중심**(=대개 그래프 한가운데,
허브형 그래프에서 가장 빽빽한 곳)에 ②이웃이 없으면 학생 허브 위에 ③반지름 110~182px 고정으로 ④충돌 검사
없이 놓았다. 간격 슬라이더도 이 값에 영향을 주지 않았다.

**수정 1 — 규칙은 `utils/newNodePlacement.ts`(순수 함수)**: 앵커는 **주변이 가장 한산한 이웃 하나**(평균을
내지 않는다) → 그래프 무게중심에서 앵커를 향하는 **바깥 방향부터** 링을 넓혀 가며 후보를 훑고 →
**라벨 포함 실측 상자**로 충돌을 판정해 첫 빈자리에 놓는다(`placeIsolatedNodes` 와 같은 원칙). 공기는
간격 배수를 따른다. 새 노드끼리(planned→planned)는 놓이는 순서대로 서로 앵커가 된다. 상한(24링×12후보)까지
못 찾으면 `unresolved` 로 돌려준다(현재 화면은 마지막 후보에 놓고 경고하지 않는다).

**수정 1-b — 정착 패스 (사용자 제안)**: 빈자리 배치는 **출발점**이고 라벨 겹침까지 푸는 것은 힘이다.
간격 슬라이더가 이미 쓰는 `randomize: false` 재배치를 새 노드 추가 직후 한 번 돌린다(`fit: false`,
끝나면 `focusOnAdded`). 전체 모양은 유지된 채 새 노드 주변만 정돈된다 — 증분 갱신 주석이 막던 옛 결함은
**무작위** 재배치였지 재배치 자체가 아니다. 감수하는 것: 기존 노드도 슬라이더 때만큼 살짝 움직이고 그
좌표가 저장된다. 빈자리 배치를 빼면 안 된다(0,0·허브에서 출발한 노드가 그래프를 가로질러 끌려온다).

**수정 2 — 강조**: 미리보기 노드는 `z-index` + 호박색 후광(`underlay`), 그 1-hop 이웃 밖은 `preview-backdrop`
클래스로 한 단계 물린다(노드 0.35 · 엣지 0.2 — hover 의 `dimmed` 0.15 보다 옅게, 지도는 계속 읽혀야 한다).
규칙 순서상 hover 가 겹치면 hover 가 이긴다. `applyPreviewEmphasis` 는 전체 재구성·증분 갱신 양쪽 끝에서
호출돼 미리보기가 사라지면 함께 걷힌다.

①성취기준 맥락 토글을 **끄고** 만든 설계에도 붙는다(그 토글은 기본 꺼짐이다) ②**이미 쌓인
과거 이력**에도 붙는다 ③설계 본문은 종전대로 성취기준을 베끼지 않는다(그 금지는 의도된
것이다 — 위 "성취기준 맥락" 절). 대가는 LLM 호출이 한 번 더 있다는 것인데, **누를 때만**
돌고 결과를 `llm_result.achievement_links` 에 남겨 두 번째부터는 호출하지 않는다.

**AI 는 코드만 고르고 문장은 우리가 채운다.** 화면에 뜨는 성취기준 문장은 모델이 쓴 글이
아니라 본문에서 파싱한 사전의 원문이다. 그래서 ①베껴 쓰다 틀릴 자리가 없고 ②**사전에 없는
코드는 버릴 수 있다**(= 지어낸 연결이 화면에 못 올라온다). 코드에 한글이 섞여 있어 모델이
옮겨 적다 틀릴 수 있으므로 목록을 번호와 함께 보여 주고 **순수한 숫자로 답하면 그 번호로도
읽는다**(범위 밖이면 버린다).

⚠️ **"전부 버려졌다" 와 "정말 닿는 것이 없다" 를 가른다.** 둘을 같은 "없음" 으로 뭉개면
모델이 코드를 지어내는 고장이 정상 상태로 위장된다. 버린 것이 있는데 남은 것이 하나도
없으면 **실패로 던지고**(다시 눌러 볼 값어치가 있다), 모델이 보고도 고르지 않은 경우만
"직접 닿는 성취기준을 찾지 못했어요 · 그것 자체는 문제가 아니에요" 로 말한다.

⚠️ **공급자를 `openai` 로 못 박는다.** 기본 공급자 solar 경로는 `max_tokens` 를 아예 보내지
않아(`aiChat.ts`) 추론 토큰이 예산을 다 먹으면 본문이 빈 채 끝난다 — 구조화된 JSON 을
기대하는 이 호출에서는 그게 곧 실패다. 입시 정보 분석·스펙 채움이 같은 이유로 이미 openai
경로를 택했다. 응답 파싱은 공용 복구 파서(`ipsi-hub/utils/analysisJson.ts`)를 재사용한다.

**본문 형식 실측 (2026-09-18, 라이브 118건 전수)** — 비어 있지 않은 줄 2,093 = 문서당 머리글

추측하지 않는다. 형식이 나중에 바뀌어 **절반만 읽히는** 사고는 오류를 내지 않으므로
`standardCountMismatch()` 가 선언값과 대조해 콘솔에 남긴다. 코드는 한 구간(`12생명03-02`)과
두 구간(`10통과1-02-06`, 실재함) 둘 다 있다 — 한쪽만 받으면 그 줄이 통째로 사라진다.

다른 경로가 생기면 이 가정이 깨진다.** 아직 저장되지 않은 결과에서는 화면 state 에만 붙었다가

초안" 만 담아 **이력에서 불러온 정식 설계에는 null** 이라 그 행을 가리킬 수 없다.

- **기록**: `student_inquiry_designs.kg_version_id` 신설. `student_inquiry_recommendations` 는
  이미 갖고 있었다(라이브 27행 전부 보유). 저장 RPC `save_inquiry_design_with_ontology` 는
  컬럼을 **명시 나열**하므로 `p_design` 에 키만 더하면 조용히 버려진다 — 함수도 함께 고쳤다.
- **기존 행은 추정하지 않는다**: 라이브 16행 중 출처 행으로 되살릴 수 있는 **1행만** 채웠다.
  14행은 초안이라 출처 행 자체가 없고(초안은 부모 행만 만든다) 버전 선택기가 있어
  "생성 시각의 최신 버전"이라 단정할 수도 없다. 나머지는 `기반 그래프 미기록`으로 표시한다.
- **읽기**: `fetchHistoryEntityLabels()` 가 이력이 참조하는 **다른 버전만** 골라
  `student_kg_entities(kg_version_id, entity_id, label)` 을 읽어 `workspace.historyEntityLabels`
  에 담는다(참조가 없으면 요청 자체가 나가지 않고, 있어도 라벨 열 하나만 읽는다).
  실패해도 화면을 막지 않는다 — 라벨은 설명을 돕는 값이지 기능의 전제가 아니다.
- **해석 규칙**: `labelMapForVersion()` — 기반 버전이 현재와 같으면 `kgEntities`, 다르면
  그 버전의 사전, 없으면 **빈 맵(원시 id)**. **현재 그래프로 폴백하지 않는다** —
  엉뚱한 라벨보다 원시 id 가 정직하다.
- **목록은 버전으로 거르지 않는다**(사용자 결정). 전부 보이되 `기반 v6 · 26-09-12` 배지로
  어느 그래프인지 밝히고, 지금 보는 것과 다르면 앰버 + `다른 그래프`로 표시한다.

`InquiryGuideDialog` — 왼쪽 시연 + 오른쪽 설명 4단계(근거 고르기 → AI와 설계 → 이유 쓰고

- **학생이 읽는 글이고 학생 화면을 그린다**(2026-09-04 사용자 결정). 학생이 주 설계자이고
  교사는 보조·제안이라, 안내는 **학생이 보는 화면과 학생이 하는 일만** 다룬다.
  - 그래서 ①단계에 **학생 선택이 없다** — `canPickStudent = !isStudentView && (teacher|admin)`
    이라 학생에게는 그 패널이 애초에 없고, 로그인하면 자기 지도가 바로 열린다.
    그 자리를 지도에 돌려주면 노드 라벨도 잘리지 않는다.
  - 문구는 학생 모드 쪽(`바로 설계하기`·`나의 탐구 이유`·`설계 저장`)과 1인칭을 쓴다.
  - 교사 기능은 **받는 쪽 시점**으로만 등장한다 — "선생님이 먼저 설계를 만들어 주면 이력에
    '선생님 제안'으로 오고, **내 이유를 쓰고 수락**해야 내 설계가 된다".
- 글이 맡는 것 셋 = ①**AI가 대신 정해 주는 도구가 아니다**(남는 것은 자기 말로 쓴 이유)
  ②**설계로 끝나지 않는다**(실제 활동과 이어야 기록) ③**분석할 때마다 '임시'가 자동 저장**
  (날아가지 않으니 편하게 시도할 것).
- **진입점이 예외적이다**: 이 페이지는 `Layout fullWidth` 라 헤더가 없어, 캔버스 상단 중앙의
  모드 토글을 감싸는 flex 행의 **첫 항목**으로 붙였다(그 왼쪽에는 아무 버튼도 없다는 규약 유지).
- 씬 목업은 `InquiryDesignPage`·`InquirySidePanel`·`HistoryPanel` 의 실제 문구에서 채집했다.
  **화면 문구가 바뀌면 `components/guide/scenes.tsx` 도 함께 고칠 것.**
