# evalog

> CLAUDE.md '주요 패턴'에서 분리한 evalog(생기부) Smart Upsert·일괄 적재 상세. 스키마는 docs/database/education-ontology.md.

- **Smart Upsert**: INSERT 새 레코드 / UPDATE 변경분만 / SKIP 동일 (evalog)
  - **생기부 일괄 적재는 반드시 `파싱 → reconcile → 스마트 업서트` 3단계다**: `parseStudentExcel`은 학번을 **입학연도 + 1학년 반·번호**로 채번하는데 이 값이 전입생에게는 유일하지 않다(2026-08-31 실측: 박시우·강지아이 둘 다 "1학년 2반 3번"). 그래서 `services/studentIdReconciler.ts`가 `(현재 학번, 이름)`으로 `resource.meta.id`를 찾아 교체하고, 못 찾은 ID가 타인 소유면 업로드에서 제외한다. **이 단계를 건너뛰면 남의 생기부를 덮어쓴다** — 파서만 돌리는 새 경로를 만들지 말 것.
  - **일괄 적재 도구** = `scripts/evalog-record-import/`(`parse.mts` 읽기 전용 파싱 → `reconcile-and-diff.mts` ID 교정 → `upload.mts --apply` 적재, `check-basic-loss.mts`·`diff-keys.mts` 점검). 앱 UI(`AdminDialog`)와 같은 규칙이되 안전장치 2개를 더 둔다: ①파일이 빈 값인데 DB에 내용이 있으면 갱신 제외(앱은 덮어쓴다) ②내용 비교 시 `null`/`''`를 동등 취급(안 하면 미작성 행동특성 412건이 매 실행 재기록된다 — `content: item.content || JSON.stringify(item.data)`가 `undefined`를 낳아 DB엔 null로 저장되기 때문).
  - **기존 행 조회에서 PostgREST 1000행 상한을 반드시 처리할 것**: `.in('student_id', 100명)`은 학생당 평균 16행이라 1,600행이 되어 **조용히 잘린다**. 못 본 기존 행이 전부 "신규"로 분류되고(실측 1,535 → 4,329으로 부풀었다) 빈 값 덮어쓰기 방어도 무력화된다. `range()` 페이징 + `count: 'exact'` 대조로 잘림을 검증한다.
  - **`student_basic_info`는 스마트 업서트가 아니라 행 통째 upsert**다. 파일에 항목이 덜 들어 있으면 성적·봉사 기록이 조용히 사라지므로, 적재 전 `check-basic-loss.mts`로 배열 길이를 대조할 것.
  - **세특은 "한 셀에 전 과목이 이어 붙은 한 덩어리"라 과목 경계 탐색이 급소다 (2026-08-31)**: `parseSeTeukSheet`가 경계를 놓치면 그 과목 세특이 **앞 과목에 통째로 흡수**되고 화면에는 "그 과목 세특이 없는" 것으로 보인다 — 오류도 경고도 없다. 종전 정규식은 **과목명 앞이 마침표·개행·공백일 때만** 경계로 인정했는데, 실제 원문은 문장 부호 없이 바로 이어지거나(`…배려도 보임인간과 철학:`) 이물질 문자가 낀다(`…생임. ㄹ정보:`, `ㄴㅇㄻㄴㅇㄹ체육1:`, `,한국사1·`). 라이브 실측 **10건/8명**이 이렇게 묻혀 있었다. 지금은 앞 문자 제약을 없앴다 — `subjectPattern`이 이미 "그 학생이 수강한 과목명"으로 좁혀져 있어 본문 중 우연한 일치 위험이 낮고, 콜론이 없으면 경계가 아니다. 회귀 = `npx tsx --tsconfig tsconfig.app.json scripts/seteuk-split-test/run.mts`(19건).
  - **`공통국어1·공통국어2:` 는 누락이 아니라 NEIS의 1·2학기 통합 세특**이다(내용 하나). `combinablePrefixes` 전처리가 대표 과목 하나로 합치는 것이 의도된 동작이므로 `공통국어2` 레코드가 없다고 놀라지 말 것 — 라이브 1,331건이 이 형태다. 누락 여부는 `audit-seteuk.mts`로 판정한다(앞 문자 제약 없이 원문의 `과목명:`을 전부 찾아 DB와 대조하고, 결합 표기는 정상으로 분류).
  - **★ 적재는 절반이다 — 갱신된 행의 낡은 분절이 굳는다 (2026-09-14, 3학년 적재에서 발견)**: 스마트 업서트가 `content` 만 바꾸고 `segmentation` 은 그대로 두는데, 분절 러너(`segment-missing.mjs`)의 대상은 **`segmentation is null` 뿐**이다. 그래서 **내용이 바뀌었는데 분절이 남아 있는 행은 영원히 건너뛰어진다** — 그 분절에서 나온 `inquiry_activity` 는 현재 생기부에 없는 문장을 `sentence_ids` 로 가리키고 KG 근거 인용도 함께 어긋나는데, **오류는 나지 않고 화면은 멀쩡히 그려진다**. 3학년 적재 실측: 갱신 2,781건 중 **분절이 달린 채 내용이 바뀐 것 2,246건 → 거기서 나온 활동 5,125건**.
    - **무효화 대상 목록은 적재 *전에* 잡아야 한다** — 적재가 끝나면 DB 내용이 파일과 같아져 "어느 행이 바뀌었는지"를 되물을 방법이 사라진다. `inspect-changes.mts` 가 `stale-segmentation-ids.json` 을 남기고, `invalidate-stale.mts --apply` 가 **판정을 먼저 지우고 분절을 나중에** 비운다(순서가 안전장치다 — 중간에 끊겨도 "분절은 없는데 옛 판정만 남은" 가장 나쁜 조합이 생기지 않는다).
    - 변경의 성격도 함께 볼 것: 3학년 실측은 **길이 변화 중앙값 1자**인데 최소 −862·최대 +1,048 이었다(7월의 미완성 세특이 9월에 완성된 것 — 보건 178자 → 1,120자처럼 아예 다시 쓴 것도 있다). 공백만 다른 326건도 문장 분리가 밀릴 수 있어 함께 무효화한다.
  - **★ 재분절은 그 코호트가 쓰던 분절 모델로 할 것 (2026-09-14, 2026-09-21 기본값 제거)**: 라이브 실측 **24학번은 활동 12,765건이 100% pro4**(2023·2025·2026 은 pro3)라, 3학년 기록만 pro3 로 들어가면 **한 학생 안에서 학년 간 비교가 모델 차이에 오염**된다(스킬 `/inquiry-graphrag` §3-6 이 코호트 간에서 겪은 그 교란이 학생 안으로 들어온 형태). 재분절 전에 대상 코호트의 `inquiry_activity.seg_model` 분포를 먼저 세고 `RESEARCH_MODEL` 로 맞출 것.
    - **원인은 "기본값이 있다"였다**: `_harness.MODEL` 기본값이 2026-08-14 에 `solar-pro4` → `solar-pro3` 으로 바뀌어 그냥 돌리면 pro3 분절이 조용히 만들어졌고, **121건을 만든 뒤에야** 알아채고 되돌렸다. **2026-09-21 사용자 결정으로 기본값을 아예 없앴다** — `RESEARCH_MODEL` 미지정이면 `callOpen2` 가 대상 코호트 확인법까지 적힌 예외로 막는다. 즉 이제 **모르고 돌리는 일 자체가 불가능**하다.
    - ⚠️ 막는 자리는 **모듈 로드가 아니라 호출 시점**이다 — 현행 `kg-extract-v8` 이 같은 `_harness.mjs` 에서 `callOpen2` 만 가져다 쓰면서 모델은 자기 것(`KG_MODEL ?? 'solar-pro4'`)을 명시적으로 넘기기 때문이다. import 시점에 던지면 멀쩡한 v8 이 통째로 죽는다.
    - 라이브 분포(2026-09-21): `solar-pro3` 27,029건(583명) · `solar-pro4` 21,593건(218명) · `motif/motif-3` 7,262건(320명).
  - **전입생 충돌은 학년마다 새로 난다**: 3학년 적재에서도 한선우·오로아이 둘 다 "1학년 2반 15번"이라 파생 ID 가 `00-00269` 하나로 접혔다. 교정 없이 넣었으면 유니크 키가 같은 **40건이 오류 없이 서로를 덮어썼을 것**(마지막 값이 이김)이고, 교정 후 충돌은 3건으로 줄었다. 정본은 **3학년 학반번**으로 갈린다(한선우 3-1-8 = `00-00645`, 오로아 3-7-8 = `00-00269`) — DB 의 기존 1학년 구성(regular·career·pe_arts 건수)이 이 대응을 독립적으로 확증해 준다. `REMAP` 은 **과거 차수를 지우지 말고 추가**한다(키가 `(파생 ID, 이름)` 쌍이라 다른 학년 파일에서는 발화하지 않는다).
  - **적재 절차(3학년 기준 전체)**: `parse.mts <디렉터리> --json payload.json` → `reconcile-and-diff.mts payload.json <outDir>` → `inspect-changes.mts <outDir>`(무효화 목록 확보) → `upload.mts <outDir>`(시험) → `upload.mts <outDir> --apply` → `invalidate-stale.mts <outDir> --apply` → `RESEARCH_MODEL=<코호트 모델> segment-missing.mjs --cohort <NN>` → E1 판정 → KG v8 `--force`. **`--apply` 앞에는 반드시 시험 실행**으로 "빈 값 덮어쓰기 0건"을 확인한다.

## 역량분석 · 활동 타임라인 (2026-09-12 신설)

탐구 설계(`/inquiry-design`)가 읽는 **학생 지식그래프**와 비교과 탭의 **활동 분절**을
생기부 분석 화면으로 들여온 것. 두 탭이 같은 데이터 계층을 공유한다.

| 탭 | 화면 | 답하는 질문 |
|---|---|---|
| **역량분석** (구 '키워드분석') | `CompetencyAnalysis.tsx` | 어떤 역량이 기록되었고 **무엇이 그것을 뒷받침하는가** |
| **활동 타임라인** (구 'AI 분석') | `ActivityTimelineView.tsx` | 이 학생이 **시기별로 무엇을 했는가** |

데이터 계층(전부 순수 함수 + 훅 2개):

```
useActivityLedger      student_detailed_activities 1회 조회 → byId · byContentKey
  └ useActivitySegmentation   (내용 색인만 꺼내는 얇은 래퍼 — 비교과 탭이 쓴다)
useStudentKgLayers     student_kg_versions/entities/relations → StudentKgLayers
utils/kgLayers.ts      엔티티·관계 → 활동 중심 평탄화
utils/activityLedger.ts 분절 + KG → 원장 · 학년 밴드 · 역량 뷰
```

회귀 = `npx tsx scripts/evalog-competency-test/run.mts` (103건).

### 조용히 틀리는 자리

- **⚠️ 결합 키는 분절이 저장한 `entity_id` 다 — 배열 위치로 계산하면 안 된다.**
  `act:<기록id>#<n>` 의 `n` 은 GraphRAG 파이프라인의 **원본 활동 번호**이고 추출 문턱에서
  걸러져 구멍이 난다. 라이브 실측 60,245건 중 위치와 일치하는 것은 **22,293건(37%)**뿐이다.
  저장된 `entity_id` 를 쓰면 KG 활동 9,212건 중 **9,211건(99.99%)**이 붙는다. 어긋나도
  오류가 없고 역량이 **엉뚱한 활동**에 달린 채 화면이 멀쩡하게 그려진다.
- **⚠️⚠️ 활동을 가리키는 id 가 두 종류다. 섞으면 오류 없이 조용히 빈 결과가 된다.**
  구현 중 이 혼동으로 **세 번** 깨졌고 그중 하나는 화면에 raw id(`acti_aaa111`)가
  그대로 찍히는 형태였다.

  | 종류 | 모양 | 어디에 담기나 |
  |---|---|---|
  | **KG 엔티티 id** | `acti_xxxxxx` | `KgActivityNode.entityId` · `KgTrait.activityId` · `KgThread.memberActivityIds` · `deepenedFrom`/`developsInto`/`relatedTo` (= **관계**가 쓰는 id) |
  | **분절 활동 id** | `act:<기록id>#<n>` | 분절의 `entity_id` · `properties.sources[].activity_id` · `KgThread`·`Interest` 의 `sources` (= **엔티티 속성**이 쓰는 id) |

  즉 **관계는 엔티티 id, `sources` 는 분절 id** 다. 색인도 그래서 둘이다 —
  `ledger.byKey`(분절 id) / `ledger.byKgEntityId`(엔티티 id). 화면에서 사슬·서사 엣지의
  이름을 풀 때는 `kg.activities.get(엔티티id)?.label` 을 쓴다. 회귀가 어느 필드가 어느
  종류인지 단언으로 못 박아 둔다.
- **⚠️ 관계는 `layer === 'local'` 만 쓴다.** 같은 뜻이 두 층으로 중복 저장돼 있다
  (`DEMONSTRATED` = `local` 6,222 · `student` 6,221). 층을 안 가리면 역량이 두 배로
  세어지고 그 절반은 활동을 모른다.
- **⚠️ `category='career'` 의 뜻이 두 곳에서 반대다.** 기록의 `career` 는 *진로선택 과목*
  (=교과활동), KG 의 `career` 는 *창체 진로활동*이다(KG 는 세특을 `seteuk`/`seteuk_career`
  로 쓴다). 그래서 `areaOf` 와 `areaOfKgCategory` 가 따로 있고, 후자는 기본 표를 **먼저**
  펼치고 덮어쓴다. 순서를 뒤집으면 진로활동이 교과활동 칸으로 들어간다.
- **⚠️ 축은 학년이다. 학기로 버킷을 나누지 말 것.** `student_detailed_activities`
  30,785행 중 `semester` 가 있는 것은 **1,658행(5.4%)**이고 창체(자율·동아리·진로)는
  **0건**이다(`inquiry_activity` 도 3.3%). 학년-학기로 나누면 대부분이 '학기 없음'에
  쌓여 축이 고장난 것처럼 보인다 → 학기는 **있을 때만 붙는 꼬리표**.
- **Thread 의 학년 범위는 구성원에서 계산한다.** `sources[0]` 은 첫 구성원의 학년일 뿐이라
  3개년 사슬이 1학년으로 보인다. 구성원은 `PART_OF` 관계로 세는데, 이것과 Thread 의
  `sources[]` 는 **완전히 일치한다**(실측 5,140 = 5,140, 불일치 0) — 폴백이 필요 없다.
- **`sources[]` 는 여럿일 수 있다.** Activity 9,881건 중 11건이 출처 2개다. `sources[0]`
  만 색인하면 그 11건은 "역량이 안 붙은" 상태가 된다 → `sourceActivityIds` 전부를 쓴다.
- **'새로 등장한 개념'은 학년 순서대로 훑어야 한다.** 뒤에서 계산하면 1학년 개념이
  새것이 아니게 되어 뜻이 뒤집힌다.
- **`inquiry_activity` 를 화면에서 읽지 않는다.** `research_question`·`level`·
  `career_fields` 의 정본이지만 RLS 가 **`is_teacher_or_admin` 교사 전용**이라 학생 시점에서
  0행이 된다(evalog 는 학생도 쓴다 — 본인 1행). 필요한 값은 KG 안의 사본으로 대체했다:
  수준·유용성은 Activity `properties`, 연구 질문은 `evidence[]` 의 `연구 질문:` 접두
  (v8 Activity 의 83%가 갖는다).

### 카드 순서 — 유용성 높은 순 (2026-09-13)

학년 → 영역 안에서 **`usefulness` 내림차순**으로 놓는다(사용자 결정). 목적은 읽을 만한
활동을 위로 올리는 것이고, `usefulness` 는 분절이 매긴 점수(핵심개념·자료·표지·문장 수의
합)로 라이브 60,245건 **전부** 값을 갖는다.

- **동점이 매우 흔해 타이브레이크가 대부분의 순서를 정한다** — 실측 분포에서 2~7점이
  전체의 **80%**(4점 17.5% · 5점 15.7% · 3점 15.0% …). 사슬은
  **학기(있으면) → 과목 → 기록 → 기록 안 배열 위치 → 키** 로, 같은 점수 카드가 과목별로
  묶여 흩어지지 않고 **실행마다 순서가 달라지지 않는다**.
- **타이브레이크의 "기록 안 순서"는 배열 위치이고 `#n` 접미가 아니다** — `#n` 은
  파이프라인의 원본 활동 번호라 문턱에서 걸러져 구멍이 난다(위 id 표 참고).

- **순서가 시간순이 아님을 화면이 말한다** — 영역 머리글의 `유용성 높은 순`(카드 2장
  이상일 때만)과 개요 각주. 학년 축 안에서 시간순을 기대한 사람은 그냥 두면
  "왜 뒤죽박죽인가"로 읽고, 카드에 숫자가 있어도 그 숫자가 **순서를 정한다**는 것은
  따로 알려야 안다.
- 영역 **구획 순서**는 고정(교과활동 → 자율 → 동아리 → 진로 → 행동특성)이다. 즉 정렬은
  구획 안에서만 일어난다 — 영역을 넘나드는 단일 "잘한 순" 목록이 필요하면 별개의 결정이다.

## 유사도 분석 — 같은 학년만 대조 (2026-09-12)

**규칙(사용자 결정): 유사도 분석은 같은 학년 학생의 기록만 대조한다.** 이 기능이 답하는
질문은 "교사가 같은 문장을 여러 학생에게 썼는가"이고 그 위험은 같은 학년을 같은 시기에
함께 쓸 때 생긴다. 다른 학년·졸업생까지 끌어오면 관계 없는 일치가 섞여 정작 봐야 할
일치가 묻힌다.

| 파일 | 역할 |
|---|---|
| `utils/similarityCohort.ts` | 학년 판정·같은 학년 필터·페이징 구간 (순수, 단일 출처) |
| `hooks/useSimilarityCandidates.ts` | 같은 학년 재학생 명단 → 그 학생들의 기록 전량(페이징) |
| `components/evaluation/SimilarityAnalysis.tsx` | 유사도 탭. 대조 범위를 머리글에 상시 표시 |
| `components/writer/EvaluationWriter.tsx` | 작성 중 실시간 검사기의 후보도 같은 학년으로 |

회귀 = `npx tsx scripts/evalog-similarity-cohort-test/run.mts` (43건).

### 고친 것 — 종전 구현은 사실상 동작하지 않았다

- **⚠️ `student_no` 는 입학연도가 아니라 현재 학반번이다.** 종전 코드는
  `student_no.substring(0,4)` 를 코호트로 알고 접두 비교했는데, `10926` 은
  `1학년 9반 26번`이라 앞 4자리(`1092`)는 **학년+반+번호 십의자리**다. 실측(00-00872
  기준): 후보 **870명 중 6명**만 통과(같은 학년은 226명). 즉 "같은 반, 번호 십의자리까지
  같은 학생"과만 대조하고 있었다 — 이 기능이 일치를 거의 못 찾은 이유다.
- **⚠️ 후보 조회가 행 상한에 조용히 잘렸다.** 창체는 범위 없이 전체를 긁어 **5,865행**을
  요구(상한 1,000 → 83% 유실), 세특은 과목 목록만으로 **7,587행**을 요구(87% 유실).
  PostgREST 상한은 오류가 아니라 **부분 결과**로 오므로 화면은 멀쩡했다. 지금은
  `count: 'exact'` 로 총량을 먼저 알고 `range()` 로 전량을 받으며, 받은 수가 count 와
  어긋나면 `incomplete` 를 화면에 띄운다.
- **대조 범위를 화면에 상시 표시한다.** 이 사고의 본질은 "대조 대상이 6명뿐"이라는 사실이
  화면 어디에도 없었다는 것이다. **유사도 0건은 "깨끗하다"와 "아무것도 안 봤다"를
  구분하지 못한다** → 머리글에 `N학년 재학생 M명의 기록 K건과 대조했습니다` 를 고정한다.
- **후보 텍스트 정규화를 문장 루프 밖으로 뺐다**(`findExactSentenceMatches`). 종전엔
  `cand.text.replace(/\s+/g,' ')` 를 (문장 수 × 후보 수) 번 호출했다. 후보가 6명일 때는
  티가 안 났지만 같은 학년 전체로 바로잡으면 한 화면에서 수백만 번이 된다.
