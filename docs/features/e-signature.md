# 전자서명 (e-signature)

> `src/features/e-signature` 상세. 스키마·좌표계·날인 엔진 3종·UI.

## 무엇인가

**임의의 문서(한글·PDF·이미지)에 서명을 받는 공용 기능.** 특정 화면에 매인 기능이 아니라
`<SignatureButton subjectType subjectId />` 하나로 어디에나 붙는다(결재·task_work 와 같은
`subject_type`+`subject_id` allowlist 원칙). 독립 메뉴는 `/signatures`.

## 결재(approval)를 흡수한다

사용자 결정(2026-09-03). 결재는 "HWPX 결재란 4칸 + 순차 승인"이라는 이 시스템의 **한 형태**다.
라이브 결재 데이터가 요청 2건(둘 다 종료)·서명 1건뿐이라 이관 위험이 없어 새 모델을 정본으로 삼았다.

**결재로는 불가능했던 것 = 동시 서명.** `act_on_approval_step` 이
`WHERE order_index = current_order` 로 **한 행**을 집으므로 같은 순번에 두 명을 넣으면
그중 하나만 잡히고 나머지는 영원히 서명할 수 없다. UI 문제가 아니라 스키마 문제였다.

## 진행 규칙 — 한 줄

> **같은 `order_index` = 한 그룹 = 동시 서명. 그룹 전원이 끝나야 다음 그룹.**

이 규칙 하나로 동시(전원 같은 값)·순차(전부 다른 값)·혼합이 모두 표현된다. `mode` 컬럼을
따로 두지 않은 이유 — 두면 데이터와 규칙이 어긋날 수 있다. 형태는 `flowShape()` 가 파생한다.

한 명이라도 거절하면 **요청 전체가 종료**된다(결재와 같은 결정 — 부분 진행은 문서를 애매하게 만든다).

## 스키마

| 표 | 내용 |
|---|---|
| `signature_request` | 문서 1건. 원본·완성본 storage 경로, 상태, `current_order`, 선택적 `subject_type`/`subject_id` |
| `signature_signer` | 서명자 1명. `order_index`(그룹), `role_label`(결재 형태에서만), 획 서명, **`fields` JSONB** |

**서명 칸을 별도 표로 두지 않았다** — 칸은 서명자 없이 의미가 없고(항상 함께 읽고 함께 지운다)
칸 단위 조회가 없다. 표를 하나 줄이면 RLS 정책도 하나 줄어든다.

**쓰기는 RPC 전용**(`create_signature_request` · `act_on_signature_request` ·
`cancel_signature_request` · `set_signature_source_path` · `set_signature_request_signed_path`).
두 표에 INSERT/UPDATE 정책을 두지 않았다 — 직접 쓰기를 열면 차례를 건너뛰거나 남의 칸에
서명할 수 있다. 열람 판정은 DEFINER `can_view_signature_request`(요청자 ∪ 서명자 ∪ admin) —
정책 안에서 두 표를 직접 조인하면 **RLS 가 재귀한다**(창체·결재에서 겪은 것과 같은 함정).

**Storage** = 비공개 버킷 `signatures`, 경로 `<request_id>/source-*` · `<request_id>/signed-*`.
첫 세그먼트가 요청 id 라서 정책이 `can_view_signature_request` 하나로 판정한다.
**이 규약을 깨면 업로드는 되는데 아무도 못 읽는다.** `documents` 버킷을 재사용하지 않은 이유 —
서류함의 "교사 전원 열람" 규칙이 그대로 적용돼 서명 문서가 관계자 밖으로 샌다.

요청 생성은 **행 먼저, 파일 나중**(경로에 id 가 필요하다). 업로드가 실패하면 행을 취소한다 —
원본 없는 껍데기는 열 수 없는데 서명자에게 알림만 가는 최악의 상태다.

## 좌표계 — 정규화 0~1

세 포맷의 단위가 전부 다르다:

| | 단위 | 원점 |
|---|---|---|
| 화면 미리보기 | CSS px (렌더 배율마다 다름) | 좌상단 |
| PDF | point (72dpi) | **좌하단** |
| HWPX | HWPUNIT (1/7200 inch) | 좌상단 |
| 이미지 | 원본 픽셀 | 좌상단 |

그래서 저장은 **페이지 크기 대비 0~1** 하나로 통일하고 각 엔진이 환산한다
(`lib/signatureField.ts` 단일 출처). 픽셀로 저장하면 확대/축소·DPI 변경에 값이 깨지고
포맷마다 다른 숫자가 된다.

**PDF 의 y 뒤집기가 가장 틀리기 쉽다** — 위쪽에 지정한 서명이 아래쪽에 찍히는데,
페이지 한가운데 근처 박스는 얼추 맞아 보여서 늦게 발견된다. 회귀 테스트가 이 함정을 기록한다.

**서명은 항상 비율 유지 contain**(`fitContain`). 칸에 맞춰 늘리면 사인이 찌그러지는데,
서명은 모양 자체가 신원이라 왜곡하면 안 된다. 칸보다 작은 서명은 **키운다**(작게 찍히면 안 보인다).

### HWPX — 용지 절대좌표 + 모든 개체 위

결재 날인(`lib/rhwp/approvalCells.ts`)과 목적이 다르다:

- 결재 = "'교감' 칸을 찾아 그 안에 **글자처럼**"(`treatAsChar="1"` · `vertRelTo="PARA"`)
- 여기 = "사용자가 페이지 위에 찍은 좌표에 **모든 개체 위로**"
  (`treatAsChar="0"` · `RelTo="PAPER"` · `textWrap="IN_FRONT_OF_TEXT"` ·
   `allowOverlap="1"` · `flowWithText="0"`)

결재가 rhwp `insertPictureEx` 를 버린 이유는 *rhwp 가 계산한 셀 위치*를 용지 좌표로 굳혀
한글이 다시 배치할 때 어긋났기 때문이다. **여기서는 사용자가 렌더된 페이지에서 직접 찍은
좌표**라 추적할 셀이 없고, 용지 절대좌표가 정확히 의도한 자리다.

**한글의 제약**: PAPER 에 고정한 개체도 **어떤 문단에 속하는지**가 페이지를 결정한다.
"3쪽에 찍으려면 3쪽에 흐르는 문단"이 필요하고 그 번호는 rhwp 레이아웃만 안다
(`getPageTextLayout` → `cellIdx`·`parentParaIdx` 없는 **본문** run 의 `paraIdx`).

**빈 문단도 세야 한다** — `<hp:p/>` 같은 자기 닫힘 문단을 건너뛰면 이후 문단 번호가
한 칸씩 밀려 **서명이 다른 쪽에 찍힌다**(오류 없이 조용히). 회귀 테스트가 실제로 잡은 버그.

편집은 **오프셋 큰 것부터** 적용한다(앞 편집이 뒤 오프셋을 밀지 않게). 그림을 넣은 문단의
`<hp:linesegarray>` 는 반드시 제거한다(줄 캐시가 남으면 한글이 옛 줄 높이로 그린다).

## UI

- **요청 마법사** 3단계 — ①문서 ②서명자·순서 ③페이지 위 드래그로 서명 칸.
  단계를 나눈 이유: 칸은 사람에게 배정되므로 **사람이 먼저** 있어야 그릴 대상이 생긴다.
  반대로 칸 없는 서명자는 저장을 막는다(`validateSigners`) — 서명은 받아도 문서에
  아무것도 안 찍히는 상태가 된다.
- **문서 렌더 = `DocumentPageView`** — 세 포맷을 하나의 인터페이스로. 오버레이는 `%` 로만
  그린다(렌더 폭이 화면마다 달라 픽셀로 환산하면 리사이즈 때 어긋난다).
- **서명자 색은 이름 해시로 결정론적**(`lib/signerColor.ts`, dataviz 검증기 통과 6색).
  같은 사람이 늘 같은 색이어야 문서 위 칸과 진행 현황이 서로 이어진다. 색 단독 의존이 아니다 —
  칸마다 이름표가 붙는다.
- **진행 현황 = `SignerLine`** — 결재선과 달리 **한 칸에 여러 명**이 들어간다(동시 서명).
  그룹 사이 `›` 가 순서를, 그룹 안 나열이 동시성을 나타낸다.
- **완성본은 필요할 때 굽고**, 완료된 요청만 Storage 에 저장한다(`signed_path`).
  미리 구우면 서명이 추가될 때마다 낡은 파일이 남는데 최신 여부를 화면에서 구분할 수 없다.
- **출력** — PDF·이미지는 새 창에서 바로 인쇄, 한글은 브라우저가 못 여니 내려받기로 돌린다.

## 휴대폰 서명 QR

`/signature-sign/:requestId` — QR 로 여는 **앱 셸 없는 단독 화면**. QR 부품은
`components/signature/SignQrCode.tsx` 로 **결재와 공용**(링크만 다르다).

**QR 에 토큰·유효기간이 없다.** 라우트를 public 화이트리스트에 넣지 않아 로그인이 필수이고,
`act_on_signature_request` 가 "지금 차례인 본인"을 서버에서 재검증하므로 링크가 새어 나가도
남의 칸에 서명되지 않는다. 화면 표시는 작게 하되 QR 원본은 480px 로 굽는다 — 저해상도로
만들어 확대하면 셀 경계가 뭉개져 카메라가 못 읽는다.

**휴대폰 화면에는 문서 미리보기를 넣지 않는다.** 작은 화면에서 A4 를 읽는 것은 어차피
어렵고, rhwp WASM·pdfjs 를 모바일 회선에서 받는 비용이 크다. 여기서 하는 일은 하나 —
**손가락으로 사인하는 것**이고, 무엇에 서명하는지는 제목·요청자·진행 현황으로 밝힌다.
대신 서명 패드를 크게 준다(모바일은 세로가 넉넉하다).

## 알림 — 트리거 2개

클라이언트가 아니라 DB 트리거로 보낸다. 서명자 명단·차례 판정이 서버에만 있고,
클라이언트가 보내면 "요청은 만들어졌는데 알림만 안 간" 상태가 조용히 생긴다.

| 시점 | 받는 사람 |
|---|---|
| 원본 경로가 `pending` → 확정될 때 | 첫 그룹 서명자들 |
| `current_order` 가 바뀔 때 | 새 그룹 서명자들 |
| `pending` → `completed`/`rejected` | 요청자 (취소는 본인이 한 것이라 안 보낸다) |

**첫 알림의 방아쇠가 서명자 INSERT 가 아니라 `source_path` 확정인 이유**: `create_signature_request`
가 서명자를 하나씩 넣으므로, INSERT 마다 보내면 **아직 다 만들어지지 않은 요청**을 알리게 되고
같은 그룹의 두 번째 사람이 아직 없어 절반만 발송된다. 원본이 확정되는 순간이 곧 요청이 실제로
쓸 수 있게 된 순간이다.

**알림 실패가 서명을 막으면 안 된다** — 본문이 하위 트랜잭션이고 실패는 `raise warning`
으로만 남는다(구매 신청 알림과 같은 처리). 수신 리소스는 `signer_resource_id`, 없으면
**이름 폴백**(계정 연결이 아직 없는 사람도 알림은 받아야 한다). `related_meeting_id` 는
meeting FK 라 쓸 수 없어 딥링크는 `meta.signature_request_id` 로 넣는다.
타입 `signature_request` 아이콘은 `notificationUtils.tsx` 에 등록돼 있다.

**검증(2026-09-03)**: 라이브에서 요청 1건·서명자 3명(그룹0 2명 + 그룹1 1명)으로 종단 실행 →
①그룹0 2건 ②차례 이동 후 누적 3건 ③완료 후 누적 4건(마지막이 요청자의 '서명 완료'), 정리 완료.

## 결재 흡수 — 진입점 이전

결재는 **업로드가 아니라 생성된 문서 + 결재란 칸**이라 요청 화면이 다르다:

- `ApprovalStyleRequestDialog` — 파일 선택 대신 `buildDocument()` 로 문서를 받고,
  드래그 대신 **칸 이름**(계·부장·교감·교장)으로 배정한다. 자유 좌표가 아닌 이유는
  **양식이 이미 그 4칸을 갖고 있어서** — 좌표로 찍으면 양식이 조금만 바뀌어도 칸 밖으로
  나가지만 칸 이름으로 찾으면 따라간다. 칸 순서 = 결재 순서(순차)가 기본이되, 같은 순번을
  주면 동시 결재가 되므로 규정이 바뀌어도 스키마를 손댈 필요가 없다.
- 날인은 `stampDocument` 가 `hwpx-cell` 배치를 만나면 기존 `approvalCells.stampSignaturesIntoSectionXml`
  에 넘긴다. 박스와 칸을 **차례로** 같은 XML 에 적용하며, 각 함수가 받은 문자열을 다시
  스캔하므로 앞 편집이 뒤 편집 위치를 어긋나게 하지 않는다. **칸 배치만 있으면 rhwp WASM 을
  부르지 않는다**(페이지 앵커가 필요 없다 — 로딩이 몇 초 걸린다).

**이전한 진입점 2곳**(둘 다 `timetable.swap_document`):
`SwapDocumentDialog` 푸터(결재 현황 + 결재 상신) · `SwapRequestList` 의 [결재 문서] 탭.
구 `src/features/approval` 모듈은 **지우지 않고 남겨 뒀다** — 되돌릴 여지를 남기는 것과,
`ApprovalSign` 라우트가 아직 살아 있어서다.

## 받는 파일 형식 — `.hwp` 는 받지 않는다 (2026-09-04)

`.hwpx` 는 **zip**(OPC 패키지)이지만 `.hwp` 는 한글 97~2007 의 **복합 바이너리(CFB)** 로
완전히 다른 포맷이다. 이 기능의 한글 처리는 rhwp 레이아웃도 XML 편집도 **전부 zip 전제**라
`.hwp` 는 고쳐서 되는 것이 아니라 애초에 받으면 안 되는 파일이다.

종전에는 `detectSourceKind` 가 `.hwp` 를 `'hwpx'` 로 분류하고 업로드 `accept` 도 `.hwp` 를
허용해 통과시켰다. 그 결과 JSZip 이
`Can't find end of central directory : is this a zip file?` 를 던졌는데, **터지는 시점이
파일을 올릴 때가 아니라 서명을 다 받은 뒤 완성본을 구울 때**라 가장 나빴다.

방어는 세 겹이다:
1. `detectSourceKind` 가 `.hwp` 에 `null` 을 돌려준다(MIME 폴백으로도 되살아나지 않는다).
2. 업로드 `accept` 에서 제외하고, 거절 토스트는 `sourceRejectReason()` 이 **무엇을 하면
   되는지**까지 말한다("한글에서 [다른 이름으로 저장] → .hwpx").
3. 날인 단계의 `looksLikeZip()` — 이 규칙 이전에 만들어진 요청이 남아 있을 수 있으므로
   완성본을 굽는 자리에서도 사람이 읽을 수 있는 오류를 낸다.

회귀 = `npx tsx scripts/signature-core-test/run.mts`(형식 판정 10건 + zip 서명 5건 포함).

- **문서 페이지의 쪽 번호는 여백을 확보해서 넣는다**: `absolute -top-2` 로 페이지 위에 걸치면 앞 페이지 하단·sticky 툴바와 **겹친다**. 래퍼에 `pt-5` 를 줘 자리를 만들고 `top-0` 에 놓는다
- **서명 차례 알림에서 요청자를 건너뛰지 말 것 (2026-09-03 수정)**: "요청자 본인이 서명자면 안 보낸다"는 규칙이 두 가지를 깼다 — ①**순차 서명에서 요청자의 나중 차례를 통째로 삼킨다**(앞사람이 끝나도 알림이 없어 멈춘 것처럼 보인다) ②알림 목록은 발견 경로인데 자기가 올린 문서라고 그 경로를 없앨 이유가 없다. 실측: 실사용 요청 2건이 모두 요청자=서명자였고 **알림 0건**이었다. 지금은 전원에게 보내되 요청자에게는 문구만 다르게(«…» 서명할 차례입니다)
- **Drive 는 복사가 아니라 옮기기 (2026-09-03 사용자 결정)**: 완성본을 Drive 에 올리면 **Storage 완성본은 지운다**(`set_signature_drive_file` 이 `signed_path` 를 null 로). 완성본은 원본+서명으로 언제든 똑같이 재생성되는 파생물이라 두 벌 둘 이유가 없다. **원본은 지우지 않는다** — 무엇을 보고 서명했는지의 증거이고 재생성의 유일한 재료다. **RPC 가 먼저, Storage 삭제가 나중**이어야 한다(반대면 파일은 없는데 경로만 남아 열 때마다 오류가 난다)
- **`session.provider_token` 은 세션 갱신 때 사라진다 (2026-09-03)**: 최초 OAuth 직후에만 존재하므로 `googleDriveService.isAuthenticated()` 는 **평소에 대부분 false** 다. 이걸 "조용히 넘어감"으로 처리하면 **기능이 한 번도 동작하지 않는다**(실사용 확인 — 자동 Drive 보관이 전혀 안 됐다). 인증이 없으면 모달 대신 **막지 않는 토스트 + [인증하고 보관]**(`popupReauth`)으로 안내할 것
- **`.hwp` 는 받지 않는다 (2026-09-04)**: `.hwpx` 는 zip(OPC)이지만 `.hwp` 는 한글 97~2007 의 **복합 바이너리(CFB)** 라 완전히 다른 포맷이고, 한글 처리(rhwp·zip+XML)가 전부 zip 전제다. 종전엔 `detectSourceKind` 가 `.hwp` 를 `'hwpx'` 로 분류해 통과시켜 JSZip 이 `Can't find end of central directory` 를 던졌는데, **터지는 시점이 업로드가 아니라 서명을 다 받은 뒤 완성본을 구울 때**라 가장 나빴다. 방어 3겹 = 판정(`null`, MIME 폴백으로도 안 되살아남) + 업로드 `accept` 제외·`sourceRejectReason()`(무엇을 하면 되는지까지) + 날인 단계 `looksLikeZip()`
