# 학생 개인·학급·과제 일정

## 일정 추가 모달 디자인 (2026-09-10)

- 학생·교사의 모달이 `ScheduleComposeLayout`과 `schedule-compose.css`를 공유한다. 헤더·유형 선택 버튼·입력 테두리·하단 버튼을 같은 스타일로 통일했다.
- 유형 선택은 색상 아이콘, 선택 체크, 키보드 포커스를 갖춘 네이티브 버튼이다. 학생은 3개 유형, 교사는 6개 유형을 표시하며 좁은 화면에서는 3열로 배치한다.
- 헤더를 고정하고 본문을 스크롤하며 저장 버튼은 하단에 유지한다. 내부 드롭다운이 잘리지 않도록 모달 자체에는 overflow 숨김을 적용하지 않는다.
- 날짜·시간을 밝은 회색 영역에 묶고 종일 선택은 스위치로 표시한다. 학생 설명에는 선택 항목 표시와 글자 수를 제공하며, 공유 대상 안내를 짧게 정리했다.
- 교사 화면의 강한 색상 패널을 흰색·얇은 테두리로 바꾸고 중복된 개인일정 안내를 줄였다. 저장·공유 권한과 기존 업무·첨부 기능은 그대로 사용한다.
- 검증: 학생 로그인 화면에서 개인/과제 유형과 수업 드롭다운 선택 확인, 저장할 수 없는 임시 미리보기에서 실제 교사 모달의 렌더링 확인. 프로덕션 빌드와 기능 테스트 7건 통과. 공통 레이아웃·학생 모달 ESLint 통과. 교사 모달에는 기존 `any`, `prefer-const`, `false &&` 관련 ESLint 오류 3건이 남아 있다.

## 과제일정 (2026-09-10)

- 학생의 일정 추가에 **과제일정**을 추가했다. `SearchableMultiSelect`의 `singleSelect` 모드를 사용해 수업 하나를 선택한다. 새 수업을 고르면 교체하고 팝오버를 닫는다. 단일 선택에서는 일괄 붙여넣기·쉼표 일괄 선택을 사용하지 않는다.
- 관리자가 설정한 `academic_term`의 학년도·학기와 학생의 실제 학년에 해당하는 `course_offering` 중 수강생이 등록된 수업을 조회한다. 선택값은 수업 UUID다. 동일 과목도 학급·교사가 다르면 별개 항목이다.
- **과목명 · 학급 · 담당 교사**를 표시하며 내 수업을 먼저 정렬한다. 과목·학급·교사명 검색을 지원하고, 선택 후에도 전체 문구가 줄바꿈되어 보인다. `class_label`이 없는 기존 수업은 `classroom`을 표시한다.
- 공개 대상은 `student_enrollment.course_offering_id`가 일치하는 수강생과 작성자다. 이름이 같은 다른 수업, 같은 반의 비수강생에게는 공개하지 않는다. 작성자만 수정·삭제한다. 수업 변경도 현재 학기·동일 학년 조건을 서버에서 다시 검증한다.
- 수강 신원은 인증 이메일과 학적 정보의 현재 학년·반·번호로 판별한다. 이전 학년도의 학급·번호 재사용으로 과거 과제가 노출되지 않도록 수강 조회를 현재 학년도로 제한한다. 작성자는 과거 작성 내역을 계속 관리할 수 있다.
- 달력·일별 계획표·학생 홈 주간 일정에 과제 유형과 선택한 수업을 표시한다. 기존 개인·학급 공개 정책은 유지한다.
- `20260910010222_student_assignment_events.sql`을 연결된 프로젝트에 적용하고 Supabase 타입을 재생성했다. CLI로 생성한 파일명은 실제 원격 적용 버전과 일치시켰다.
- 검증: 기능 테스트 7건, 실제 DB 트랜잭션에서 과제 수강생 조회·다른 수업 차단·학년/학기 검증·작성자 위조 차단·수업 변경·본인 수정/삭제·익명 접근 차단 및 기존 개인/학급 RLS 회귀 테스트. 테스트 데이터는 모두 롤백한다.
- 수정 UI·기능 파일 ESLint와 프로덕션 빌드 통과. 전체 TypeScript 검사는 기존 오류로 실패했으며, 새 과제 기능 파일에는 오류가 보고되지 않았다. 실제 로그인 화면의 수동 검증은 진행하지 않았다. 보안 Advisor에 새 `school_life` 객체 관련 지적은 없었다.

## 동작

- 학생은 `/schedule`의 **일정 추가** 또는 달력 날짜의 추가 메뉴에서 **개인일정 / 학생일정**을 선택한다. 학생일정은 소속 반과 담임교사에게 공유되는 학급 일정이다.
- 개인 일정은 본인만 조회·수정·삭제한다. 학급 일정은 현재 같은 반 학생과 담임교사가 조회하고, 작성자만 수정·삭제한다.
- 학생의 학급은 인증 계정 이메일의 학적 코드와 `student_basic_info`를 연결해 결정한다. 학급을 임의 입력하거나 다른 반을 선택할 수 없다.
- 담임은 교사 리소스에 부여된 `1학년 1반` 형식의 태그로 판별한다. 여러 학급 태그가 있으면 해당 학급들만 선택할 수 있다. 교사는 기존 **일정 추가** 안의 **학급일정** 유형을 선택한다. 별도 추가 버튼과 사용 중단된 서류제출 생성 버튼은 표시하지 않는다.
- 범례에는 개인일정(남색)과 교사의 학급일정 / 학생의 학생일정(청록색)을 표시한다.
- 학급 일정은 3월 시작 학년도에 귀속된다. 다음 학년도에 같은 학년·반 번호가 재사용되어도 과거 학생들의 학급 일정을 새 학급에 노출하지 않는다. 개인 일정에는 이 학급 공개 제한을 적용하지 않는다.
- 하루 종일·시간 지정·여러 날짜 일정, 제목(120자), 설명(4,000자)을 지원한다. 달력/일별 계획표 및 학생 홈의 이번 주 일정에 함께 표시된다.
- 관리자 역할 미리보기에서는 개인·학급 일정을 조회하거나 작성하지 않는다. 실제 로그인 계정으로 조회·작성해야 한다.

## 저장과 권한

`20260909225905_student_personal_and_homeroom_events.sql`을 연결된 Supabase 프로젝트에 적용했다.

- 새 테이블 `public.school_life_events`에 RLS를 적용한다. 기존 `meeting` 테이블과 학교 공용 일정의 권한을 확장하지 않는다.
- `get_school_life_schedule_context()`는 인자 없이 현재 인증 사용자의 작성 권한과 학급만 반환한다. 공개 RPC는 SECURITY INVOKER이고, 인증이 필요한 내부 신원 조회만 비공개 `school_life_private` 스키마에서 SECURITY DEFINER로 수행한다.
- 학생 신원에는 `auth.users.email`을 사용한다. 사용자가 수정할 수 있는 JWT user_metadata나 화면에서 선택한 반을 권한 근거로 사용하지 않는다.
- 담임의 태그는 실시간으로 읽는다. `user_resource`는 자기 연결을 추가할 수 있는 기존 정책이 있어 그 연결만으로 담임 권한을 부여하지 않는다. 인증 이메일과 교사 리소스 이메일이 일치하는 경우를 사용하고, 기존에 이메일이 다른 교사 연결 1건은 마이그레이션 시 비공개 고정 매핑으로 보존했다. 이 매핑은 일반 사용자가 읽거나 쓸 수 없다.
- INSERT는 본인 작성자·허용 학급·현재 학년도를 검사한다. UPDATE는 제목·설명·시각·종일 여부 컬럼에만 허용해 작성자와 공개 범위를 바꿀 수 없다. 잘못된 수정·삭제가 0행으로 끝나도 성공으로 표시하지 않는다.
- 익명 접근을 허용하지 않는다. 조회는 날짜 겹침으로 제한하고 개인 작성자 및 학년도·학급별 날짜 인덱스를 둔다.
- Supabase 도구로 `src/integrations/supabase/types.ts`를 재생성했다. 생성 결과에는 이 기능 외에 DB에 이미 존재하던 스키마와 기존 타입 파일 사이의 차이도 포함된다.

## 검증

- `npx tsx --test src/features/school-life-schedule/__tests__/schoolLifeSchedule.test.ts` — 작성 권한·학급·학년도·입력 검증·날짜 겹침 5건.
- `scripts/school-life-schedule-test/rls.sql` — 실제 DB에서 학생 2명(같은 반), 다른 반 학생, 담임교사의 인증 역할을 적용해 개인/학급 조회, 작성, 본인 수정·삭제, 타인 수정·삭제 차단, 타 학급 작성 차단, 작성자 위조 및 공개 범위 재지정 차단을 검증했다. 마이그레이션 적용 전·후 모두 `BEGIN … ROLLBACK`으로 실행해 테스트 일정은 남기지 않았다.
- Supabase 보안 Advisor 확인 결과 새 `school_life` 객체에 대한 지적은 없었다. 프로젝트 전체의 기존 경고는 별도 작업 대상이다.
- 학생 홈과 일정의 회귀 테스트 총 16건 및 `npm run build`가 통과했다. 전체 TypeScript 검사는 기존 프로젝트 오류로 실패하며, 새 기능 파일에서 보고된 오류는 없다.
- 로컬 Edge에서 실제 관리자 계정의 개인·학급 일정 추가 버튼과 작성 대화상자(공개 범위·종일·시작/종료·설명)를 확인했다. 실제 일정 저장은 위 DB 트랜잭션 검증으로 확인했다.

## 알려진 제한

- 학년도 변경 시 과거 학급 일정은 해당 학급의 현재 구성원에게 공개되지 않는다. 별도 학급 이력 열람 기능은 제공하지 않는다.
