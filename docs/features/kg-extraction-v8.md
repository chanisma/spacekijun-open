# 학생 지식그래프 추출 v8 (`scripts/kg-extract-v8/`)

탐구 설계(`/inquiry-design`)가 읽는 학생별 지식그래프를 만드는 파이프라인.
**2026-09-12 전 학년 적용 시작**, 모델은 **Solar Pro 4**.

> 이 문서는 **왜 그렇게 만들었는지와 운영 실측값**을 담는다.
> 단계별 규칙의 세부는 코드 주석이 정본이다(`select-nodes.mts`·`llm-stages.mts`·`assemble.mts`).
> 창체 GraphRAG(재료를 만드는 쪽)는 `docs/features/creative-activities-graphrag.md`,
> 방법론 스킬은 `/inquiry-graphrag`.

## 왜 새로 만들었나 — 앞의 둘이 각각 반쪽이었다

| 엔진 | 학생 | Activity | Concept | Competency | Achievement | Attitude |
|---|---|---|---|---|---|---|
| `solar-pro3` (구, 9-stage/4-pass) | 412 | 14,673 | 11,134 | 20,266 | 9,974 | 6,775 |
| `research-v7` (신, 3학년만) | 218 | 19,464 | 3,117 | **0** | **0** | **0** |

- **구 파이프라인**은 사람 층(역량·성취·태도·역할)을 채우지만 **기록 1행 = 활동 1개**로 강제해
  한 기록에 든 여러 탐구가 뭉개졌다. 그리고 관계를 **활동 1건 안에서만** 판단해
  **활동↔활동 엣지가 구조적으로 0개**였다.
- **신 v7**은 분절과 활동 간 서사를 얻었지만 S5(traits)를 배치에서 빼 **사람 층이 0개**다.
- **1학년(26학번) 222명은 그래프가 아예 없었다.**

그 사이에 창체 GraphRAG가 더 나은 재료를 만들었다 — `inquiry_activity` 52,268건이
네 코호트를 덮고, 활동마다 분절 점수(`usefulness`)·탐구 판정(`is_inquiry`)·심화 수준(`level`)·
정규화 개념(`inquiry_activity_concept`)을 갖는다. v8은 **구 파이프라인의 어휘·가드·사람 층
분석을 기반으로 하되 입력을 분절된 활동으로 바꾼 것**이다.

## 단계

```
E0 재료·활동 노드   코드     LLM 0   inquiry_activity → Activity + Concept + Interest 노드 확정
E1 사람 층          Solar    20건 묶음   Competency/Achievement/Attitude/Role/Person/Book
E2 서사·Thread      Solar    학생당 1콜  활동↔활동 엣지 + Thread
E3 조립·검증·저장   코드     LLM 0   가드 적용 → kg_json → save_kg_version
```

**노드를 먼저 놓고 나머지를 채운다**(사용자 결정). 활동·개념·관심은 코드가 데이터에서
확정하므로 LLM 변동이 없고, 같은 개념이 학생 간 같은 노드가 된다.

### E0 문턱은 **고정**이다

```
is_inquiry ∧ (usefulness ≥ 5 ∨ level ≥ 3)
```

학생당 쿼터를 두지 않는다 — **품질 기준은 활동 자체의 성질이지 학생의 사정이 아니다.**
상대 문턱(학생당 상위 N)은 1학년을 억지로 채우거나 3학년을 잘라 내 양쪽으로 왜곡한다.
그 결과 1학년 13명은 통과 활동이 0건인데, **그건 1학기라 재료가 실제로 없는 것이라 정직한 값**이다
(빈 그래프를 만들지 않고 건너뛴다).

### E1 이 20건씩 묶는 이유

v7 실험에서 **단일 대형 콜**이 같은 학생·같은 조건 3회에 출력 46,734/51,582/98,817자
(Competency 3/4/78)로 갈렸다. 원인은 데이터가 아니라 **표본 1개 구조**였다.
묶음은 표본 수를 늘린다. **개수 목표는 두지 않는다** — v7 의 E1v4 가 활동당 최소 엣지를
강제하자 심화 엣지가 11 → 98 로 튀었다.

### E2 의 방향은 **코드가 정한다**

모델은 "이어졌는가"만 답하고 시간 순서는 `grade*10 + semester` 로 코드가 붙인다.
v7 실험에서 모델이 시간 엣지 **20개 전부** 방향을 틀렸다. 같은 시점이면 무방향 `RELATED_TO`.
Thread 는 **구성원 3 이상**일 때만 만든다.

### E3 — 출력 계약 (지키지 않으면 조용히 깨진다)

| 항목 | 요구 | 어기면 |
|---|---|---|
| `source_stats.extraction_engine` | **`research-v7` 이 아닌** 값 (`solar-pro4-seg-v8`) | v7 스타일로 그려진다 |
| `entities[]` + **`triples[]`** | 둘 다 | 버전 선택기가 "엣지 0" |
| `entity_id` | `^[a-z]+_[a-z0-9]{6,}$` | 설계 프롬프트가 라벨을 버린다 |
| entity `properties` | **평탄하게** | 트리거가 `properties.properties` 로 이중 포장 |
| relation `properties` | `confidence`·`evidence` | `source` 키는 **트리거가 지운다**(그래서 층은 `layer`) |

`triples` 와 `relations` 는 **내용으로** 대조한다 — 처음엔 `kg.triples !== kg.relations`(참조 동일성)로
썼는데 같은 프로세스에서만 통과하고 파일을 거치면 무조건 실패했다.

## 관심분야 lift 거르기 (2026-10-02 — **기각**, 시범분 되돌림)

> **결론**: 시범 3명을 화면으로 본 사용자 판단 — 의미가 크게 늘지 않는다. 시범 v5 3건은 삭제해 v4 로 되돌렸다
> (참조 자료 0건 확인 후). 갈래 자체가 열람용 분류라 거르는 것만으로는 학생을 설명하지 못한다는 것이 원인이다.
> 후속 = **흐름 분야**(아래 절) — 관심분야 노드를 걷어 내고 흐름마다 학문 분야를 붙인다. 스크립트·회귀는 재현 기록으로 남긴다.

**문제**: E0 의 관심분야 규칙(학생 E0 활동 중 같은 상위 주제군 3건 이상)은 **관심이 아니라 분량**을 쟀다.
상위 주제군은 학교 활동의 최대 16%(사회·윤리·제도)라 활동이 많으면 저절로 3건이 찬다 — 활동 30건 이상
학생의 82% 가 「사회·윤리·제도」를, 전체의 48.4% 가 같은 관심분야를 가졌다. 상위 주제군은 창체 **열람 화면용**
(k = √리프 수 = 39)으로 만든 것이라 학생 설명용으로는 굵기와 층위가 맞지 않는다(39개 중 학생에게 실제로
쓰이는 것 약 17개 · 의학·생명이 세 갈래로 갈림).

**규칙** = `≥3건 ∧ lift ≥ 1.5` (lift = 학생의 그 갈래 비율 ÷ 학교 기준 비율). 시뮬레이션(학생 616 · 활동 11,780,
현행 규칙 재현값 = 실제 KG 와 일치): 학생당 2.05 → 1.29개 · 가장 흔한 관심분야 48.4% → 16.2% · 0개 학생
33.6% → 36.9%. lift 1.25/2.0/3.0 · 이항검정 p≤0.10/0.05 도 쟀다 — 이항검정은 활동 20~30건 학생의 절반을
0개로 만들어 기각.

**적용** = `scripts/kg-extract-v8/interest-lift.mts` — LLM 없이 최신 v8 KG 에서 Interest 노드와 **그 노드에 닿는
엣지 전부**(ENGAGED_WITH · 학생 허브 INTERESTED_IN · LLM 엣지)를 빼고 남은 노드에 `lift` 를 적어 **새 버전**으로
저장한다(되돌리기 = 새 버전 삭제). 기준 비율은 실행 시점의 모집단(최신이 v8 인 학생)으로 계산해
`source_stats.interest_rule` 에 고정한다. 기본은 미리보기, `--apply` 로 저장, 이미 적용된 학생은 건너뛴다.

- ⚠️ **재계산한 ≥3건 집합이 KG 의 Interest 와 정확히 같을 때만** 적용한다. 다르면 GraphRAG·활동 데이터가
  KG 생성 뒤 바뀐 것이다(실측 2명: 테스트 학생 00-00001, 00-00645) — 건너뛴다.
- ⚠️ lift 비교에 허용 오차 1e-9 — `6 ÷ 20 ÷ 0.2 = 1.4999999999999998` 이라 정확히 문턱인 값이 떨어진다
  (실데이터에서는 해당 0건이었다).
- 시범 적용(되돌림) = 00-00343(7→1) · 00-00234(3→2) · 00-00244(3→0). 전원 미리보기였던 값: 저장 예정 285명 ·
  변화 없음 328명 · 관심분야 제거 458개.

회귀 = `npx tsx scripts/kg-interest-lift-test/run.mts`(22건).

## 흐름 분야 — 관심분야 노드를 대신한다 (2026-10-02 — **전원 적용**)

**결정 (사용자)**: 주제군 관심분야(Interest) 노드를 걷어 내고, **탐구 흐름(Thread)마다 학문 분야 하나**를 붙인다.
관심분야 노드는 새로 만들지 않는다. 흐름은 이 학생이 실제로 이어 간 탐구라서 그 위의 분야가 학생을 설명한다.
화면은 흐름 노드 라벨 둘째 줄에 `분야: …` 를 쓴다(`inquiryGraph.ts` 의 `sourceAwareNodeLabel` — 활동의 `출처:` 와 같은 자리).

**구성**: `scripts/kg-extract-v8/thread-fields.mts`(LLM 분류 한 번 → 코드 검증 → 새 버전 저장) ·
`academic-fields.mts`(분야 32개 · 계열 7개, KEDI 중계열을 고교 탐구 수준으로 조정) ·
`prompts/thread-fields.md`. 저장 = 흐름에 `field`·`field_group` 속성 + Interest 노드와 그 엣지 전부 제거
(`source_stats.thread_field_method`). 흐름이 없는 학생은 LLM 없이 관심분야만 걷어 낸다(두 방식이 섞이지 않게).
잘렸거나 분야가 빠진 흐름이 있으면 저장하지 않는다. 회귀 = `npx tsx scripts/kg-thread-fields-test/run.mts`(36건).

**시범 다섯 판에서 배운 것** (학생 6~12명 × 2회, 같은 입력 반복으로 안정성을 쟀다):

|---|---|---|---|---|
| 1 | LLM 이 흐름을 묶어 관심분야 | — | — | 흐름 하나짜리가 22/39, 이름이 흐름 이름의 복사(글자쌍 겹침 중앙값 0.90) |
| 2 | 흐름 분야 + LLM 묶기(2개 이상만) | 93% | Jaccard 0.50 | 분류는 안정, **묶기 판단이 불안정** |

## 조용히 틀리는 자리

- **⚠️ 완료 판정은 "성한 결과가 하나라도 있는가"가 아니라 "최신 버전이 성한가"다 (2026-09-15 실제 사고).**
  재시도가 있으면 한 학생에게 여러 버전이 남는데 **화면은 최신만 그린다**. `remaining.mts` 가
  처음엔 "성한 버전이 하나라도 있으면 완료"로 판정해, 00-00239 의 버전 7(Thread 10, 정상) 뒤에
  버전 8(Thread 0, **E2 출력 잘림**)이 온 경우를 건너뛰었다 — 활동 66개 학생의 서사 층이 빈 채 남았다.
  같은 사고를 겪은 다른 6명은 순서가 반대라 저절로 나아서 **문제가 6/7 확률로 숨는다**.
  사용자가 그래프를 눈으로 보고 "THREAD 가 없다"고 알려 주기 전까지 아무 신호도 없었다.
  → 판정은 **소비되는 그 버전**(= 최신)만 본다. `alreadyDone()` 은 원래 `order=version.desc&limit=1` 이었고,
  그 위에 얹은 스크립트가 규칙을 어긴 것이 원인이다 — **같은 질문에 답이 두 벌이면 반드시 갈라진다.**

- **⚠️ 배경 러너를 재시작할 때 자식만 죽이면 루프가 살아남는다 (2026-09-15 실제 사고).**
  동시성을 바꾸려고 `node` 만 죽였더니 **bash 루프가 다음 조각으로 넘어가** 새 인스턴스와 둘이 돌았다.
  둘이 같은 재개 파일에 **서로 다른 조각 크기의 번호**를 써서 그 파일이 무의미해졌고,
  학생 8명이 조용히 두 번 추출됐다(오류 0건 · 로그상 정상). 들킨 것은 "완료 조각 3인데 학생 20명"이라는
  **산술 불일치** 때문이었다. → 죽일 때는 **부모(루프)를 먼저** 죽이고 세어서 확인하며,
  러너에 **락**(PID 파일 + `kill -0`)을 둔다. 그리고 재개 근거를 **파일이 아니라 DB** 에 둔다
  — 파일은 누가 썼는지·어떤 기준인지·그 사이 DB 가 어떻게 됐는지를 모른다.

- **감시기가 감시 대상보다 먼저 죽을 수 있다.** 진행 감시를 `Get-CimInstance` 로 하고 있었는데
  시스템이 커밋 한도에 닿자 **PowerShell 자체가 실행되지 못했고**(`0x800705AF`), 프로세스 수가
  빈 문자열 → `0` 으로 읽혀 "러너 멈춤"을 선언하고 감시기가 스스로 종료할 뻔했다(러너는 멀쩡했다).
  자원이 부족한 순간에 무거운 도구는 정확히 그때 실패한다 → 생존 판정은 **로그 파일의 갱신 시각**으로 한다.

- **429 경보는 "일어난 일"이 아니라 "행동이 갈리는 지점"에 걸 것.** 429 자체는 설계된 정상 동작
  (대기 후 재시도)이라 그걸로 울리면 10시간 내내 울며 정작 중요한 신호를 묻는다.
  울려야 하는 것은 ①백오프 **최종 회차**(동시성을 낮춰야 한다는 신호) ②`회 실패|출력 잘림`
  (사람 층 결손) ③조각 실패 ④프로세스 사망 — `alreadyDone()` 과 **같은 정규식**을 쓸 것.

- **⚠️ 429 는 "실패 0" 을 보고하면서 데이터를 잃는다 (2026-09-12 실제 사고).**
  1학년 1차 실행(동시 8)이 **실패 0** 을 출력했는데 실제로는 E1 104콜·E2 78콜이 죽었고
  **104명이 사람 층 없이 저장**됐다. 원인 둘 — `callOpen2` 의 재시도에 **대기가 없고**,
  배치 실패를 경고로 삼켰다. 지금은 `callWithBackoff`(30/60/90초) + 동시 기본 4 이고,
  `alreadyDone()` 이 **버전 존재가 아니라 실패 경고 부재**로 판정한다.
  창체에서 잰 동시 상한 8 은 **짧은 호출 기준**이라 여기(한 콜 80~200초)에는 맞지 않는다 —
  요청 수가 아니라 **토큰 속도**에 걸린다.
- **`inquiry_activity` 를 학생 목록의 출처로 쓰지 말 것.** 52,268행이라 코호트로 훑으면
  `57014 statement timeout`(authenticator 8초)을 맞는다. 대상은 **630행짜리 `resource`**
  (`type='student' ∧ status='active'`)에서 고르고 학적 코드 앞 두 자리로 코호트를 가른다.
- **PostgREST `in.(...)` 는 `#` 에 잘린다.** 활동 id 에 `#` 가 있어 목록을 통째로
  `encodeURIComponent` 해야 한다(`select-nodes.mts` 의 `quoted()`).
- **엔드포인트 계약이 두 벌이면 산출물이 경고 없이 사라진다.** 구 파이프라인은
  `FP_ALLOWED_ENDPOINTS` 와 본 계약이 서로 어긋나 pass4 결과 일부가 조용히 삭제됐다.
  v8 은 `lib.mts` 의 `ALLOWED` 한 벌로 합쳤다.
- **개념 규칙을 "학생 안에서 2회 이상"으로 두면 안 된다.** 33개 활동 학생에게 개념이
  **2개**만 남았다(157종 중 2종만 반복). 지금은 **활동당 상위 2개 ∧ `is_node`** 다.
- **육안 검토를 마친 그래프는 파일로 올린다**(`save-file.mts`). 다시 돌리면 LLM 이 다른 것을
  내므로 "확인했다"가 사실이 아니게 된다.
