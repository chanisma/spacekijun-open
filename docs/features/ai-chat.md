### LLM 호출 (공용 어댑터, 2026-07-31)
- **새 기능에서 `supabase.functions.invoke('openai-proxy'/'solar-proxy', {action:'chatCompletion'})`를 직접 쓰지 말 것.** `aiChat()`(`src/services/aiChat.ts`)을 쓴다. 이전엔 5개 기능이 invoke를 각자 복붙해, 공급자를 바꾸려면 기능마다 손대야 했고 모델 ID·오류 처리가 제각각 어긋났다.
- **기본 공급자 = Solar**(`DEFAULT_AI_CHAT_PROVIDER`), 기본 모델 = **`solar-pro4`**(`SOLAR_CHAT_MODEL`, **2026-09-21 사용자 결정으로 pro3 → pro4 복귀**). 선택지는 `SOLAR_MODELS`(`aiChat.ts`·`solar-proxy` 양쪽에 같은 형태)에 모아 뒀고 **`pro3`는 보관**(둘 다 `GET /v1/models`로 생존 확인) — **지우지 말 것**, 이미 저장된 이력 행(`activity_analysis.model`·KG `engine`)이 그 값을 갖고 있고 그것을 해석하는 화면이 있다. **이 파일의 벽시간·추론 비중 수치는 전부 pro4 실측이라 이제 기본 모델의 값**이다(기억 노트 `solar-pro4-tuning-knowledge`) — 2026-08-14~2026-09-21 사이 pro3 기간에는 그 값들이 기본 모델과 어긋나 있었다. OpenAI 경로는 제거하지 않았고 `aiChat({ provider: 'openai' })`로 쓴다. 이 상수 한 줄이 세특 작성·문서 분석·입시 뉴스 분석·HWPX AI 작성·암기카드 생성의 공급자를 함께 정한다.
  - **⚠️ 이 한 줄을 바꾸면 `specFillService.PLAN_REASONING_EFFORT_BY_MODEL`이 함께 켜지고 꺼진다**: 그 표는 **측정된 모델만** 담는 설계라(`{[SOLAR_MODELS.pro4]: 'none'}`) pro3 기간에는 조회가 빗나가 `reasoning_effort`를 **아예 보내지 않고** 있었다. pro4 복귀로 `'none'`이 다시 실린다 — 의도된 동작이지만, HWPX 계획 생성의 속도·품질이 달라지면 여기부터 의심할 것.
- **모델 ID는 클라이언트와 엣지 함수 양쪽에 있고, 둘 다 고쳐야 한다**: `solar-proxy`는 요청 body의 `model`을 그대로 쓰되 **없으면 자기 기본값**을 쓴다. 그래서 `aiChat()`(항상 모델을 실어 보냄)만 고치면 model을 생략하는 호출부(`specFillService.solarProxyChat`)는 계속 죽은 모델로 나간다 — 2026-08-11 workflow 스펙 채움 장애가 정확히 이 경로였다. 교체 지점 = `src/services/aiChat.ts`·`solar-proxy`·`openai-proxy`·`inquiry-comprehensive/providers.ts` **4곳 + 모델을 직접 적는 호출부**(`evalog/utils/solarApi.ts`·`activityAnalysisService.ts`).

Solar Pro 4 컨텍스트는 524,288토큰인데 우리가 싣는 가장 큰 블록(분석 프롬프트의 엔티티 120개)이 실측 평균 35,098자·최대 57,877자로 3~6%에 불과하다. 텍스트 예산을 만질 땐 ①같은 상수가 몇 군데 복붙돼 있는지 먼저 세고(그때 `2000`이 **네 곳**이었다) ②자르는 **방향**이 보존하고 싶은 쪽과 맞는지 확인하라 — `slice(0, N)`은 앞을 남기므로, 뒤로 갈수록 중요한 데이터(대화·로그·시계열)에는 정확히 반대로 작동한다.

- **wire 공급자 값과 모델 ID를 혼동하지 말 것**: inquiry-design의 `InquiryAiProvider`(현재 `'solar-pro4'`, 구 값 `'solar-pro3'`·`'solar-open2'`는 **읽기 전용으로 계속 수용**)는 "Solar로 돌려줘"라는 **선택자**이고 모델 ID와 우연히 같을 뿐이다. 그래서 **모델 교체 때 함께 바꾸는 대상이 아니다** — 이미 저장된 이력 행이 구 값을 갖고 있다. 값을 바꿀 땐 엣지 함수 3곳(`normalizeInquiryProvider`/`isSolarProvider`/`index.ts` 타입)이 **구 값을 별칭으로 계속 받아주게** 둔다 — 프런트 배포가 엣지 함수보다 빠르거나 느려도 조용히 OpenAI로 새지 않는다.
- **`model`은 공급자와 반드시 짝**: OpenAI 모델 ID를 Solar 경로로 보내면 거부된다. 호출부는 모델을 생략하고 `resolveAiChatModel(provider, model?)`이 정하게 두는 것이 기본이며, 이력·표시용 모델명도 이 함수로 얻는다. **단 `specFillService.solarProxyChat`은 예외적으로 모델을 명시한다(2026-08-14)** — 생략하면 엣지 함수 기본값에 기대게 되고, 그 탓에 `solar-open2` 폐기 때 이 경로만 홀로 죽었다(프런트를 배포해도 서버 기본값이 낡아 있으면 스펙 채움만 계속 실패).

- **⚠️ `maxCompletionTokens`는 solar 경로에서 조용히 무시된다**: `aiChat`이 그 값을 `provider === 'openai'`일 때만 실어 보내고 `solar-proxy`는 `max_tokens`를 아예 보내지 않는다. **기본 공급자가 solar이므로 호출부가 예산을 적어 두는 것만으로는 예산이 정해지지 않는다.** 추론 토큰과 최종 출력이 **같은 예산**을 나눠 쓰는 모델에서 이건 "답이 중간에 끊기는데 이유를 알 수 없는" 상태다 — 입시 정보 AI 분석의 `JSON을 찾을 수 없습니다`가 그 증상이었다(실측 근거: 성공한 분석 2건이 모두 OpenAI 경로 시절 산이다). **대처는 두 가지뿐**이다 — ①그 호출을 `provider: 'openai'`로 보낸다(입시 정보 분석·스펙 채움이 택한 길: `gpt-6-luna`) ②`solar-proxy`에 상한 지원을 **추가하고 배포**한다. ②를 할 땐 **지정하지 않은 호출에는 아무것도 보내지 말 것** — Upstage 기본값이 문서에 없어(2026-09-11 확인) 하한을 전원에게 강제하면 상한이 없던 다른 호출부(문서 생성 등)의 긴 출력을 **새로** 자른다. 하나를 고치려고 다섯을 깨지 않는다.
