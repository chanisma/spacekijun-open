# purchase-requests

> CLAUDE.md 에서 분리한 상세 문서. 스키마·마이그레이션은 `docs/database/purchase-request.md` 참조.

구매 신청 게시판 (`/purchase-requests`). 매니저가 페이지(기간·대상·컬럼 정의)를 만들고 학생/교사가 품목을 신청하면, 매니저가 상태(제출됨/검토중/승인/완료/불가)를 사유와 함께 관리한다.

**매니저 = 페이지 작성자 ∪ 공동 작업자**(`is_purchase_page_manager`). 아래에서 "작성자만"이라 적지 않은 매니저 권한은 둘 다에게 열려 있다.

## 화면 뼈대 — 탭은 헤더 카드 안에 (2026-09-02)

목록·세부 두 페이지 모두 **탭 전환기를 헤더 글래스 카드 안**에 둔다(사용자 지시). 본문 위에 따로 떠 있던 `TabsList` 를 없애 화면 상단이 한 덩어리로 읽힌다.

- **`Tabs` 루트가 헤더와 본문을 함께 감싼다** — 탭 트리거와 `TabsContent` 가 같은 루트 아래 있어야 하므로, 헤더만 감싸거나 본문만 감싸면 동작하지 않는다.
- **목록 페이지**(`PurchaseRequestsPage`): 헤더 마지막 줄이 `[신청 페이지 | 내 신청]` + 검색 입력 **한 줄**이다(세로로 쌓으면 헤더가 길어진다. 좁은 화면에서만 검색이 아래로 내려간다).
  - 탭이 헤더로 올라오면서 헤더의 **건수·검색 placeholder 가 탭을 따라간다** → `Tabs` 를 controlled(`tab` state)로 바꿨다. 건수와 탭이 나란히 있으니 어긋나면 바로 눈에 띈다.
  - **보관함 버튼은 '신청 페이지' 탭에서만** 렌더한다 — 내 신청 목록에는 안 걸리는 필터다. `hidden` 속성으로는 안 사라진다(Button 이 `inline-flex` 라 Tailwind 유틸리티가 preflight 의 `[hidden]{display:none}` 을 이긴다) → 조건부 렌더.
- **세부 페이지**(`PurchaseRequestDetailPage`): 탭이 **조건부**(`showTabs` = 매니저이면서 신청 대상)라 헤더를 `headerCard(tabs: ReactNode)` 함수로 만들고 슬롯만 갈아 끼운다. 헤더 JSX 를 두 벌 적으면 한쪽만 고치는 사고가 난다. 탭이 없으면(`null`) 그 줄 자체가 렌더되지 않는다.

## 화면 개편 — 단계 탭 · 툴바 두 줄 · 내 품목 한 목록 (2026-10-13)

요구는 "UI/UX 대폭 개선", 사용자가 꼽은 불편은 **"전체적으로 복잡·산만함"**. 운영 규모(페이지 5 · 신청 69 · 신청당 품목 1.4개 ·
열 1~2개)에 비해 장치가 컸다. **기능과 DB 는 그대로**이고 배치만 바꿨다. 과정·기각한 안 = `src/features/purchase-requests/PROMPTS.md`.

### 매니저 — 단계 탭 (`components/ManagerStepTabs.tsx`)
- `[신청 관리 | 품의 정리 | 내 신청]` → `① 신청 검토 ●N · ② 품의·구매 ●M · 내 신청`. **탭 값은 그대로**(`manage`·`order`·`mine`) — 딥링크 `?tab=` 가 이 값을 쓴다.
- 숫자 = 남은 일. ① 처리 대기 품목, ② 품의에 안 담긴 품목(불가 제외). 판정 단일 출처 = `utils/managerSteps.ts` — **탭 안의 숫자와 같은 정의**여야 한다(① = 상태 칩 «처리 대기», ② = 품의 요약 «아직 안 담김»). 0 이면 숫자를 감춘다.
- 두 탭 본문과 같은 쿼리 키라 추가 요청이 없다.

### 매니저 «① 신청 검토» (`ManagerView`)
- 머리 = **두 줄**: 검색 + [보기 ▾] / 상태 필터 알약 + 요약 한 줄(신청자·신청·품목·합계). 제목 «전체 신청 내역»·보기 3종 버튼·통계 4칸·정렬 드롭다운·쇼핑몰별 묶기·전체 열·CSV 를 걷었다.
- **[보기 ▾]** (`components/ViewOptionsMenu.tsx`) = 묶는 단위(품목별·신청건별·신청자별) · 정렬 · 쇼핑몰별로 묶기 · 선택 입력 열까지 모두 보기 · CSV. 기본값에서 벗어난 설정이 있으면 버튼에 파란 점 — 메뉴에 숨긴 설정 때문에 표가 다르게 보이는 이유를 찾게 한다.
- **상태 필터 = 전체 · 처리 대기 · 승인 · 완료 · 불가**. «처리 대기» = 제출됨 ∪ 검토중(`utils/statusFilter.ts`). 검토중은 운영에서 0건이라 따로 두지 않았다(상태 값 자체는 그대로 — 상태 변경 팝오버에서 고를 수 있다). 0 인 칩은 감추되 **지금 고른 칩은 남긴다**.
- **처음 열 때 처리 대기가 있으면 그것만** 보인다. 한 번만 — 매니저가 «전체»로 바꾼 뒤 데이터가 다시 읽혀도 되돌리지 않는다(`autoFilterDoneRef`).
- 필터가 걸리면 요약이 «품목 N개» 대신 **«보이는 품목 N개»** — «전체 7» 옆의 «품목 3개»가 모순처럼 읽혔다(스크린샷에서 발견).
- **선택 바는 하나**: `N개 품목 선택 · [상태 변경] · [품의 차수에 올리기 ▾] · [⋯ 품의 없이 바로 공문 만들기 / 물품명 일괄 변경] · 선택 해제`. 주된 흐름(승인 → 품의)을 앞에, 품의를 건너뛰는 공문은 ⋯ 안으로.
- 결과 0건이면 «전체 보기» 링크를 함께 준다.

### 매니저 «② 품의·구매» (`PurchaseOrderView`)
- 통계 4칸 → 한 줄 요약(신청 품목 · 품의에 담김 · **아직 안 담김**(0 아니면 앰버) · 차수). 나머지는 그대로.

### 신청자 — 내 신청 품목 한 목록 (`RequesterView`)
- 신청서 카드(기본 접힘 · 카드마다 이력·수정·삭제 · 상태 스테퍼)를 없애고 **품목 한 목록**. 줄마다 물품명 + 상태 / 나머지 칸(«열이름 값») / 품의 진행 / 사유(불가는 로즈). 머리에 상태별 칩·합계.
- **저장 단위는 그대로 신청건이다.** 펼치기·고치기·지우기 계획 = `utils/myItems.ts`(순수):
  - `planReplaceRow` — **행 id 유지**. 품목 상태(`meta.itemStatus`)와 품의 연결이 이 id 에 묶여 있어, 새 id 를 주면 승인된 품목이 새 품목이 되고 품의에서 고아가 된다.
  - `planRemoveRow` — 지운 뒤 실제 품목이 0 이면 **신청 자체를 삭제**(빈 신청이 매니저 화면에 «0개 품목»으로 남지 않게).
- 품목 하나 고치기 = ✎ → `requester/ItemEditDialog`(그 품목의 칸만). 이미 처리된 품목이면 "처리 상태는 그대로 남는다"를 알린다 — 사실이다: `guard_purchase_request_status` 가 비매니저의 status·itemStatus 변경을 되돌린다.
- 새 품목 = «품목 더 신청하기» → `requester/NewRequestPanel`(여러 줄 한 번에). **새 신청(INSERT)으로 낸다** — 기존 신청에 행을 끼워 넣으면 UPDATE 라 담당자 알림이 가지 않는다. 아직 신청한 품목이 없으면 작성 칸이 바로 열려 있고 [취소]가 없다.
- 필수 칸 검사·링크 `https://` 보정은 새 신청 표와 수정 창이 같은 함수(`missingRequiredColumns`·`normalizeCellValue`)를 쓴다.
- `StatusStepper` 는 지웠다(유일한 사용처였다). 수정 이력 창은 `requester/RequestHistoryDialog` 로 옮겼고 ⋯ «신청 수정 이력»에서 연다.
- 사용 방법 안내(`guide/`)의 목업 문구도 새 화면에 맞췄다(«품목 더 신청하기» · 요약 칩 · «① 신청 검토» · «상태 변경» · «⋯ 바로 공문 만들기»).

### 남긴 것
- 휴대폰에서 매니저 품목 표의 상태 열이 가로 스크롤 밖에 있다(개편 전부터).
- 동아리 페이지가 `동아리명(한 칸에만 입력)` 처럼 **신청 단위 정보를 품목 칸에** 넣고 있다 — 페이지에 «신청서 공통 항목»이 필요하다(DB 변경).
- 목록 페이지(진행 중 / 마감 / 보관 구분)는 이번 범위 밖.

## 품목(항목) 단위 승인 (2026-09-02)

종전엔 `status` 가 신청건 1건에 하나뿐이라 **"3개 중 2개만 승인"을 표현할 수 없었다**. 지금은 품목마다 상태·사유를 갖고 **신청건 상태는 품목 상태에서 파생**된다(단일 출처).

### 저장·쓰기
- 저장 = `purchase_requests.meta.itemStatus` = `{ "<items[].id>": {status, reason, at, by} }`.
  **새 테이블을 만들지 않았다** — `items` 가 JSONB 라 행 id 에 FK 를 걸 수 없어, 별도 표를 둬도 참조 무결성은 똑같이 없고 조인만 늘어난다(`task.meta.assignees` 와 같은 패턴). 채택 전 라이브 62행 전부 `meta` 가 비어 있음을 확인했다.
- **쓰기는 `set_purchase_request_item_status(p_request_id, p_status, p_row_ids, p_reason)` RPC 하나뿐**. 직접 UPDATE 를 허용하면 ①JSONB read-modify-write 로 동시 승인이 서로를 덮어쓰고 ②파생이 클라이언트로 새어 나가 화면마다 답이 갈린다.
  - `p_row_ids` 생략(NULL) 또는 전 품목 → 신청건 전체 변경(종전 UX 유지). 그 외 → 지정 품목만.
  - 클라이언트 진입점은 `useUpdatePurchaseRequestStatus({ requestId, status, reason, rowIds })` 하나다.

### 파생 규칙 (TS·SQL 두 곳에 있다)
- 전부 같으면 그 상태 / 미결(`submitted`·`pending`)이 하나라도 있으면 `pending` / 전부 종결이면 `completed`+`rejected` 조합만 `completed`, 그 외 혼재는 `approved`.
- 마지막 규칙의 이유: **승인만 되고 아직 안 산 품목이 남았으면 '완료'라고 말하면 안 된다**.
- 구현이 `utils/itemStatus.ts`(`deriveRequestStatus`)와 SQL `purchase_derive_request_status()` **양쪽에 있다** — 한쪽만 고치면 화면과 서버가 다른 상태를 말한다. 회귀가 같은 표를 양쪽에 돌린다.

### 호환·기준선
- 품목 상태가 없는 기존 신청은 **전 품목이 신청 상태를 따른다**(폴백). 데이터 마이그레이션 없음.
- RPC 가 처음 호출될 때 나머지 품목을 **현재 신청 상태·사유로 채워 기준선**을 만든다. 이걸 안 하면 "미설정 품목은 신청 상태를 따른다" 폴백과 파생이 서로를 참조해 **순환**한다.
- **일부 품목만 바꾸면 신청건 `status_reason` 을 지운다** — 신청 전체를 설명하던 문장이 더는 맞지 않기 때문. 기준선에서 각 품목이 그 사유를 복사해 갔으므로 정보는 사라지지 않는다.

### 보안 2중 (라이브 실측)
- RPC 가 `is_purchase_page_manager` 를 재검증 → 신청자 호출 시 42501 거부.
- `guard_purchase_request_status` 트리거가 비매니저의 **`meta.itemStatus` 직접 쓰기를 되돌린다**(`meta` 의 나머지 키는 그대로 둔다). 종전 guard 는 status/status_reason 만 지켰다.

### 이력
`purchase_request_history` 에 `meta` 컬럼을 추가하고 트리거가 **meta 변경도 기록**한다. 품목 하나만 승인하면 파생 status 가 그대로일 수 있어(3건 중 1건 승인 → 여전히 pending) items/status 만 보면 그 결정이 이력에서 통째로 사라진다.

### 화면
- **품목별 뷰**: 상태 열이 품목 상태(배지 클릭 = 그 품목만 변경). 선택 후 **일괄 품목 상태 적용** — 같은 신청의 품목은 묶어 한 번에 보낸다(품목마다 호출하면 같은 신청의 meta 를 연속 read-modify-write 한다).
- **신청건별·신청자별 뷰**: 품목마다 상태 열 + 헤더에 분포 칩(`승인 2 · 불가 1`, 갈릴 때만). 헤더 배지는 신청 전체(= 모든 품목) 변경.
- **신청자 화면**(`RequesterView`): 품목 표에 `처리 상태` 열과 품목별 사유. 품목 상태가 갈리면 신청 전체 사유 배너는 감춘다(품목 칸이 각자 사유를 보여준다).
- **품목별 뷰에서는 상태 필터·분포 칩이 품목 단위**로 센다 — 신청건 기준이면 "pending 신청 안의 approved 품목"이 통째로 사라진다.
- CSV 내보내기는 행 단위라 **그 품목의** 상태를 적는다.

## 공문 본문 만들기 (2026-09-02)

매니저 뷰에서 **품목** 또는 **신청건**을 골라 학교 공문 본문을 만든다. 뷰마다 선택 단위가 다르지만(품목별=품목 체크, 신청건별·신청자별=신청 체크) **공문은 언제나 품목 목록을 받고**, 신청건 선택은 그 신청의 품목 전부로 펼친다.

### 본문에 넣지 않는 것 (사용자 지시로 차례차례 걷어냈다)
- **제목·학교명·수신·경유·기안자·기안일·결재란·예산 과목** → 문서관리시스템(에듀파인) 양식 필드라 본문에 쓸 자리가 없고, 여기서 받으면 같은 정보를 두 번 적게 된다.
- **품목 표** → 본문이 아니라 **붙임**으로 나간다.

남는 입력은 **구매 목적·사유 / 관련 근거 / 붙임** 셋뿐이다(+ 붙임 표 구성 옵션 3개).

### 본문 모양
```
1. 관련: 2026학년도 과학과 교육과정 운영 계획      ← 근거를 적었을 때만
2. ○○에 필요한 물품을 아래와 같이 구매하고자 하오니 검토하여 주시기 바랍니다.

  가. 구매 목적: ○○
  나. 구매 물품: 화이트보드 마카(검정) 외 4개
  다. 소요 예산: 금 173,200원(금십칠만삼천이백원)

붙임  구매 물품 내역 1부.  끝.                      ← 붙임을 적었을 때만
```
- **구매 물품**: 3개 이하면 물품명을 모두 나열, **4개 이상이면 `○○ 외 N개`**(N = 전체−1, `ITEM_NAME_SUMMARY_THRESHOLD`). 이름이 빈 품목도 `(물품명 없음)` 으로 **세어 남긴다** — 조용히 빠지면 본문의 물품 수와 붙임 표 행 수가 어긋난다.
- **끝 표시 자리가 붙임 유무로 달라진다**(행정업무운영 편람): 붙임이 있으면 `붙임  ○○  끝.`, 없으면 **본문 마지막 글자 뒤에 두 칸 띄고 `끝.`**.
- 하위 항목 부호(가·나·다)는 실제 출력 항목 수를 따라가므로 항목을 더하거나 빼도 어긋나지 않는다.

### 순수 로직 단일 출처 = `utils/officialDocument.ts`
본문·붙임 TSV·금액 한글 표기. 미리보기·복사·다운로드·인쇄·AI 프롬프트가 **같은 정의**를 쓴다(화면마다 조립하면 "미리보기와 내려받은 파일이 다른" 상태가 생긴다).
- **금액은 한글 병기**: `금 452,300원(금사십오만이천삼백원)`. 만·억의 '일'은 남기고(`일만오천`) 십·백·천의 '일'은 생략한다(`십오`).
- **열 역할은 추정하되 못 찾으면 비운다**(`resolveColumnRoles`): 기본 양식은 컬럼 id 로 잡고 커스텀 페이지는 타입·이름으로 추정한다. 숫자 열이 없으면 단가를 만들어내지 않는다.
- **같은 물품 합치기는 물품명·규격·단가가 모두 같을 때만** — 단가가 다르면 사실상 다른 물건이라 합치면 합계가 틀어진다.

### AI 프롬프트 = `utils/officialDocumentPrompt.ts` (순수)
호출부 `officialDocumentAi.ts` 는 `aiChat()` → supabase 브라우저 클라이언트를 물고 있어 **Node 회귀가 import 하면 `localStorage is not defined` 로 죽는다.** 그래서 프롬프트 문구는 순수 모듈에 둔다.
- **완성된 값을 넘긴다**: "구매 물품"·"소요 예산"은 이미 만들어진 문구로 전달하고 "글자 그대로 쓰라"고 지시한다 — 모델이 물품 수를 다시 세거나 금액을 한글로 다시 옮기게 두면 그 자리에서 틀린다(예산 문서라 치명적).
- 품목 TSV 는 **맥락 참고용**으로만 주고 "본문에 옮겨 적지 마세요"를 시스템·사용자 프롬프트 양쪽에 못박는다.
- 두문·결문·제목 작성 금지, 하위 항목 셋으로 고정, 붙임 유무별 끝 표시, 지어내기(납품일·업체명·계약 방법·예산 과목) 금지, 마크다운 금지.
- 모델이 코드펜스로 감싸는 경우가 있어 `stripMarkdownFence` 가 마지막에 한 번 더 벗긴다.
- LLM 호출은 공용 `aiChat()` 경유(규약). temperature 0.2 고정.

### 내보내기
본문 복사 / **붙임 표 복사(TSV)** / .txt 저장(BOM 포함) / 인쇄(A4).
본문에 표가 없으므로 **붙임 표 복사가 붙임 문서의 원본**이다(한글·엑셀에 붙이면 표로 들어간다).
파일명·인쇄 창 제목은 폼이 아니라 **게시글 제목**에서 만든다(제목을 또 묻지 않는다).
미리보기를 직접 고치면 폼 변경이 덮어쓰지 않는다(되돌리기 버튼 제공).

## 체크박스 Shift 범위 선택 (2026-09-02)

품목별·신청건별·신청자별 표의 체크박스에서 **Shift+클릭 = 앵커부터 여기까지를 클릭한 항목의 새 상태로 통일**(켜기·끄기 양방향). 파일 탐색기·메일함과 같은 동작.

- 순수 로직 = **`src/lib/rangeSelection.ts`의 `toggleWithRange`**(기능 비의존 — 다른 목록에서도 그대로 쓴다).
- **앵커는 인덱스가 아니라 키**로 들고 있다. 정렬·필터·삭제로 목록이 흔들리면 인덱스는 엉뚱한 행을 가리킨다. 키가 지금 목록에 없으면 범위를 만들지 않고 **단일 토글로 떨어뜨린다**.
- **Shift+클릭은 앵커를 옮기지 않는다** — 앵커가 고정돼야 이어서 구간을 넓히거나 줄일 수 있다. 그냥 클릭만 앵커를 옮긴다.
- **`onCheckedChange` 가 아니라 `onClick` 을 쓴다** — Radix Checkbox 의 `onCheckedChange` 는 이벤트를 주지 않아 `shiftKey` 를 알 수 없다. 대신 `checked` 만 제어하고 `onClick(e)` 으로 판정한다.
- **범위 기준 순서는 "클릭이 일어난 표"의 순서다** — 쇼핑몰별 묶기에서는 표가 여러 개라 전체 순서를 쓰면 화면에 안 보이는 행까지 구간에 들어간다. 그래서 `FlatItemsTable` 이 자기 `orderedKeys` 를 넘긴다.
- 공문 다이얼로그의 '포함 품목' 목록에는 아직 적용하지 않았다(이미 고른 것만 담겨 목록이 짧다).

## 목록 필터·다중 선택 (2026-09-02)

### 검색 — 쉼표는 OR
`GPT, 클로드` = GPT **이거나** 클로드(전각 `，` 도 받는다, 빈 조각은 버린다). 발주 담당자가 여러 품목을 한 번에 훑는 게 실제 사용법이라 AND 보다 OR 이 맞다 — AND 는 한 셀에 두 단어가 다 있어야 해서 거의 0건이 된다.
검색어 해석은 `utils/itemSearch.ts` 의 `parseSearchTerms` 하나이고 **신청건 판정과 품목 판정이 같은 함수를 쓴다** — 한쪽만 다르게 읽으면 뷰를 바꿀 때 결과 개수가 설명 없이 달라진다.

### 열 머리글 정렬
품목 표와 신청 페이지 목록 모두 머리글 클릭으로 정렬한다. 순환 = **오름차순 → 내림차순 → 해제**(세 번째 클릭으로 원래 순서에 돌아오므로 리셋 버튼이 필요 없다). 순수 로직 = `src/lib/tableSort.ts`, 머리글 = `components/SortableHeader.tsx`.
- **빈 값은 방향과 무관하게 항상 뒤로** — 내림차순으로 바꿨더니 빈 칸이 위를 덮는 표는 쓸모가 없다.
- **숫자 열은 숫자로** 비교한다(문자열이면 `'9' > '10'`). 컬럼 `type === 'number'` 로 판정하고, 숫자 열에 글자가 섞이면 그것만 뒤로 민다.
- **안정 정렬이라 열 정렬과 기본 정렬이 겹쳐 쓰인다** — 값이 같은 행은 위쪽 '정렬' 드롭다운(최근 수정순 등)의 순서를 유지한다.
- 정렬 중이 아닐 때도 **아이콘 자리를 비워 두지 않는다**(흐린 `ChevronsUpDown`) — 아이콘이 나타났다 사라지면 머리글 폭이 흔들려 표가 미세하게 움직인다.
- **한국어 대조 순서는 `숫자 < 한글 < 라틴`** 이다(ko CLDR). 알파벳 순을 기대하고 회귀 기대값을 '고치면' 오히려 틀린다.
- 정렬은 **`flatItems` 단계에서** 건다 — 표 안에서 걸면 CSV·공문·전체 선택이 화면과 다른 순서를 쓴다.
- 신청 페이지 목록은 제목·작성자·신청 기간·신청 현황이 정렬 대상(대상은 값이 2종뿐이라 제외).
- 회귀 `npx tsx scripts/purchase-requests-test/run-table-sort.mts`(30건).

### 필터 단위는 보고 있는 뷰를 따른다
- **신청건별·신청자별 뷰**: 검색·상태 필터가 **신청건 단위**(한 행만 맞아도 그 신청이 통과) — 여기서는 그게 맞다.
- **품목별 뷰**: 검색·상태 필터를 **행마다 한 번 더** 건다(`utils/itemSearch.ts` 의 `matchesItemQuery`, `getItemStatus`).
  - **이걸 안 하면 `"GPT"` 를 검색했는데 GPT 를 신청한 사람의 다른 품목까지 나온다**(사용자 보고). 신청건 필터를 그대로 펼치면 형제 행이 딸려 온다.
  - 다만 **신청자 이름이 맞으면 그 사람의 품목을 모두 남긴다** — 신청자는 모든 행이 공유하는 속성이라 "이 선생님 것 보기"가 자연스러운 해석이다.
  - 상태 분포 칩도 품목 단위로 센다 — 신청건 기준이면 "검토중 신청 안의 승인된 품목"이 사라진다.
- **요약(품목 수·합계 금액)과 CSV 내보내기는 `flatItems` 하나를 본다** — 화면과 다른 모집단을 더하거나 내보내면 그게 더 큰 사고다.
- 회귀 `npx tsx scripts/purchase-requests-test/run-item-search.mts`(19건).

### 다중 선택 액션 바는 화면 아래에 떠 있다 (버튼만)
체크박스를 누르는 순간 바가 생기면서 **표 전체가 아래로 밀려** 연속 체크가 어긋났다(사용자 보고). `SelectionActionBar` 가 `position: fixed` 로 띄워 레이아웃이 아예 움직이지 않는다.
- 바 높이는 줄바꿈에 따라 달라져 **"자리를 미리 비워 두는" 방식으로는 정확히 막을 수 없다** — 흐름에서 빼는 것이 유일한 확실한 해법이다.
- 모바일 하단 네비(`--mobile-nav-height`, fixed z-40) **위**에 올려 겹치지 않게 한다.
- 바깥 래퍼는 `pointer-events-none` — 바가 없는 자리의 클릭을 가로채지 않는다.
- 선택이 있을 때만 `CardContent` 에 아래쪽 여백을 준다. **내용 뒤에 붙는 여백이라 위쪽 행은 움직이지 않는다**(마지막 행이 바에 가리는 것만 막는다).
- **바에는 버튼만 둔다** — 상태 select 와 사유 입력은 `BulkStatusDialog` 모달로 옮겼다. 떠 있는 바에 입력 요소까지 얹으니 좁은 화면에서 줄바꿈으로 화면을 크게 가렸고, 사유가 한 줄 input 이라 긴 문장을 쓰기도 나빴다.
- 모달은 열 때마다 상태·사유를 초기화한다 — 직전 일괄 처리의 사유가 남아 엉뚱한 품목에 붙는 것을 막는다.

## 매니저의 물품명 수정 (2026-09-02)

작성자·공동 작업자가 신청된 물품명을 고친다. 발주 직전 표기 통일("화이트보드마카" · "화이트 보드마카" · "보드마카(검정)" 이 한 발주서에 섞여 들어온다)이 매니저 작업의 대부분이라, 한 건씩 고치는 길과 골라서 한 번에 바꾸는 길을 둘 다 뒀다.

**공통 규칙**
- **마이그레이션 없음** — RLS `update_own_or_manager` 가 이미 매니저 UPDATE 를 허용하고, `purchase_request_history` 트리거가 감사 추적을 남긴다.
- **RLS 차단은 오류가 아니라 0행**이라 `.select('id')` 반환 행으로 실제 반영을 확인한다.
- **저장 직전 서버에서 items 를 다시 읽어** 대상 행만 갈아끼운다 — 화면 캐시로 read-modify-write 하면 그 사이 신청자가 추가한 행이 사라진다.

### 한 건씩 — 표에서 인라인 (`ItemNameCell`)
- 진입은 **연필 버튼만**(셀 클릭은 이미 '상세 열기'라 충돌). 터치 기기에는 hover 가 없어 `[@media(hover:none)]` 에서 연필을 상시 노출한다.
- 상세 모달은 행 **스냅샷이 아니라 참조**(`{reqId, rowId}`)를 들고 쿼리에서 다시 찾는다 — 스냅샷이면 모달 안에서 이름을 고쳐도 옛 값이 계속 보인다.

### 여러 개 한 번에 — 일괄 통일 (`BulkItemNameDialog`)
품목별 뷰에서 체크한 뒤 **[물품명 일괄 변경]**. 순수 로직 = `utils/itemNameBulk.ts`.

- **바꾸기 전에 무엇이 무엇으로 바뀌는지 먼저 보여준다** — 현재 물품명 분포(건수 포함)와 각 항목이 `변경`인지 `그대로`인지를 표시한다. UI 에 되돌리기가 없는 조작이라(이력엔 남지만 복원 버튼은 없다) 눈으로 확인시키는 편이 안전하다.
- **기본값 = 가장 많이 쓰인 표기**(동점이면 먼저 나온 것). 단 **빈 이름만 있으면 제안하지 않는다** — `(물품명 없음)` 을 그대로 저장하면 사람이 적은 것처럼 보이는 가짜 물품명이 남는다.
- **신청 하나당 한 번만 읽고 쓴다**: 선택 품목을 `requestId` 로 묶어 `rowIds` 배열로 넘긴다(`useUpdatePurchaseRequestItemCell` 을 배열 입력으로 일반화). 행마다 호출하면 같은 신청의 items 를 연속 read-modify-write 하게 되어 앞 결과를 덮어쓸 여지가 생긴다.
- 적용 후 **선택은 유지한다** — 방금 통일한 품목을 이어서 공문에 담거나 상태를 바꾸는 흐름이 자연스럽다.
- `isAlreadyUnified([])` 는 **false** — `every` 의 공허참에 기대면 "이미 통일됨"이라는 잘못된 사유가 화면에 뜬다(대상이 없는 것과 이미 같은 것은 다른 상태다).
- 물품명 열을 못 찾은 커스텀 페이지에서는 버튼 자체를 내지 않는다.

## 새 신청 알림 (2026-09-03)

신청이 들어와도 담당자가 게시판을 열어 보기 전에는 알 수 없었다. 이제 **신청이 등록되면
그 페이지의 담당자(작성자 + 공동 작업자) 전원에게 알림**이 간다.

### 보내는 쪽은 DB 트리거다

`purchase_requests` **AFTER INSERT** → `notify_purchase_request_submitted()`
(SECURITY DEFINER, 마이그레이션 `20260903081803_purchase_request_submitted_notification.sql`).

클라이언트에서 보내지 않은 이유 두 가지:

1. **신청자는 담당자 명단을 알 수 없다.** 수신자를 화면에서 정하려면
   `purchase_request_collaborators` 를 신청자 전원(학생 포함)에게 열어야 한다.
   트리거는 명단을 서버 안에 두고 알림만 내보낸다.
2. **알림이 신청과 같은 트랜잭션에서 만들어진다.** 저장 직후 탭이 닫히거나 네트워크가
   끊겨도 "신청은 됐는데 아무도 모르는" 상태가 생기지 않는다.

`notification_events` 의 INSERT 정책은 `with_check true` 라 클라이언트로도 넣을 수는 있다 —
못 해서가 아니라 위 두 가지 때문에 안 한 것이다. 일정 알림(`create_meeting_notification`)과 같은 패턴.

### 규칙

- **INSERT 에만** 건다. 신청 수정(`items` UPDATE)은 새 신청이 아니다 — 저장 버튼을 누를 때마다
  알림이 쌓이면 알림함이 곧 무시된다.
- **신청자 본인은 제외**한다(매니저가 자기 페이지에 직접 신청하는 경우).
- **품목 0건이면 보내지 않는다.** 화면이 이미 최소 1건을 강제하지만(`validateRows`), 알릴 내용이
  없는 알림을 만들지 않는 편이 맞다.
- **실패해도 신청은 커밋된다.** 트리거 본문이 하위 트랜잭션(`begin … exception when others`)이라
  알림 INSERT 만 롤백되고 `raise warning` 으로 끝난다.

### 문구·딥링크

| 항목 | 값 |
|---|---|
| `type` | `purchase_request_submitted` |
| 제목 | `새 구매 신청` |
| 내용 | `{신청자}님 · {보드마카 외 2건}` + 줄바꿈 + `📋 {게시판 제목}` |
| `priority` | `medium` |

품목 요약은 물품명 열(기본 `default-name`, 없으면 첫 text 열)의 첫 값 + `외 N건`이다.
클라이언트 `summarizeItemNames()` 와 같은 모양이지만 **표시용 메아리**일 뿐 판정 경로가 아니다
(어긋나도 문구가 덜 친절해질 뿐 승인·상태에는 영향이 없다).

**`related_meeting_id` 는 meeting FK 라 쓸 수 없다** — 그래서 딥링크 키를 `meta` 에 담는다.
알림 카드의 **[신청 확인]** 버튼이 `meta.purchase_page_id` 로 `/purchase-requests/<id>` 를 연다
(`NotificationItem.tsx`, 누르면 읽음 처리도 함께). 아이콘·색은 `notificationUtils.tsx`
(장바구니 아이콘 + `warning` = 행동 필요), 감사 목록은 Admin ▸ 알림 관리

## 품의 정리 (2026-10-12)

종전 흐름은 **신청 → (체크박스로 고르기) → 공문**뿐이었다. 그런데 운영 신청의 대부분은
「물품명 + 용도」 두 열뿐이라(최근 세 페이지 모두 단가·수량·주소 열이 없다) `resolveColumnRoles`
가 단가를 못 찾아 **공문의 소요 예산이 비었고**, 매니저가 금액·구독 플랜·구매처를 시스템 밖에서
정리했다. 그리고 실제 신청은 `ChatGPT` 15건, `클로바노트 2달 * 4명` 처럼 와서 **신청 품목과
품의 품목이 1:1 이 아니다**. 그래서 둘 사이에 매니저 단계를 넣었다.

```
신청 품목 ──▲ 올리기──▶ 품의 차수 표(엑셀식) ──▶ 차수 공문
  (N)     같은 물품끼리 1줄    └ 차수 상태: 작성 중 → 품의 완료 → 구매 완료
```

### 사용자 결정 (2026-10-12)
1. **관리 단위 = 품의 품목으로 묶기** — 신청 품목마다 칸을 붙이는 안(meta 저장)은 기각. 묶음을
   공문을 만들 때마다 '같은 물품 합치기'로 다시 계산해야 하고, 「chat GPT」·「ChatGPT」처럼
   표기가 다른 신청을 영영 하나로 셀 수 없다.
2. **차수로 나눔** — 한 페이지에서 1차·2차 품의를 따로 올린다. 차수 상태가 신청 품목 상태로 이어진다.
3. **신청자에게는 진행 단계만** — 차수 이름·단계·확정 품명. 단가·구매처·예산 과목은 매니저만.
4. ~~고정 항목 + 메모~~ → **같은 날 뒤집혔다**(아래 후속).

### 같은 날 후속 — 대화상자를 없애고 표에서 (사용자 요구)
첫 구현은 고른 품목을 [품의에 담기] 대화상자(`OrderLineDialog`)로 담고 값도 거기서 적게 했는데
"매우 불편하다"는 피드백을 받았다. 바꾼 것:
- **▲ 올리기** — 고르고 ▲ 를 누르면 대화상자 없이 바로 차수에 들어간다. **같은 물품끼리 한 줄로
  묶이고**(`normalizeItemName` — 대소문자·띄어쓰기·문장부호 무시), 차수에 같은 이름의 줄이 이미
  있으면 새 줄 대신 거기에 붙는다(수량 +). 계획은 순수 함수 `planAddToBatch`, 쓰기는
  `useAddItemsToBatch`, 화면 공용 훅 = `components/order/useAddToBatch.ts`.
- **▼ 내리기** — 표에서 고른 품목을 지운다. 연결된 신청 품목은 '아직 안 담긴' 쪽으로 돌아간다.
- **합치기** — 표에서 고른 품목들을 맨 위 품목 하나로(`planMergeLines`). 이름이 달라 자동으로 안
  묶인 것(「GPT」 + 「ChatGPT Plus」)을 사람이 묶는 길이다. 연결을 **먼저** 옮기고 나머지를 지운다
  (반대 순서면 cascade 로 연결이 사라진다).
- **엑셀식 표** (`components/order/OrderSheet.tsx`) — 셀이 늘 입력칸이고 칸을 떠날 때 바뀌었으면 저장.
  Enter·↓ 아래 · ↑ 위 · Esc 되돌리기 · Tab 오른쪽 · **엑셀에서 여러 칸을 복사해 붙이면 그 칸부터
  채운다**(있는 행까지만, 해석 못 한 칸·넘친 줄은 경고). 맨 아래 빈 줄에 품명을 적으면 새 품목.
  셀 저장은 **낙관적 갱신**(먼저 화면을 바꾸고 실패하면 되돌림) — 왕복을 기다리면 칸을 옮길 때마다
  값이 깜빡인다. 한글 조합 중 Enter 는 글자 확정이라 이동하지 않는다(`isComposing`).
- **열은 사용자가 정한다** — 열 머리 메뉴로 이름 바꾸기·왼쪽/오른쪽·빼기, 맨 끝 [+]로 새 열(글자·숫자·
  링크) 또는 준비된 열 넣기. 정의는 차수마다 `purchase_order_batches.columns`(빈 배열 = 기본 열),
  사용자 열의 값은 `purchase_order_lines.extra`. 새 차수는 직전 차수의 열 정의를 이어받는다.
  - **기본 열 = 품명 · 단가 · 수량 · 비고**(+ 계산 열 금액). 처음엔 10칸이었는데 "너무 많다 → 공문
    필수만 → 규격도 제외 → 비고 추가"로 정해졌다. 규격·이용 기간·구매처·링크·결제 방법·예산 과목은
    [+]의 «준비된 열»(실제 DB 칸이라 공문이 읽는다).
  - **품명·단가·수량은 뺄 수 없다**(잠금) — 금액과 공문의 '구매 물품'·'소요 예산'이 이 셋을 읽는다.
    저장된 정의에서 빠져 있어도 `resolveOrderColumns` 가 되살린다. 기본 칸의 종류(숫자/글자)는 DB 가
    정한다 — 단가를 글자 열로 바꿀 수 없다.
  - 열을 빼도 **값은 지우지 않는다**(기본 칸은 DB 컬럼, 사용자 열은 extra 에 남는다).

### 화면
- **상세 페이지 탭** — 매니저는 늘 탭을 본다: `신청 관리 | 품의 정리 | (내 신청)`. 딥링크 `?tab=order`. (2026-10-13 이름이 `① 신청 검토 · ② 품의·구매` 단계 탭으로 바뀌었다 — 위 «화면 개편»)
  (종전엔 매니저이면서 신청 대상일 때만 탭이 있었다.)
- **품의 정리 탭** — 요약(신청 품목 · 담긴 품목 · 아직 안 담긴 품목 · 차수) → 차수 칩 + [새 차수] →
  이름·진행 단계·[공문 만들기] → **차수 표** → **▲ 올리기 · ▼ 내리기 · 합치기** 줄 → **아직 안 담긴
  신청 품목**(행 클릭·Shift 범위 선택). 불가 처리된 품목은 기본으로 숨긴다. 차수가 없을 때 ▲ 를 누르면
  1차 품의가 만들어지며 올라간다.
- **신청 관리 → [▲ 품의 차수에 올리기 ▾]** — 세 뷰의 선택 액션 바. 차수를 고르면 바로 올라간다(대화상자
  없음). 선택 단위는 공문과 같다. 품목별 뷰의 상태 칸 아래에 담긴 품의가 차수 상태 색으로 붙는다 —
  **빈 칸이 곧 '아직 안 담김'**.
- **표의 «신청» 칸** = 연결 수 칩, 누르면 연결된 신청 품목 목록과 하나씩 빼기(수량도 그만큼 −).
- **신청자 화면** — 품목 표의 `처리 상태` 칸 아래에 `1차 품의 품의 완료 · ChatGPT Plus`.
- 이미 품의 완료·구매 완료된 차수에 올리면 확인창이 "신청 품목 상태는 자동으로 바뀌지 않는다"고 묻는다.

### 초안 규칙 (`draftLineFromSelection`)
▲ 로 새 줄이 생길 때 채우는 값. **사람이 표에서 고치는 출발점**이다.
- 품명 = 가장 많이 쓰인 표기(물품명 일괄 변경과 같은 함수). 빈 이름은 `(물품명 없음)`(품명 NOT NULL).
- 규격·단가 = **모두 같을 때만**. 다르면 비운다 — 평균을 내면 아무도 적지 않은 단가가 생긴다.
- 수량 = 품목마다 수량 열 값(없거나 비면 1)의 합 — 기존 줄에 붙이거나 빼거나 옮길 때의 수량 증감
  (`itemQty`)과 **같은 규칙**이다. 기존 줄의 수량이 비어 있으면 증감하지 않는다(사람이 아직 안 정한 값).

### 차수 상태 ↔ 신청 품목 상태
서버 `set_purchase_order_batch_status` 가 정한다(화면 문구 `batchStatusEffect` 는 그 거울).
- 품의 완료(순방향) → 연결된 품목 중 **제출됨·검토중**만 승인.
- 구매 완료 → 연결된 품목 중 **불가·완료가 아닌 것** 모두 완료.
- **되돌리기는 품목 상태를 건드리지 않는다** — 매니저가 품목마다 따로 정한 상태를 차수 하나의
  되돌리기로 덮어쓰지 않기 위해서다. 확인창이 그렇게 말한다.
- 품목 상태 쓰기는 기존 `set_purchase_request_item_status` 하나로 한다 — 파생 규칙(TS·SQL 짝)을
  세 번째 자리에 복제하지 않는다. 품목마다 적혀 있던 사유를 지우지 않도록 (신청, 기존 사유) 묶음별로 부른다.
- 이미 진행된 차수에 품목을 올려도 상태는 자동으로 바뀌지 않는다(확인창이 묻는다).

### 공문
`OfficialDocumentDialog` 에 `orderItems`(+`orderLabel`)를 주면 품의 품목을 **그대로** 공문 품목으로
쓴다(`linesToDocumentItems`). 규격 칸 = 규격 · 이용 기간, 구매처 칸 = 구매처 (링크), 신청자 = 연결된
신청자(중복 제거). **'같은 물품 합치기'는 품의 경로에서 숨긴다** — 품의 품목이 이미 사람이 묶은
단위라 다시 합치면 품의 정리 표와 공문이 어긋난다. 합치기 로직은 `mergeDocumentItems` 로 분리해
'포함 품목'에서 뺀 뒤 합치는 순서를 두 경로가 공유한다. 종전 경로(신청 관리에서 바로 공문)는 그대로다.
- **붙임 표 열**(`buildItemsTsv` 의 `layout`) — 품의 공문은 표의 기본 열을 따라 **비고 열을 늘 넣고,
  규격 열은 규격을 적은 품목이 있을 때만** 넣는다(`orderTsvLayout`). 종전 경로는 기본값(규격 있음·
  비고 없음) 그대로. 비고의 탭·줄바꿈은 공백으로 바꾼다 — 그대로 두면 한글·엑셀에 붙일 때 칸이 밀린다.
- 사용자가 만든 열(extra)은 공문에 들어가지 않는다 — 품의 관리용 칸이다.

### 조용히 틀리는 자리
- **단가나 수량이 빈 품목은 합계에서 빠진다** — 0원으로 세지 않는다(`sumLines.missing`). 표 아래에
  "N개는 합계에 들어가지 않았습니다. 공문의 소요 예산도 그만큼 빠집니다"를 띄운다.
- **고아 연결** — `row_id` 는 JSONB 안의 값이라 FK 가 없다. 신청자가 행을 지우면 연결이 남는다.
  화면은 `liveLinks` 로, RPC 는 `items` 존재 검사로 거른다. 연결 수를 셀 때 원본 `links` 를 쓰지 말 것.
- **upsert 는 옮기기다** — `(request_id,row_id)` 유니크라 이미 다른 품목에 있는 신청 품목을 올리면
  조용히 이쪽으로 옮겨진다(원래 줄 수량 −). 토스트가 "다른 품목에서 N개 옮김"으로 알린다.
- **사용자 열 저장은 extra 통째 쓰기** — 셀 하나를 고쳐도 `extra` 전체를 보낸다. 그래서 패치는 반드시
  **지금 행의 extra 위에** 만든다(`buildLinePatch`). 빈 객체에 쓰면 같은 행의 다른 사용자 열 값이
  조용히 지워진다. 두 매니저가 같은 행의 서로 다른 사용자 열을 동시에 고치면 나중 저장이 이긴다(드묾).
