## 목록 조회 비용 — 재보고 고쳤다 (2026-09-11)

사용자 지적: *"데이터를 불러오는 과정이 생각보다 김. 앞으로 데이터가 더 쌓인다고 생각한다면
불러오는 과정을 개선할 필요성이 있어 보임."* 오늘 탐구 활동 1,439건을 적재해 `activity` 가
150 → **1,593행(10배)** 이 된 직후라 시점이 맞았다.

**먼저 어디가 느린지 갈랐다** — 활동 500건 + 조인 3종 = **390ms**, 기본 표만 = **18.9ms**.
95%가 조인 표에서 났고 원인은 하나도 데이터 크기가 아니었다.

### ① RLS 가 읽기마다 쓰기 권한을 검사하고 있었다 (390ms → 9.6ms)

`activity_host_link`·`activity_participation`·`activity_teacher` 의 `*_write` 정책이
**`cmd = ALL`** 이었다. `ALL` 은 SELECT 에도 걸리므로, 읽을 때마다 행마다
`can_add_activity_participant`(실측 **호출당 1.15ms** — 안에서 `can_manage_activity` 가
EXISTS 4개를 돈다)를 불렀다. PERMISSIVE 정책 둘은 OR 로 합쳐지는데 계획은 그 비싼 쪽을 먼저 놓았다.

고친 방법은 **권한을 그대로 두고 순서만 바꾸는 것**이다 — 쓰기 정책을 쓰기 명령으로 좁히고,
그것이 읽기에 주던 몫을 `*_select` 의 **맨 뒤 OR 항**에 **같은 함수·같은 인자로** 옮겼다.
역할 검사는 `(select …)` 로 감싸 **InitPlan**(한 번만 평가)이 되게 했고, 교사면 참이라
나머지가 행마다 건너뛰어진다.

**검증** = 적용 전후 교사·학생 시점의 행 수와 **md5 지문** 대조. 일곱 조합 전부 동일
(activity 1,593 · host_link 522 · teacher 4 · participation 교사 751 / 학생 9).

### ② 콜드 로드마다 목록을 두 번 받고 있었다

`useActivities` 의 queryKey 에 `lineage.length` 가 들어 있었다. 계보가 도착하면 키가 바뀌어
**같은 2 MB 를 한 번 더** 받는다. 계보 장식은 순수 클라이언트 변환이라 조회 키에 있을 이유가
없다 → `fetchActivitiesRaw` + 훅의 `select`(`decorateActivities`) 로 갈랐다.

### ③ 페이지 크기가 상한의 절반이었다

`fetchAllPages` 가 500씩 읽었는데 PostgREST 상한은 1000이다. 1,593행 기준 왕복 4회 → **2회**.
왕복 하나가 곧 지연이라 데이터가 늘수록 이 차이가 그대로 커진다.

### ④ 목록이 본문 전문을 받고 있었다 (전송 −46.2%)

**기본 연도 필터는 '전체'로 둔다**(2026-09-11 사용자 결정 — *"기본 연도는 전체로 둬야 기능의
목적을 달성함"*). 연도를 가로질러 보는 것이 이 기능의 목적이므로 **행 수를 줄이는 축이 없고,
남는 지렛대는 행당 크기뿐**이다.

목록 행은 본문을 `truncate` 로 한 줄만 그리는데 `select *` 라 전문을 받았다. 열별로 재니
`content` 21.3% · `meta` 15.3% 였고, **압축 후로 다시 재자 절감이 더 컸다**:

| 조회 | brotli (1,000행) |
|---|---|
| `select *` | 217 KB |
| `meta` 만 제외 | 196 KB (−12.4%) |
| 발췌 80자 + `meta` 제외 | **117 KB (−46.2%)** |

**원본 바이트 비중으로 추정하면 과소평가한다** — 그 두 열은 반복이 적어 압축이 덜 되기 때문이다.
(내가 처음 적은 "2 MB 중 1 MB"는 `pg_column_size` 기준이라 전송량과 달랐다. JSON 기준은 20.5% 다.)

**⚠️ 발췌를 `content` 자리에 담으면 안 된다** — 편집 화면이 목록 행을 그대로 폼에 싣고 있어,
그러면 **잘린 본문이 저장되어 원본을 덮는다**(1,593행 규모의 조용한 손실). 그래서
①발췌는 `content_excerpt`(PostgREST 계산 필드)라는 다른 이름으로 주고
②목록 타입 `ActivityListItem` 에서 **`content` 를 아예 뺐다**. 전문이 필요한 자리(상세·편집)는
`useActivity(id)` 로 따로 받고, 그러지 않으면 **컴파일이 막는다** — 실제로 타입 검사가
그 두 자리를 정확히 집어냈다.

**대가는 열 목록을 손으로 유지하는 것**이다. 빠뜨리면 오류가 아니라 그 값이 목록에서 조용히
`undefined` 가 된다 → 회귀 `npx tsx scripts/activity-select-test/run.mts` 가 DB 열과 양방향 대조한다
(열 하나를 빼서 실제로 잡히는 것까지 확인했다).

### ⑤ 학생에게 참여자 수를 세지 않는다 (214ms → 9.4ms)

사용자 결정: *"불필요해 보임."* — 성능 이전에 **틀린 값**이었다. RLS 상 학생에게는
자기 참여 행만 보이므로(실측 751행 중 9행) 30명짜리 활동도 **"1명"** 으로 나온다.

그래서 학생 시점에는 조회에서 `activity_participation ( count )` 조인을 **아예 뺀다**.
빼면 학생 시점 500행이 **214ms → 9.4ms** 가 된다 — 그 집계가 학생 조회 시간의 대부분이었다.

**"0명"과 "묻지 않았다"를 구분한다** — `participant_count` 를 `number | null` 로 두고
`null` 이면 화면이 칸 자체를 그리지 않는다. 0으로 채우면 "참여자가 없는 활동"으로 읽힌다.

**목록과 상세가 같은 기준을 써야 한다**(`useActivities`·`useActivity` 둘 다 `clubOnly` 로 판정) —
한쪽만 고치면 목록엔 안 나오는데 상세엔 틀린 수가 뜬다.

## 전체 활동 목록의 실제 주최 보정 (2026-09-10, DB 반영 완료)

사용자 의도는 탐구 상세에서 새 활동을 만드는 폼이 아니라 **전체 목록에 이미 적재된 활동의 주최 동아리**를 채우는 것이다. 원본 연결 `activity.meta.inquiry_type_id → inquiry_activity_type_member → inquiry_activity.club_name`으로 확인한 이름을 `activity_host_link`에 저장했다.

- 대상: `source='import' AND area='club'` 56건. 모두 주최가 없었으며 모두 원본 동아리명을 확인했다.
- 결과: 활동 56건에 주최 연결 95건. 이름 38종 중 기존 주최 22종을 재사용하고, 없는 원본 이름 16종을 추가했다.
- 원본의 `1` 접미사·과거 이름·쉼표/가운뎃점·철자 차이를 임의로 합치지 않았다. 신규 주최에는 `meta.source='inquiry_activity_club_backfill'`, 원본 이름, 현재 운영 여부 미확인 표시를 남겼다. 담당교사·부원·현재 운영 사실을 추정해 넣지 않았다. `active`는 주최 선택 목록에서 사용 가능하다는 뜻으로 사용한다.
- 단일 동아리는 `primary`, 여러 동아리의 원본이 묶인 활동은 모두 `co`로 연결했다. 집계된 원본만으로 공식 대표 주최나 공동 행사 개최 사실을 확정하지 않는다. 목록의 첫 표시 항목은 기존 UI 정렬을 따른다.
- 기존 주최 연결이 있는 활동과 수동 기록·자율/진로 활동은 수정하지 않는다. 이름 추측·제목 유사도 매칭은 하지 않는다.
- SQL: `scripts/inquiry-graphrag/backfill-activity-club-hosts.sql`. 트랜잭션 내 시험 실행 후 롤백하여 확인하고 실제 반영했다. 이미 주최가 있는 활동을 건너뛰므로 동일 데이터에 재실행해도 늘지 않는다. 스키마 변경은 없다.
- 실제 DB 검증: 주최 있는 동아리 활동 **56/56**, 연결 **95**, 원본 대비 누락 **0**, 근거 없는 연결 **0**, 범위 밖 연결 **0**. 기존 전체 목록 조회가 주최를 조인하므로 앱 데이터 재조회 시 표시된다.

## 탐구 원본 동아리 → 주최 연결 (2026-09-10)

탐구 상세의 **이 탐구를 활동 기록으로**를 누르면 `inquiry_activity.club_name`을 주최 동아리 후보로 전달한다. 활동 폼에서는 앞뒤 공백을 제거한 이름이 정확히 일치하는 활성 `club` 주최가 하나일 때 자동 선택한다. 학생은 본인이 선택할 수 있는 소속 동아리 안에서만 매칭한다.

목록이 늦게 도착해도 매칭하며, 직접 선택·해제하거나 영역을 바꾼 뒤에는 자동 선택으로 덮어쓰지 않는다. 이름이 없거나 비슷하기만 한 경우, 비활성 동아리 또는 여러 후보가 있으면 자동 연결하지 않는다. 폼에서 원본 동아리명과 직접 선택 안내를 보여 준다.

동아리명을 `operatorName`에 넣지 않으므로 교내 동아리 활동이 외부 운영으로 분류되지 않는다. 저장은 기존 `hostIds` → `activity_host_link` 경로를 사용한다. 기존 데이터 일괄 수정, 동아리 자동 생성, 스키마 변경은 없다.

검증: 매칭·미매칭·모호한 이름·비활성/다른 종류 주최 제외·씨앗 변환 회귀 테스트 3건, 변경 파일 린트 통과.

**`activity.name`은 NOT NULL** — 이름 없는 활동은 검색·집계·계보 추적이 불가능하고 그것이 현행 생기부의 문제다(창체 3영역 5,862행 중 **1,751행(29.9%)이 본문 없이 `{"영역":…,"시간":…}` JSON만**, 생기부 동아리명 101종 중 `club_info` 일치 **8종(8%)**).

**예산·운영주체도 활동 단위** — 같은 동아리도 교육청 사업비로 탐방 가고 학교 예산으로 재료를 산다.

**소속 ≠ 참여**: `activity_host_member`(부원 명단)는 참여자 선택의 **기본값 씨앗**이고 실제 참여는 `activity_participation`에만 있다(`ParticipantPicker`가 한 클릭 상속 + 빠진 사람만 해제).

**화면(2026-08-27 개편)**: 헤더(`ActivitiesHeader`)는 **타이틀 없이** 검색·범주 칩·연도·주최·기록 버튼을 담는 글래스 카드(입시 정보 `IpsiHubHeader` 스타일). 본문은 **진로·분야 카테고리 보드** — 첫 화면은 둥근 정사각형 타일 그리드(제목 중앙·개수 우상단, 둘 다 26px, `gap-3`으로 상하좌우 간격 동일), 분야를 고르면 framer-motion `layout`(FLIP)으로 **타일이 좌측 레일로 이동**하고 우측에 게시글 스타일 목록이 열린다. 타일을 **언마운트하지 않고 컨테이너 클래스만 grid↔flex-col로 바꾸는 것이 핵심** — `layoutId`로 두 트리를 갈아끼우면 교차 매칭이 어긋날 때 조용히 점프한다. 카테고리 색은 **이름 해시(FNV-1a)로 결정론적 배정** — 개수 정렬 기반으로 칠하면 활동 하나가 추가될 때 색이 통째로 뒤바뀐다. 팔레트는 Tailwind 램프가 아니라 **직접 고른 hex 10색**(인라인 스타일, 글자/배경 대비 5.5:1 이상 직접 검증).

**영역은 화면에서 3그룹**(자율·진로 / 동아리 / 봉사) — 생기부의 자율·진로가 비슷한 내용이라는 사용자 판단이며 **DB `area` CHECK는 4값 유지**(기존 `career` 행 보존 + NEIS는 여전히 별도 기재). 편집 시 그룹이 같으면 원래 area를 보존해 '진로활동'이 저장만 눌러도 '자율'로 바뀌지 않는다. 주최(동아리) 선택은 **영역이 동아리일 때만** 노출하고, 벗어나면 값을 비운다. 폼에서 **목적·산출물·인정 시수는 제거**(사용자 결정)했고 **진로·분야가 본문 필수 입력**으로 올라왔다(쉼표 다중값 → 카테고리 축). 페이지 컨테이너는 `Layout`의 `<main>`이 이미 `p-2 sm:p-3 md:p-4 lg:p-6`을 주므로 **패딩·max-width를 또 주지 않는다**(연수 이수증과 동일). 주 액션 버튼은 파랑(`bg-blue-600`) — 앱 전역 규약.

**기각 — 책장 세 쪽을 LLM 으로 채우는 안 (2026-09-15)**: 아카이브 `activity` 1,593건 중
`purpose`(활동의 시작)·`outcome`(발견과 성과)이 **전부 0건**이라 아카데미 도서관의 책이 모두

생성하는 안을 설계까지 했으나 **사용자 판단으로 기각**했다 — 이유가 방법이 아니라 **재료**에 있다.
생기부 원문 자체가 이미 압축된 서술이고 `did` 는 그것을 한 번 더 줄인 요약이다. 그걸 셋으로
나누면 정보량은 늘지 않고 **밀도만 떨어진다**(한 쪽이 세 조각으로 얇아질 뿐이다).
- 함께 측정해 둔 것: `did` 의 생기부 원문 **문자 5-gram 겹침 = 0.576 · 34.0%가 0.7 이상**
  (전수 1,415건, 2026-09-11 기록 0.594·38.6%와 일치). `did` 를 화면에 내보내지 않기로 한
  결정의 근거 수치이고, 재료가 원문에 얼마나 붙어 있는지도 같이 말해 준다.
- **책이 얇은 것을 LLM 으로 풀 수 없다.** 더 두꺼운 책이 필요하면 재료가 달라져야 하고,
  그 재료는 이미 설계돼 있다 — 학생이 직접 쓰는 `activity_post` 성찰(공개범위 `school`)이
  루프 B 아카이브의 본래 재료다(`docs/creative-activities-plan.md` §루프 B).
- 생기부에서 온 개별 탐구를 아카이브에 넣는 것 자체는 유지한다(`scripts/inquiry-graphrag/import-individual-deep-activities.sql`).
  그건 요약을 늘리는 것이 아니라 **없던 활동을 목록에 올리는** 일이다.

**삭제는 담당교사에게 열지 않는다** — 학생 성찰을 담당교사가 지울 수 있으면 '학생이 저자'라는 약속이 깨진다(작성자∨창체담당자만).
