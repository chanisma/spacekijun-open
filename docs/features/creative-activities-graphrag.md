## 0. 한 줄 요약

**학생 866명의 생활기록부에서 이미 분절된 탐구 활동 34,254건을 "학교의 탐구 자산"으로 묶어,
개념·과목·방법·진로·심화 관계로 이어진 그래프와 그 위의 주제군(community) 요약을 만들고,
창체 화면의 탐색이 "키워드 검색"이 아니라 "이 탐구 다음엔 무엇을 할 수 있는가 · 이 분야에서
우리 학교 학생들은 어디까지 가 봤는가"에 답하게 한다.**

추출 LLM은 **Sonnet(서브에이전트)**이고, 판정과 등급은 **코드가 유도**한다(모델은 근거 문장 번호만 고른다).

## 1. 왜 GraphRAG인가 — 지금 화면이 못 하는 것

창체 화면(`/activities`)의 탐색은 진로·분야 타일 + 텍스트 검색이다. 그리고 `activity` 표는 **4건**,
성찰·참여 0건이다. 탐색할 것이 없다.

그런데 생기부에는 이미 탐구 활동이 있다. 문제는 그것이 **문장 덩어리** 안에 갇혀 있고, 학생 한 명
안에서만 이어져 있다는 것이다(연구 §1: 기존 KG는 학생 개인 그래프이고 학생 간 연결은 0).

GraphRAG가 답하게 하려는 질문은 세 층이다.

| 층 | 질문 예 | 벡터 검색만으로 안 되는 이유 |
|---|---|---|
| **국소(local)** | "알긴산으로 약물 방출 실험을 해 보고 싶은데 선배들이 한 비슷한 탐구가 있나" | 비슷한 활동은 찾지만, 그 활동이 **무엇으로 이어졌는지**(심화 사슬)·**어떤 개념을 함께 다뤘는지**는 이웃을 따라가야 나온다 |
| **경로(path)** | "이 탐구 다음 단계로 무엇을 할 수 있나" | 같은 학생의 `DEEPENED_FROM` 사슬 + 같은 주제군에서 **더 높은 사고 수준**의 활동 — 그래프 질의다 |
| **전역(global)** | "우리 학교 화학 탐구는 주로 무엇을 하고, 어디가 비어 있나" | 문서 몇 개를 뽑아 답할 수 없다. 주제군 요약을 **전부 훑어 종합**해야 한다 |

세 번째가 GraphRAG 고유의 것이다(Microsoft GraphRAG의 *global search* — 커뮤니티 요약 map-reduce).
첫째·둘째는 그래프 이웃 확장(*local search*)이다.

## 3. 좋은 탐구를 가르는 자 — 사용자 제공 지식의 구현

사용자가 준 두 표(사고 수준 5문항 · 근거 7항목)는 원래 평가문 작성용이지만, **"무엇을 근거로 쓸지 고를 때"**
쓰는 질문이라는 점에서 그대로 추출 스키마가 된다. 답을 옮겨 적는 것이 아니라 **근거 문장을 고르는** 일이다.

### 3-1. 모델이 하는 일과 코드가 하는 일

이 저장소의 추출 원칙(연구 §6·§12-4)을 그대로 따른다 — **모델은 관찰하고 코드가 판정한다.**

| 모델(Sonnet) | 코드 |
|---|---|
| 근거 7항목마다 **해당 문장 번호**를 고른다 | 번호가 그 활동 문장 안에 있는지 검증. 없으면 항목 폐기 |
| 사고 5문항마다 `weak / strong / none` + 근거 번호 | `strong`에 근거 번호가 없으면 `none`으로 강등 |
| 탐구 질문·방법 유형·산출물·분야를 적는다 | 폐쇄 어휘(enum) 밖 값은 버린다 |
| — | **수준(level)을 유도**한다. 모델에게 점수를 매기게 하지 않는다 |

모델에게 등급을 직접 묻지 않는 이유: 등급은 프롬프트 한 줄에 흔들리고 실행 간 편차가 크다(연구 §13 —
"판단이 개입할수록 편차가 커진다"). 문장 번호 선택은 관찰에 가까워 안정적이다(문장 귀속 자카드 0.96 vs
개념 명명 0.56). 등급은 관찰값에서 코드가 계산하므로 **기준을 바꿔도 재추출이 필요 없다.**

### 3-2. 스키마

```jsonc
{
  "activity_id": "act:<record_id>#<n>",
  "is_inquiry": true,                       // 탐구 대상이 있는가 (행사 참여·기능 수행은 false)
  "research_question": "…" | null,          // 원문에 문제·질문이 드러날 때만
  "evidence": {                             // 근거 7항목 — 있는 것만, 각각 문장 번호 필수
    "problem_recognition": { "sentence_ids": [1], "self_posed": true },
    "concept_understanding": { "sentence_ids": [2,3], "depth": "own_words" },   // mention|explain|own_words
    "inquiry_design":       { "sentence_ids": [3], "criterion_self_set": false },
    "data_analysis":        { "sentence_ids": [4], "comparison": true },
    "logical_interpretation": { "sentence_ids": [4,5], "chain_complete": true },
    "extension_career":     { "sentence_ids": [6], "grounded": true, "target": "복합 겔 방출 제어" },
    "reflection_improvement": { "sentence_ids": [], "limitation_named": false, "improvement_concrete": false }
  },
  "thinking": {                             // 사고 수준 5문항 — weak / strong / none
    "procedure": "adapted",                 // followed | adapted
    "result":    "cause_narrowed",          // reported | cause_narrowed
    "criteria":  "applied",                 // applied | self_set
    "facts":     "relations",               // single | relations
    "context":   "single",                  // single | transferred_grounded
    "sentence_ids": { "procedure": [3], "result": [4,5], "facts": [4] }   // strong 답에만 필수
  },
  "method_types": ["실험", "자료비교"],       // 폐쇄 어휘 (README 참조)
  "output_types": ["보고서"],
  "career_fields": ["약학", "화학"],          // 폐쇄 분류 30종, 최대 3
  "extension_hint": "복합 겔의 방출 제어 가능성으로 확장" | null
}
```

### 3-3. 수준 유도 (코드)

`strength` = 사고 5문항 중 근거가 검증된 `strong` 수(0~5) · `breadth` = 근거 7항목 중 검증된 항목 수(0~7).

| 수준 | 이름 | 조건 |
|---|---|---|
| 0 | 비탐구 | `is_inquiry=false` 또는 S0 개념 0개 |
| 1 | 수행·보고 | strength 0 ∧ breadth ≤ 2 |
| 2 | 이해·적용 | strength ≤ 1 (그 외) |
| 3 | 분석·해석 | strength 2~3 |
| 4 | 설계·확장 | strength ≥ 4, 또는 strength 3 ∧ (`inquiry_design.criterion_self_set` ∨ `extension_career.grounded`) |

이 표는 **재계산 가능한 파생값**이다. 파일럿에서 분포를 보고 문턱을 옮길 수 있고, 그래도 재추출은 없다.
사용자 표의 "뒤쪽일수록 강한 근거"가 곧 `strong` 쪽이다.

## 4. 그래프 스키마

### 4-1. 노드

| 타입 | 무엇 | 출처 | 수(예상) |
|---|---|---|---|
| **InquiryActivity** | 탐구 활동 1단위 | S0 활동 + §3 판정 | 28,337 |
| **Concept** | 정규화된 핵심 개념 | S0 `subject_matter` → §5-3 정규화 | ~15,000 (2개+ 공유만 노드, 나머지는 활동 속성) |
| **Subject** | 과목 | `subject_name` ↔ `school_curriculum` | ~170 |
| **Source** | 도서·자료 | S0 `sources` 정규화 | ~3,000 |
| **Method** | 탐구 방법 유형 (폐쇄 어휘) | §3 추출 | ~17 |
| **CareerField** | 진로·분야 (폐쇄 분류) | §3 추출 | 30 |
| **ActivityType** | 여러 학생이 같은 프로그램으로 한 활동의 대표 | 제목·임베딩 군집 (§5-4) | ~300 |
| **Theme** | 주제군 (Leiden 커뮤니티, 계층) | §5-5 | 리프 ~300 · 상위 ~40 |
| AchievementStandard | 성취기준 | `subject_achievement_standards` | 1,118 (후속 단계) |

**Student 노드는 없다.** 연구 §3의 확정 설계(허브가 되어 구조를 가린다)이고, 여기서는 **개인정보 경계**이기도
하다 — 학생 코드는 `InquiryActivity`의 속성으로만 남기고 화면은 교사에게만 보인다(§7).
Thread(학생 안 흐름)는 학교 그래프에 올리지 않는다 — 학생 개인 KG의 것이고 학생 간에는 뜻이 없다.

### 4-2. 엣지

| 엣지 | 방향 | 근거 | 가중치 |
|---|---|---|---|
| Activity —HAS_CONCEPT→ Concept | ✓ | S0 | `concept_support`(합의 패스 수) |
| Activity —IN_SUBJECT→ Subject | ✓ | 기록 메타 | — |
| Activity —USES_METHOD→ Method | ✓ | §3 | — |
| Activity —USES_SOURCE→ Source | ✓ | S0 | — |
| Activity —IN_FIELD→ CareerField | ✓ | §3 | — |
| Activity —INSTANCE_OF→ ActivityType | ✓ | §5-4 | 군집 유사도 |
| Activity —DEEPENED_FROM→ Activity | ✓ (시간이 정향) | **research-v7 그대로** | confidence |
| Activity —RELATED_TO→ Activity | ✗ | research-v7 그대로 | confidence |
| Activity —SIMILAR_TO→ Activity | ✗ | **학생 간** 임베딩 kNN ∧ 개념 겹침 | cos·jaccard 결합 |
| Concept —CO_OCCURS→ Concept | ✗ | 같은 활동 동시 등장 | PMI |
| Activity —MEMBER_OF→ Theme | ✓ | Leiden | — |
| Theme —PARENT→ Theme | ✓ | Leiden 계층 | — |

**학생 간 엣지는 SIMILAR_TO 하나뿐**이다. 학생 A의 활동이 학생 B의 활동을 "심화했다"는 말은 성립하지 않는다.
학생 간에 뜻이 있는 것은 *같은 주제군에 속하고 사고 수준이 더 높다*는 **사실**이고, 그것은 Theme 소속 + `level`
속성으로 표현된다 — 경로 질의(§6-2)가 그 둘을 조합한다.

### 4-3. `activity` 표와의 관계 — 옮기지 않고 잇는다

`activity`(창체 기록 시스템)는 "학교가 연 활동 1건 + 참여자 N명"이고, 이 그래프는 "학생이 각자 한 탐구 34,254건"이다
(§2-3: 93%가 개인 단위). 두 모델을 합치면 어느 한쪽이 왜곡된다. 그래서

- 그래프는 **별도 표**(`inquiry_*`, §7)에 둔다.
- `ActivityType`(프로그램형 군집)만 나중에 `activity`로 **가져오기(import)** 할 후보다 — `source='import'` 값이
  이미 enum에 있다. 지금은 하지 않는다(사용자 확인 후).
- `activity` 행이 생기면 그 활동의 참여자·성찰이 새 `InquiryActivity`로 그래프에 **합류**한다(같은 스키마).
  즉 생기부 추출은 **초기 채움**이고, 창체 기록 시스템이 쌓는 데이터가 같은 그래프의 **현재형**이 된다.

### 5-1. E0 코퍼스 조립 (구현 완료, `build-corpus.mts`)

기록마다 `sentences`가 저장돼 있으므로 활동의 원문은 `sentence_ids`로 즉시 복원된다.
학년도 = 입학연도 + 학년 − 1(CLAUDE.md 규약). `field_mismatch=true`(연구 §12-4 오배치) 28건은 **제외**한다 —
제목·개념이 다른 활동의 것이라 판정의 재료가 될 수 없다.

### 5-1-1. 동아리명·시수는 **원문 서식에서 그냥 뽑힌다** (2026-09-10)

동아리활동 원문은 `(동아리명)(N시간) 본문` 서식이다. LLM 을 부를 이유가 없다 —
정규식 한 줄로 **1,359기록 100%**, 고유 동아리 **100개**, 시수 2~40시간이 나온다.

**⚠️ greedy 로 두면 실패하지 않고 그럴듯하게 틀린다.** 이름이 `윙스(화학)` 처럼 **중첩 괄호**를
포함하므로 `\((.+)\)` 로 잡아야 하는데, 그러면 본문 안에 `(N시간)` 이 또 나올 때 **거기까지 먹어
동아리명이 600자**가 된다(실측 8건). 추출률은 여전히 100% 라 숫자만 보면 정상으로 보이고,
**길이 분포를 봐야** 드러난다. 채택한 패턴 = `^\s*\((.{1,40}?)\)\s*\(\s*(\d+)\s*시간\s*\)`
(non-greedy + 이름 길이 상한). 고친 뒤 최장 13자.

**이름 안의 분류 괄호는 그대로 둔다**(`윙스(화학)` · `달구지(교지편집)`) — 원문 표기가 곧 식별자다.
쪼개면 `뷰`·`큐브`처럼 뜻을 잃는 이름이 생긴다.

**개념(`concepts`)에 섞지 않고 컬럼으로 둔다.** 동아리명은 활동의 속성이지 개념이 아니다 —
개념에 넣으면 IDF 가중치와 노드 승격에 끼어들어 **같은 동아리라는 이유만으로 활동이 묶인다**
(§5-5-1 이 역량어에서 겪은 일과 같다).

**적재**: `inquiry_activity.club_name`·`hours`, 뷰에도 노출(동아리명은 **사람이 아니라 조직**이라
학생 코드를 가리는 규칙과 충돌하지 않는다 — 한 동아리에 수십 명이 있어 개인이 특정되지 않는다).
실측 3,134건 전부 채워졌고 뷰에서 1,946건(탐구 인정분).

**화면**: 활동 목록 행의 칩 · 상세 모달 부제(`동아리활동 · 실험수학연구회 · 2학년 · 33시간`) ·
활동 기록 씨앗의 **`operatorName`**(운영 주체) — 키워드가 아니라 주최 칸이 맞는 자리다.

### 5-2. E1 탐구 판정 (파일럿 완료 — §8)

배치 파일(활동 80건: 영역·과목·학년·문장·S0 개념) → Sonnet 서브에이전트가 §3 스키마로 응답 → `validate-rubric.mts`가
검증·수준 유도·병합. **재시도 조건**은 S0와 같은 축이다 — 커버리지(배치 대비 응답 활동 수) < 95% → 재요청.

**왜 서브에이전트인가.** Anthropic API 키가 없고, Claude Code 안에서 Sonnet을 쓰는 방법은 `Agent` 도구의 모델
지정뿐이다. 배치는 파일로 주고받아 **오케스트레이터(Fable)의 컨텍스트에 활동 원문이 들어오지 않게** 한다 —
그래야 "Fable을 쓰지 않는다"가 실제로 성립한다. 같은 배치 형식이 Anthropic Batch API(50% 할인)에도 그대로
들어가므로 키가 생기면 러너만 바꾼다(§9).

### 5-3. E2 개념 정규화 — 세 층

1. **코드**: 공백·가운뎃점·괄호 제거, 로마/아라비아 숫자 통일, 조사 접미 제거 → 56,578 → 약 5만
2. **임베딩 군집**: text-embedding-3-small · cos ≥ 0.92 이웃을 후보 쌍으로 (연구 §12 Arm A "표기 근접"의 확장)
3. **Sonnet 판정**: 후보 쌍만 "같은 개념인가 / 포함관계인가 / 별개인가". `자연선택 ⊂ 자연선택 이론`은 병합,
   `진화론 ⊂ 사회진화론`은 별개 — 코드로 못 가른다(연구 S1의 분업 그대로)

**과잉 병합 가드**: 한 그룹이 전체 언급의 0.3%를 넘으면 붕괴로 보고 그 그룹만 되돌린다(S1의 `MAX_GROUP_SHARE`와
같은 원리). 병합 판단은 되돌릴 수 있지만 버려진 원 표현은 못 되살리므로 **원 표기는 전부 보존**한다.

**실측 (2026-09-07, Solar 17배치)**: 후보 820쌍 중 **같음 128 · 상하위 35 · 별개 645(79%)**. 가드 되돌림 0건.
"애매하면 별개"가 기본값이라 79%가 기각된 것이 정상이다 — 잘못 합치면 서로 다른 탐구가 한 노드로 뭉개지고
되돌리기 어렵지만, 안 합치면 노드가 둘일 뿐이다. 병합된 것은 대부분 표기 차이다
(`농도와 반응 속도 관계`=`농도와 반응속도의 관계`, `비어-람베르 법칙`=`비어-람베르트 법칙`, `수학 모델링`=`수학적 모델링`).

**효과는 작지만 실재한다** — 개념 키 49,718 → 49,592, 노드 12,815 → 12,691, **잡탕 리프 활동 비율 22.4% → 21.0%**
(응집도 lift·고립률은 변화 없음). 개념 유형 분류가 잡탕을 3.4%p **악화**시킨 것과 대비된다(§5-5-1) — 병합은 채택,
유형 분류는 `trait` 만 채택.

**배치 크기는 50이다** — 150쌍에서 Solar 가 `finish_reason=length` 로 6회 재시도를 모두 소진했다(개념 유형 분류의
400 → 120과 같은 이유). 17배치 93초.

### 5-4. E3 활동 유형 군집 (2026-09-08 구현 · `graph/activity-types.py`)

교사가 "무엇을 시킬 수 있나"를 물을 때 알아야 할 것은 **재현 가능한 프로그램**인지 **한 학생의 개인 탐구**인지다.
활동 하나만 보면 둘이 똑같이 생겼고, **여러 학생에게 반복되는가**로만 갈린다.

같은 (코호트, 학년, 영역) 안에서 ①제목 정규화 일치 ∨ ②임베딩 cos ≥ 임계 → union-find, **서로 다른 학생 3명 이상**이면
`ActivityType`. 활동 수가 아니라 **학생 수**가 기준이다 — 한 학생이 같은 제목으로 두 번 쓴 것은 프로그램이 아니다.

**임계값 0.9 는 설계 때의 짐작이었고 실측에서 너무 좁았다.** 창체 3영역 5,170건 스윕:

| cos | 유형 | 덮은 활동 | 커버리지 | 판단 |
|---|---|---|---|---|
| 0.95 | 19 | 74 | 1.4% | 같은 제목만 겨우 |
| 0.90 (설계값) | 25 | 108 | 2.1% | 큰 학교 행사를 통째로 놓친다 |
| 0.85 | 66 | 284 | 5.5% | 군집은 깨끗하다 |
| **0.80** ★ | **151** | **793** | **15.3%** | 체육 한마당·찬양축제·복교기념행사가 잡힌다 |
| 0.78 | 176 | 965 | 18.7% | 더 낮출 근거가 없다 |

**낮출수록 좋기만 한 것이 아니다 — 0.80 부터 "체험 캠프"류가 붙는다.** 실측된 오병합:
`창의 융합 탐구 캠프` · `진로 체험캠프` · `영상 매체 탐구 캠프` · `물리치료학과 체험 활동`이 한 군집이 됐다.
서로 다른 활동인데 **제목이 일반어(캠프·체험·탐구)뿐**이라 임베딩이 가깝다.

**그래서 임계값을 올리는 대신 조건을 하나 더 걸었다** — **구성원의 60% 이상이 같은 고유어를 공유해야 한다**
(`shares_distinctive`, 일반어 목록 `GENERIC_TOKENS`). 물벼룩·아스피린·DPPH·한마당·복교는 공유하고 캠프는 못 한다.
가드는 정확히 오병합이 나타나는 자리에서만 작동한다: **0.85 에서 0건 · 0.80 에서 7건 · 0.78 에서 12건**.
임계값 하나로 두 실패(놓침·뭉침)를 동시에 조절할 수 없어서 축을 나눈 것이다.

**전량 결과(28,309 활동)**: 유형 **664** · 덮은 활동 **7,602(26.9%)** · 일반이름 기각 21.
영역별 = 세특 408 · 세특(진로) 105 · 동아리 55 · 자율 49 · 진로 47.

**가장 큰 발견은 창체가 거의 전부 개인 탐구라는 것이다** — 창체 3영역에서 학생 3명 미만인 군집이 4,900여 개다.
세특은 반대로 수업 과제가 공유돼 유형이 많다. 즉 **"따라 할 수 있는 프로그램"은 세특에, "이 학생만의 탐구"는 창체에**
몰려 있고, 조회 화면은 이 둘을 같은 목록에 섞으면 안 된다(§6-1 국소 검색에서 `recurring` 으로 가른다).

**연도 간 연결(E3')이 교사가 실제로 묻는 것에 답한다 (2026-09-10)** — 군집은 코호트별로 만들어지므로 같은 프로그램이
해마다 **따로** 잡힌다(체육 한마당 2023-1 · 2024-1). 그런데 교사의 질문은 "이 프로그램은 몇 해 운영됐나"다.

**잇는 조건 셋을 모두 요구한다**: ①같은 영역·같은 학년(학년이 다르면 같은 이름이라도 다른 프로그램이다)
②공통 고유어 일치(군집 안에서 이미 검증된 이름이라 재사용) ③임베딩 중심 cos ≥ 0.75.
**이름만으로 잇지 않는 이유** — `과학`·`탐색` 같은 짧은 고유어는 해마다 다른 행사에도 붙는다. 반대로 임베딩만으로도
안 된다 — 서로 다른 해의 서로 다른 행사가 "학교 행사"라는 점에서 이미 가깝다. 이름이 강한 증거이고 임베딩은 그 이름이
우연히 겹친 경우를 걸러내는 데만 쓴다.

**실측(창체 10,082 활동)**: 유형 289개 · 활동 1,638건(16.3%) · **연도를 가로지르는 프로그램 15개**.

| 운영 연도 | 인원 | 프로그램 |
|---|---|---|
| 2023·2024·2025 | 53 | 수능 응원 영상 제작 (자율 1학년) |
| 2023·2024·2025 | 17 | 플로어볼 (동아리 1학년) |
| 2023·2024 | 61 | 체육 한마당 (자율 1학년) |
| 2023·2024 | 30 | 찬양축제 (자율 2학년) |
| **2023·2025** | 14 | 브로콜리 DNA 추출 실험 (동아리 1학년) — **2024 가 빠져 있다** |

마지막 줄이 이 연결의 값을 보여 준다 — 끊긴 해가 있다는 것은 군집만 봐서는 안 보인다.
학년별로 따로 잡히므로(수능 응원이 1학년·2학년 별도) 프로그램 수는 실제보다 많게 세어진다 — **의도한 것이다**
(같은 이름이라도 학년이 다르면 준비물·수준이 다르다).

**LLM 이름 붙이기는 아직 안 했다** — `shared_token` 과 최빈 제목이 이미 이름 노릇을 하므로, 성격 분류
(프로그램/수업 과제/개인 탐구)는 E6 배치에 함께 붙인다.

### 5-5. E5 주제군 — Leiden

이종 그래프(Activity + Concept)에 **가중 Leiden**(python-igraph + leidenalg, resolution 계층 2~3단).
Microsoft GraphRAG가 엔티티 그래프에 Leiden을 거는 것과 같지만, 우리는 활동 노드를 함께 넣는다 —
탐색 단위가 개념이 아니라 **활동**이기 때문이다(학생이 고르는 것은 "무엇을 해 볼까"다).

예체능·기능 수행형 활동은 코퍼스에서 뺐지만 창체 안의 체육 동아리 등은 남는다. 그것들은 자기들끼리 군집을
이루고 `level` 분포가 낮게 나오므로 **탐색 순위에서 자연히 밀린다.** 억지로 지우지 않는다.

**가드**: 리프 크기 상한(~200)·하한(5). 하한 미만은 상위에 흡수. 고립 활동은 있는 그대로 둔다(연구 §13 —
"고립률 0을 목표로 삼으면 안 된다").

**실측 (2026-09-07, 판정 없이 구조만)** — `graph/build-graph.py`, 임베딩 kNN k=10·cos≥0.80, Leiden 해상도 1.0,
개념 노드는 `trait` 제외(아래 §5-5-1):

| 항목 | 값 |
|---|---|
| 노드 | 41,124 (활동 28,309 + 개념 12,815) |
| 엣지 | 135,270 — HAS_CONCEPT 88,166 · SIMILAR_TO 37,015 · RELATED_TO 9,817 · DEEPENED_FROM 1,666 · DUPLICATE_OF 62 |
| 고립 활동 | **946 (3.3%)** — 학생 개인 KG의 13~49%(연구 §7)와 대비. 학생 간 SIMILAR_TO 가 고립을 지운다 |
| 리프 주제군 | Leiden 그대로 1,949(중앙값 7, 5 미만 910) → **작은 리프 흡수 + 고립 제외 후 1,057**(중앙값 19, 5 미만 **1**) |
| 상위 주제군 | 축약 그래프 Leiden 은 **792**(끊긴 조각마다 하나) → 리프 중심 k-means 로 **33** |
| 응집도 | 리프 안 무작위 쌍 평균 cos **0.493** vs 전체 무작위 쌍 0.281 → **lift 0.212** |
| 잡탕 리프(쌍 평균 cos < 0.40, 10건 이상) | 299개 · 활동 6,349건 = **22.4%** |

**두 가지 결정이 실측에서 나왔다.** ①축약 그래프에 Leiden 을 다시 걸면 상위가 수백 개가 된다 — 연결이 끊긴 리프가 각자
상위가 되기 때문이고, 열람 화면이 감당할 수는 수십 개라 **상위는 개수를 직접 정한다**(k = √리프 수, 상한 60).
②고립 활동은 리프를 만들지 않는다 — 크기 1 리프 758개가 리프 수를 부풀렸다.

### 5-5-1. 개념 유형 분류는 **대부분 기각**했다 (2026-09-07 재보고)

발단은 실측 리프 `t:320` 이다 — 『데미안』서평·마라톤 완주·한자 탐구가 `노력·인내·끈기·성공·응용력` 으로 한 군집이 됐다.
역량어를 개념 노드에서 빼면 나아질 것으로 보고 13,419개를 Sonnet… 이 아니라 **Solar 로 유형 분류**했다
(`prompts/concept-type.md` · domain 10,534 · method 1,115 · entity 637 · trait 608 · generic 493).

**그런데 재보니 이득이 없었다.**

| 구성 | 리프 | 응집도 lift | **잡탕 리프 활동 비율** | 고립률 |
|---|---|---|---|---|
| 제외 없음 | 763 | 0.1865 | **28.3%** | 2.7% |
| trait 608개만 제외 | 778 | **0.1940** | **27.7%** | 3.3% |
| 유형 분류 전체(2,853) 제외 | 645 | 0.1866 | **31.7%** | **7.0%** |

**전체 제외는 확실히 나쁘다** — 잡탕이 3.4%p 늘고 고립이 2.6배가 된다. `method`·`entity`(『조선왕조실록』·5·18 민주화 운동)를
빼면 활동을 잇던 다리가 함께 사라지기 때문이다. `trait` 만 빼는 것은 이득이 미미하고(0.6%p) 측정 오차와 구분되지 않지만,
비용도 작고 실패 사례가 그 유형에서 나왔으므로 **trait 만 제외**를 채택한다. 나머지 유형은 **활동 속성으로 그대로 남긴다**
(방법·자료·인물은 화면에서 쓸모가 있다).

**첫 측정은 틀렸다 — 지표가 크기에 오염돼 있었다.** 처음 쓴 응집도는 "리프 중심과의 평균 cos"인데 이 값은 **집합이 작을수록 커진다.**
정지어 75개가 리프를 768→978 로 잘게 쪼갠 것을 0.691→0.701 의 "개선"으로 읽었다. 지금 지표는 **리프 안 무작위 쌍의 평균 cos**
(크기 무관)이고 전체 무작위 쌍(0.281)을 기준선으로 함께 낸다. **군집 지표를 만들 때는 크기 효과부터 제거할 것.**

**그리고 진짜 지렛대는 개념 어휘가 아니라 해상도였다** — 같은 trait-제외 구성에서 Leiden 해상도만 올리면
잡탕 비율이 **27.7%(0.5) → 22.4%(1.0) → 20.0%(2.0)** 로 준다. 리프 수는 778 → 1,057 → 2,016. 열람·보고서 비용과의
맞바꿈이라 **1.0 을 채택**했다(리프 1,057 · 중앙값 19).

**지표 셋을 함께 본다** — `cohesion_lift`(뜻으로 묶였는가) · `weak_leaf_share`(꼬리의 잡탕) · `subject_purity`(과목별 군집으로
퇴행했는가, 현재 0.54). 평균만 보면 잡탕을 놓치고, 꼬리만 보면 전체가 잘게 쪼개진 것을 개선으로 착각한다.

### 5-5-2. 판정 파일이 겹치면 **이름 순서가 승자를 정한다** (2026-09-08 발견·수정)

`build-graph.py` 는 `graded/*.jsonl` 을 전부 읽어 `level[activity_id] = g` 로 덮어썼다. 그런데 `graded/` 에는
프롬프트를 고칠 때마다 **같은 활동을 다시 채점한 파일**이 쌓여 있다 — v1·v2·v2.1·v2.2·solar 실험까지 **15벌**이고,
본 판정(`w1-club`)과의 겹침이 **거의 100%** 다(pilot-v22 180건 중 179건).

**지금 무사한 것은 우연이다.** glob 이 정렬되면 `w1-club` 이 `pilot*` 보다 뒤라 마지막에 이겨서 그렇다.
다음 단계인 세특 판정을 `career`·`regular` 로 이름 붙이는 순간 **c·r 이 p 보다 앞이라 v1 시절 판정이 조용히 덮어쓴다**.
v1 은 감사에서 12/60 과다 인정으로 폐기한 판이다. 오류도 경고도 없이 그래프의 수준만 나빠진다.

**수정 2겹**: ①기본으로 `pilot*` 을 뺀다 ②그래도 두 파일이 같은 활동을 채점했으면 **예외로 중단**한다
(어느 쪽을 쓸지는 코드가 정할 문제가 아니다). 명시하려면 `--graded w1-club,career`.
검증: `pilot-v21,pilot-v22` → 180건 중복으로 차단 · `w1-club` 단독 → 통과.

**그리고 실제로 한 곳 더 있었다** — E6 입력 조립기 `make-theme-inputs.mts` 가 `readdirSync` 로 같은 폴더를
전부 읽고 있었다. 같은 규칙(`--graded` 명시 · 파일럿 제외 · 중복 시 중단)을 그쪽에도 넣었다.
**파일 이름이 우선순위가 되는 구조를 만들지 말 것** — 한 군데를 고치면 같은 폴더를 읽는 다른 곳을 함께 찾아볼 것.

### 5-6. E6 주제군 보고서 (Sonnet)

리프마다 한 편, 상위마다 한 편. **모든 문장에 활동 id 인용**을 강제한다(연구 §3의 evidence 원칙).

```
- 이름 · 한 줄 요약
- 무엇을 탐구하나 (핵심 개념 · 과목 · 학년 분포)
- 어떻게 하나 (방법 유형 분포 · 산출물)
- 대표 활동 5건 (수준 4→3 순, 활동 id)
- 이어지는 경로 (군집 안 DEEPENED 사슬 요약)
- 비어 있는 곳 — 근거 7항목 중 이 군집이 약한 항목 (예: 성찰·개선 12%)
- 확장 후보 (extension_hint 집계 + 인접 군집)
- 진로 분야 분포
```

**"비어 있는 곳"이 전역 질문(§1)의 답이 되는 자리다.** 개별 활동으로는 볼 수 없고 군집 통계로만 보인다.

**시험 실행(2026-09-07, Solar 5개 주제군)에서 드러난 것 3가지** — 프롬프트에 반영했다.
①**인용이 장식이 된다**: 같은 활동 id 3개를 모든 문장에 복붙했다 → "그 문장을 실제로 뒷받침하는 활동에만, 통계 문장에는 인용 없이".
②**표본이 적은데 비율을 말한다**: 판정된 활동이 148건 중 3건인 군집에서 "성찰 0%"라고 썼다 → `graded < 10` 이면 비율 금지.
③**폐쇄 어휘를 벗어난다**: `fields` 에 목록에 없는 `사회학` 이 나왔다 → 입력에 있는 이름만.
그리고 **보고서는 판정이 채워진 뒤에 만든다** — 지금 판정된 활동이 480건뿐이라 대부분 군집의 `level_dist`·`evidence_rate` 가 비어 있다.

### 5-6-1. E6 실행 결과 — 인용 id 를 복원해야 화면에서 링크가 산다 (2026-09-10)

창체 전용 그래프(§8-11) 위에서 **주제군 363개 전량** 보고서를 만들었다(`solar-pro4 · --expect object`, 4.5시간).
필수 키 누락 0. 그런데 **인용한 활동 id 를 전수 검사하니 링크가 깨질 상태였다.**

**첫 검증이 틀렸다 — 패턴이 좁아 오류가 없는 것처럼 보였다.** 완전한 uuid(`act:<36자>#n`)만 세었더니
"본문 인용 2,234건 중 목록 밖 6건(0.27%)"이었는데, **축약형까지 세니 1,466건이 축약**이었다
(`act:3952507c` 처럼 앞 8자만, `act:f78ca80d#4` 처럼 축약에 활동 번호만). 화면에서 전부 죽은 링크가 된다.

**복원기 `repair-theme-reports.mts`** — 접두가 그 주제군 안에서 **고유하면** 되살리고(활동 번호가 있으면 그것까지 맞아야 한다),
안 되면 **지운다**. exemplar 는 항목째 빼고(활동을 지목하지 못하는 예시는 예시가 아니다), 본문은 **문장을 남기고 id 만** 뺀다
(문장을 지우면 설명이 끊긴다).

| | 복원 | 제거 |
|---|---|---|
| exemplar | 24 | 2 |
| 본문 인용 | 1,466 | 25 |

**적용 후 재검증: exemplar 1,582 · 본문 인용 3,697 중 목록 밖 0건.**

**`fields` 가 빈 39건은 결함이 아니다** — 전부 **탐구 0건인 주제군**이고(수능 응원 영상 · 동아리 기획·운영 ·
학급 리더십) 입력에도 분야가 0개였다. 모델이 "근거 없으면 쓰지 않는다"를 지킨 결과다. 화면은 이 39개를
"진로 분야가 특정되지 않는 활동군"으로 표시하면 된다(빈칸으로 두면 누락으로 읽힌다).

**보고서가 낸 분야 분포**(324개 주제군): 의학 102 · 생명과학 85 · 사회·문화 80 · 컴퓨터·AI 59 · 교육 57 ·
환경·기후 54 · 경제·경영 48 · 화학 48. 이름 길이 중앙 18자.

**교훈 — 검증기의 패턴이 좁으면 "오류 없음"이 거짓말을 한다.** 인용을 강제하는 프롬프트를 쓸 때는
**모델이 실제로 쓴 형태**를 먼저 표본으로 보고 패턴을 정할 것.

### 5-6-2. 상위 주제군 보고서 — 리프를 **요약본으로 접어** 넣는다 (2026-09-10)

§6-3 전역 검색("이 학교의 창체는 어떤 갈래로 이뤄지나")의 재료다. 창체 전용 그래프의 **상위 21개**가 대상이고
각 상위 아래 리프가 최대 50개다.

**원문 활동을 다시 넣지 않는다** — 상위 하나에 리프 50개 × 활동 최대 200건이면 한 콜에 수천 건이 되어 예산을 넘긴다.
대신 **이미 만들어진 리프 보고서의 `name`·`summary`·`fields` 와 `deep_ratio`** 를 접어서 넣는다
(LazyGraphRAG 의 map-reduce 에서 reduce 가 하는 일이 이것이다). 리프 보고서가 없는 것
(활동 8건 미만이라 §5-6-1 대상이 아니었던 75개)은 **개념으로 대신한다** — 비워 두면 상위가 그 리프를 아예 못 본다.

**인용 단위가 다르다** — 리프 보고서는 활동 id 를 인용하지만 여기서는 **`theme_id` 만** 인용한다.
상위는 활동을 직접 보지 않으므로 활동을 인용할 자격이 없다(그렇게 두면 §5-6-1 의 축약·환각 문제가 여기서 재발한다).

**프롬프트가 막는 것 하나** — "심화 비율이 낮은 것을 *학생이 못한다* 로 읽지 말 것. 기록이 짧으면 판정 자체가
불가능하다"(§8-10). 실제로 모델이 `shallow` 에 "체험부스·실험·제작 중심이라 **심화 판정이 어려움**"이라 썼다.

**출력 항목**: `name` · `summary` · **`landscape`(이 갈래 안에서 리프들이 어떻게 갈리는가 — 대비되는 축)** ·
`deep` · `shallow` · **`entry`(처음 시작하는 학생에게 권할 진입 지점)** · `fields`.
`landscape` 와 `entry` 가 이 층에만 있는 값이다 — 리프 하나만 봐서는 "어디서 시작할지"를 알 수 없다.

## 6. 질의 (조회 시점)

### 6-1. 국소 검색

질문 임베딩 → 활동 top-k(pgvector) + 개념 top-k → 1~2홉 확장(개념 공유 활동·SIMILAR_TO·DEEPENED 사슬·
소속 Theme 보고서) → 컨텍스트 팩(≤ 8K 토큰) → LLM 답변(활동 id 인용 강제). 질의 시점 LLM은 공용 `aiChat()`
규약(기본 Solar)을 따른다 — 추출 비용 제약은 인덱스 시점 얘기다.

### 6-2. 경로 검색 ("다음엔?")

활동 A → ①같은 학생의 `DEEPENED_FROM` 후속 ②같은 리프 Theme에서 `level > A.level`이고 학년이 같거나 높은
활동 ③A의 `extension_hint`와 임베딩이 가까운 활동. 셋을 합쳐 **"선배들이 실제로 간 길"**로 보여 준다.
LLM 없이 SQL만으로 1차 결과가 나오고, LLM은 그 목록에 이유를 붙일 때만 쓴다.

### 6-3. 전역 검색

질문 임베딩으로 Theme 보고서 상위 N(리프 20 + 상위 5)을 고르고(LazyGraphRAG식 선택 — 전 커뮤니티를 훑지
않는다) → map(보고서별 관련 요점) → reduce(종합). 보고서가 ~340편이라 선택만으로 충분하다.

### 6-4. 열람 (LLM 없음)

Theme 트리 → 리프 → 활동 카드(수준·방법·분야·개념) → 활동 상세(원문 문장 + 근거 하이라이트 + 심화 사슬).
창체 화면의 **진로·분야 타일이 CareerField 노드**와 정확히 대응하므로 지금 첫 화면에 그대로 얹힌다.

### 6-5. 탐구 → 활동 기록: **씨앗까지만** 옮긴다 (2026-09-10)

"탐구 탐색의 데이터를 기존 활동 기록에 저장할 수 있나"에 대한 답이다. **할 수 있고, 대량 적재는 하지 않는다.**

**`activity` 는 교사가 쓰는 운영 기록이다** — 목적·내용·성과·장소·시수·예산·기간이 있어야 기록으로서 뜻이 있다.
파이프라인이 가진 것은 제목·개념·판정뿐이라, 활동 유형 289개를 그대로 밀어 넣으면 **반쯤 빈 행 289개가
진짜 기록 사이에 섞인다.** 그러면 "활동 기록"이라는 표의 뜻이 흐려진다(§4-3 이 두 표를 나눈 것과 같은 이유다).

그래서 **폼을 미리 채워 여는 것**까지만 한다. 이미 있는 씨앗 경로(`ActivityFormDialog seed`)를 그대로 쓰므로
새 저장 경로도, `source='inquiry'` 같은 새 값도 만들지 않는다 — 저장하는 사람은 교사이고 `source='manual'` 이 맞다.

**세 자리에서 옮긴다**(`utils/inquiryToActivity.ts`):

| 자리 | 씨앗에 담기는 것 |
|---|---|
| 해마다 반복된 프로그램 | 이름 · 영역 · 운영 연도 · 참여 인원 — `activity` 와 모양이 가장 가깝다(학교가 연 활동 + 참여자 여럿) |
| 리프 주제군 | 주제군 이름 · 진로 분야 · 개념 키워드 · **깊이 있게 진행된 사례 3건** |
| 활동 하나 | 제목 · 한 일 · 연구 질문 · 방법 · 확장 가능성 |

**채우지 않는 것: 기간·장소·시수·예산.** 파이프라인은 모른다. 그럴듯한 값을 넣으면 교사가 확인하지 않고
지나칠 위험이 있고, **빈 칸은 "채워야 한다"고 스스로 말한다.** 내용 끝에 "지난 기록을 요약한 것이니
올해 운영 계획으로 고쳐 주세요"를 덧붙인다.

**진로 분야·키워드는 판정된 활동에서 실제로 나온 값만 쓴다** — 보고서의 서술을 그대로 넣으면
교사가 쓰지 않은 말이 운영 기록에 남는다.

**학생에게는 버튼을 그리지 않는다**(`access.canCreate` 로 판정). 활동 기록은 교사가 쓰는 것이다.

### 6-6. 활동 유형 150건을 `activity` 에 실제로 적재했다 (2026-09-10 사용자 지시)

§6-5 는 "씨앗까지만"이었는데, 사용자가 **전체 목록에도 보여야 한다**고 해서 실제 적재로 넓혔다.

**조건은 "활동당 평균 2.5문장 이상" 하나다** — 심화 비율은 보지 않는다(사용자 결정).
처음엔 `심화 ≥ 5%` 로 89건을 넣었는데, **두 조건은 서로 다른 것을 묻는다**:
심화 비율은 "이 활동이 깊었나", 문장 수는 **"깊이를 판단할 재료가 있나"** 다(§8-10).
심화만 보면 `'수학은 발견인가 발명인가' 토론`처럼 **심화 75%인데 2.25문장**인 활동이 들어온다 —
4건 중 3건이 L3+ 지만 그 판정 자체가 얇다. 반대로 지금 조건에서 들어온 심화 5% 미만 82건은
**"깊이가 없다"가 판단 가능한 상태에서 내려진 결론**이라 활동 기록으로서는 그것도 정보다.

**단위는 활동 유형이지 주제군이 아니다.** 둘 다 심화 비율을 갖지만 `activity` 는
"학교가 연 활동 1건 + 참여자 N명"이다 — 활동 유형(학생 3명 이상)이 그 모양이고
주제군은 **주제**다. 주제군을 넣었으면 "저출산·SDGs·노동인권"이 활동 기록에 들어갔을 것이다.

| 단위 | 전체 | 문장 ≥ 2.5 | (참고) 심화 ≥ 5% |
|---|---|---|---|
| 리프 주제군 | 438 | — | 158 |
| **활동 유형** ★ | 289 | **150** | 89 |

**적재 결과**: 활동 **150** · 참여자 **751** · 계보 연결 **7**.
행마다 `meta.inquiry_mean_sentences`·`inquiry_deep_ratio` 를 남겨 **어떤 기준으로 들어왔는지** 보인다.
조건을 좁혀 지울 때는 **교사가 손댄 흔적(목적·기간·장소·시수·예산·작성자)이 있으면 남긴다** —
적재 뒤 사람이 채운 것은 파이프라인이 만든 것이 아니다.
`source='import'`(허용값에 `inquiry` 가 없고 실제로 import 다) · `status='done'` · `scale='group'`.
학년도 = 입학연도 + 학년 − 1 (2023~2026).

**멱등이다** — `meta.inquiry_type_id` 가 있으면 건너뛴다. 같은 SQL 을 다시 돌려도 늘지 않는다.

**기간·장소·시수·예산은 비운다.** 파이프라인이 모르는 값이라 그럴듯하게 채우면 교사가 확인 없이 지나친다.
`starts_on` 은 NOT NULL 이라 학년도 3월 1일을 넣되 `meta.period_unknown=true` 와 본문에 그 사실을 적는다.

### ⚠️ 내용은 **집계 서술**이다 — 학생별로 나열하지 않는다

사용자가 "자세한 내용도 표시되도록" 해서 본문을 채웠는데, **학생별 항목을 나열하면 안 된다.**

`activity_participation` 의 SELECT 정책은 `... OR is_activity_participant(activity_id)` 라
**참여자는 서로의 명단을 본다.** 거기에 학생별 탐구 서술을 나열하면 3명짜리 활동에서
참여자끼리 **누구의 세특 문장인지 맞출 수 있다** — 세특은 개인 평가다.

탐구 탐색에서는 `student_code` 가 없어 원리적으로 불가능한데 활동 기록에는 명단이 있다 —
**같은 데이터라도 놓이는 자리에 따라 위험이 달라진다.**

그래서 본문은 활동을 서술한다(원래 `content` 가 그런 자리이기도 하다):
수준 분포 · 방법 분포 · 반복 운영 연도 · **학생들이 던진 연구 질문(최대 8, 이름 없이)** ·
**여기서 더 나갈 수 있는 것(최대 4)**. 평균 358자.
끝에 "개인별 기록은 [탐구 탐색] 에서 볼 수 있습니다"를 적어 개인 단위 열람은 권한이 갈리는 그쪽으로 보낸다.

#### 집계 본문에서도 통계를 걷어냈다 (2026-09-18)

**위 문단의 "수준 분포 · 방법 분포 · … 평균 358자"와 끝의 안내문은 더 이상 맞지 않는다.**
개별 활동(§6-7)과 같은 지적이 여기에도 적용됐다 — 머리말("생기부 기록에서 확인된 활동입니다.
참여 학생 N명 · **탐구 판정 N건** · **기록 평균 N문장**")과 `· 수준 분포:` 줄, 그리고
`※ 개인별 기록은 [탐구 탐색] 에서 …` 꼬리말은 파이프라인 어휘라 교사에게 뜻이 없다.

**`· 방법` 은 사용자 지시로 남겼다** — 개별 활동에서 남긴 것과 같은 항목이고, 150건 전부가
갖고 있어 **이것이 본문이 통째로 비는 것을 막는 유일한 줄**이기도 하다(연구 질문 블록은 113건,
확장 블록은 27건뿐이라 둘만 남기면 24건이 빈다). 남는 것 = `· 방법` ·
[학생들이 던진 연구 질문] · [여기서 더 나갈 수 있는 것]. 평균 284자 → **180자**.

**정규식이 아니라 줄 단위로 걸렀다** — 이 본문은 빈 줄로 나뉜 블록 구조라 정규식이 경계를
먹으면 오류 없이 모양만 망가진다. 손대기 전에 150건의 줄을 **전수로 열거**해 예상 밖 줄이
없음을 확인했다(`· 운영 연도` 0건). 표본 몇 개만 보고 정규식을 쓰면 조용히 어긋난다.

마이그레이션 = `supabase/migrations/20260918170438_activity_type_aggregate_strip_stats.sql`.
**이 150건을 만든 SQL 은 저장소에 없다**(일회성으로 적용됐다) — 다시 적재한다면 같은 3종을
빼고 만들 것. §6-7 의 적재 SQL 과 달리 고쳐 둘 대상이 없다.

한편 **폼 씨앗 경로(`utils/inquiryToActivity.ts`)는 건드리지 않았다** — 거기 붙는
"※ 위는 지난 기록을 요약한 것입니다. 올해 운영 계획으로 고쳐 주세요."는 저장된 값이 아니라
**교사에게 지금 하라고 말하는 지시문**이고, 실제로 그 문구를 단 채 저장된 행은 **0건**이다
(교사가 늘 고쳐서 낸다). 저장 결과가 아니라 편집 안내이므로 같은 자를 대지 않는다.

### 6-7. 묶이지 않은 L3·L4도 개별 활동 기록으로 표시 (2026-09-11)

사용자 요청으로 활동 유형에 묶이지 않아 전체 활동 기록에서 빠졌던 심화 탐구도 표시한다.
창체 `autonomy`·`club`·`career`의 `is_inquiry=true`, L3·L4를 대상으로,
이미 적재된 활동 유형에 포함된 기록과 `meta.inquiry_activity_id`가 있는 기록은 건너뛴다.
주제군·학생 수·문장 수 조건은 추가하지 않는다. 세특은 창체 영역으로 임의 변환하지 않는다.

`scripts/inquiry-graphrag/import-individual-deep-activities.sql`로 **1,439건**을 반영했다
(L3 **927**, L4 **512**). `scale='individual'`, `source='import'`, `status='done'`으로 저장하며
내용에 수준·분량·활동 설명·연구 질문·방법·산출물·확장 가능성을 표시한다.
학년도 3월 1일은 기존 적재와 같은 대체 날짜이고, 본문과 `meta.period_unknown`에 기간 미상을 남긴다.
원본과 정확히 일치하는 활성 동아리가 하나인 **427건**은 기존 주최에 연결했다.

학생 코드와 참여 명단은 복사하지 않는다. 개별 내용에 학생 신원을 연결하지 않고,
기존 `activity` 열람 정책을 적용한다. 원본 추적용 `inquiry_activity_id`와 수준·분량·적재 규칙만 메타에 남긴다.
스키마·권한 변경은 없다. 재실행 결과 추가 **0건**, 부적격 기록 **0건**, 참여 명단 연결 **0건**을 확인했다.

#### 본문에서 추출 흔적을 걷어냈다 (2026-09-18)

위 문단의 "내용에 **수준·분량**…을 표시한다"와 "**본문**과 `meta.period_unknown` 에 기간 미상을
남긴다"는 **더 이상 맞지 않는다.** 사용자 지적 — 출처 안내("생기부 탐구 기록에서 가져온 개별
활동입니다.")·`· 탐구 수준: L3 분석·해석`·`· 기록 분량: 5문장` 세 줄과 꼬리의 기간 미상 안내는
**파이프라인을 돌린 사람에게만 뜻이 있는 값**이라 활동을 쓰는 교사에게는 군더더기다.

본문에 남는 것은 활동 자체의 내용 5종뿐이다: **연구 질문 · 방법 · 산출물 · 다룬 개념 ·
확장 가능성**. 기간 미상은 이제 `meta.period_unknown` **에만** 있다.

**⚠️ 눈에 띄는 증상은 상세 모달이 아니라 목록이었다.** `content_excerpt` 가 `left(content, 80)`
(→ `20260911090539`)이라 그 80자를 상용구가 거의 다 먹어 **1,880개 행이 전부 같은 한 줄**을 달고,
정작 구별되는 연구 질문·개념은 한 글자도 보이지 않았다. 본문에 무엇을 넣을지 정할 때
**발췌 창(80자)에 무엇이 들어오는지**를 함께 볼 것 — 상세 화면만 보고 정하면 이렇게 된다.

값은 잃지 않는다 — 탐구 수준·문장 수는 `meta.inquiry_level`·`meta.inquiry_n_sentences` 에
그대로 있다(1,880건 전부 보유). 배지로 보이고 싶으면 본문이 아니라 그쪽을 읽는다.

적재 SQL 과 이미 적재된 행을 **함께** 고쳤다 — 스크립트만 고치면 라이브가 그대로이고,
데이터만 고치면 다음 재실행에 되살아난다.
`scripts/inquiry-graphrag/import-individual-deep-activities.sql` (재실행해도 안 붙는다) +
`supabase/migrations/20260918164859_activity_strip_import_boilerplate.sql` (1,880건 정리).
검증: 테이블 **전체**에서 상용구 0건 · 빈 본문 0건 · 1,880행을 줄 단위로 펴서
`· (연구 질문|방법|산출물|다룬 개념|확장 가능성): ` 외의 줄 **0건**. 평균 281자 → 152자.

**활동 유형 집계(§6-6, `meta.inquiry_type_id` 150건)도 같은 날 정리했다** — 다만 자가 다르다.
→ 아래 §6-6 의 「집계 본문에서도 통계를 걷어냈다」.

전체 기록이 1,593건이 되어 서버의 기본 1,000행 제한을 넘으므로,
활동 목록과 계보 조회는 안정적인 ID 정렬을 포함해 500건씩 끝까지 읽는다.
회귀 테스트는 1,593건, 빈 목록, 페이지 크기의 배수, 후속 페이지 실패를 검증한다.

## 7-1. E7 적재 — 제안본에서 세 곳을 고쳐 적용했다 (2026-09-10)

`migration-proposal.sql` 은 **그래프가 하나이던 시점**에 쓰였다. 그 뒤 §8-11 에서 창체 전용 그래프가 갈라졌고,
§8-10 에서 "길이를 함께 보여야 한다"가 나왔다. 그래서 적용 전에 세 곳을 고쳤다.

**① 주제군 키에 `graph` 를 넣었다** — 전체 그래프와 창체 전용이 `t:0`·`T:0` 을 **각각** 쓴다.
id 만으로는 충돌해 한쪽이 다른 쪽을 덮어쓴다. `primary key (graph, id)` 이고 부모 FK 도 복합이다.
창체 화면은 `graph='club'`, 교차 연결은 `'full'`.

**② `n_sentences`(활동)·`mean_sentences`(주제군)를 컬럼으로 뒀다** — 화면이 "깊이가 없는 주제"와
"판단할 재료가 없는 주제"를 구분하려면 그 값이 DB 에 있어야 한다(§8-10). `seg_model` 도 함께 담는다
(코호트 비교의 교란원, §8-9).

**③ 학생용 뷰가 직원을 스스로 막는다** — `security_invoker=false` 뷰는 RLS 를 우회하므로
`grant ... to authenticated` 만으로는 **직원까지 열린다**(학생 정보 차단 규약 위반).
뷰의 `where` 에 `is_teacher_or_admin(auth.uid()) or current_student_code() is not null` 를 넣어
직원이 0행을 받게 했다(`current_student_code()` 는 학생이 아니면 NULL 을 준다).

**추가한 표 하나** — `inquiry_activity_type`(+ member). E3 활동 유형과 **연도 간 프로그램**(`program_years`)은
제안본 이후에 만든 것이라 담을 자리가 없었다. 교사에게 "이 프로그램은 몇 해 운영됐나"가 이 표의 존재 이유다.

### id 가 고유하지 않았다 — 조건부 접미로 고쳤다 (2026-09-10)

`act:<record_id>#<첫문장번호>` 인데 **한 기록 안에서 두 활동이 같은 문장에서 시작하면 id 가 겹친다**.
실측 **10건 · 22행**(0.04%). 그대로 넣으면 기본키 충돌로 뒤엣것이 앞엣것을 조용히 덮어쓴다.

**게다가 판정도 이미 하나만 남아 있다** — `graded` 를 Map 으로 읽는 순간 33,042 → 33,031 이 됐고,
어느 활동에 대한 판정인지 알 방법이 없다(배치 입력도 같은 코퍼스에서 나왔으므로 모델이 본 것도 하나다).
그래서 **하나를 고르지 않고 그룹째 건너뛴다** — 잘못 붙은 판정이 화면에 나가는 것보다 낫다.

**분절이 저장한 `entity_id` 도 같은 규칙이라 거기서부터 겹쳤다** — 실측 `cdc19c97…` 은 활동 9개에
충돌 4쌍이고 그중 둘은 **제목까지 같은 중복 분절**이다. 그래서 어디서 왔든 최종 id 에 접미를 붙인다.

**접미는 겹칠 때만 붙인다** — 무조건 붙이면 33,000건의 id 가 전부 바뀌어 기존 판정이 통째로 버려진다
(재채점 2~3일). 조건부면 두 번째부터만 새 id 를 받아 **재채점이 22건**이다. 순서는 `segmentation.activities`
배열 순이라 재실행해도 같다(멱등). 수정 후 실측: 52,268행 = 고유 id 52,268.

**충돌 22건은 전부 세특이었다**(창체 0건) — 창체 전용 그래프와 주제군 보고서 384건은 영향받지 않았다.

**적재 규모**: 활동 52,246 · 개념 88,516(노드 23,754) · 활동-개념 236,930 · 엣지 18,083 ·
주제군 459(보고서 384) · 주제군 구성원 9,260 · 활동 유형 289(프로그램 15) · 유형 구성원 1,638.

**적재기는 멱등이다**(`scripts/inquiry-graphrag/load-db.mts`) — 모든 쓰기가 upsert 이고 키가 결정적이라
몇 번 돌려도 같은 결과이고 중간에 끊겨도 이어서 돌리면 된다. `--only activities|concepts|edges|themes|types`
로 단계를 골라 올린다(재판정만 반영하는 것이 싸야 한다).

## 7-2. `did` 는 요약이 아니라 **전재**였다 — 전수 검사와 수정 (2026-09-11 사용자 지적)

사용자 지적: *"'한 일'로 기록된 내용 중에 생활기록부 내용은 거의 그대로 사용한 경우도 있는데 문제가 될 수도 있음.
전수 검사와 수정이 필요해 보임. 이를 테면 신경 주위 침윤(PNI)과 비교종양학 탐구와 같은 것들이 그러함."*

지목된 사례를 열어 보니 **원문 6문장을 이어 붙이고 종결어미만 바꾼 것**이었다(`수행함.` → `수행하여,`,
마지막 문장만 탈락). 요약이 아니라 전사다.

### 무엇을 어떻게 쟀나

`public.__overlap5(a, b)` — `did` 의 **문자 5-gram 중 원문에도 있는 것의 비율**. 5-gram 을 쓴 이유는
어절 단위로는 조사·어미 변화에 과민하고, 더 길게 잡으면 문장 재배열을 놓치기 때문이다. 문턱을 정하기 전에
**전량을 재서 분포를 봤다**(`inquiry_activity.did_overlap` 에 저장 — 재기만 하고 버리면 다음에 또 잰다).

| 대상 | 건수 | 평균 겹침 | ≥0.7 | 최대 |
|---|---|---|---|---|
| `inquiry_activity.did` (탐구 판정분) | 34,180 | **0.594** | **13,197 (38.6%)** | 1.000 |
| `inquiry_theme.report.summary` (리프 보고서) | 401 | **0.054** | **0** | 0.282 |
| `inquiry_activity.did` (전량 — 비탐구 포함) | 52,268 | 0.614 | 22,055 (42.2%) | 1.000 |

### 왜 이렇게 됐나 — 환각을 막은 설계가 전재를 밀어냈다

이 파이프라인은 지어내기를 막으려고 **"있는 것만 써라"** 를 강하게 걸었다(§2-1 근거 번호 선택,
§2-2 폐쇄 어휘). 그런데 **2~4문장짜리 기록에서 "지어내지 않은 가장 충실한 요약"은 원문 그 자체**다.
즉 이것은 프롬프트 실수가 아니라 **한 건을 요약시키는 과제의 구조적 귀결**이다.

**비탐구까지 넣으면 겹침이 더 높다**(42.2%) — 짧고 담을 것이 적은 기록일수록 전재가 되기 쉽다는 뜻이라
위 진단과 같은 방향이다. 전량을 잰 이유가 이것이다: 재채점으로 비탐구가 탐구로 뒤집히면
**측정되지 않은 채 화면에 뜬다**(`coalesce(null,0) >= 0.7` 은 false 다).

**대조군이 그 진단을 확인해 준다** — 같은 모델·같은 원문으로 만든 주제군 보고서는 평균 0.054 로 깨끗하다.
차이는 과제뿐이다: 보고서는 **여러 활동을 가로질러 종합**하게 하므로 어느 한 원문을 옮겨 적는 것이
애초에 답이 될 수 없다. **한 건을 요약시키면 전재가 되고, 여러 건을 종합시키면 안 된다.**

### 고친 것 — 한쪽만 막으면 우회 통로가 된다

1. **화면**: `inquiry_activity_public` 이 `did_overlap >= 0.7` 이면 `did` 를 null 로 주고
   `did_withheld` 로 **가렸다는 사실을 밝힌다**(빈칸으로 두면 "기록이 없다"로 읽힌다).
   실사용자 컨텍스트 검증: 교사·학생 각각 34,180행 · `did` 보유 20,983 · 가림 13,197.
2. **씨앗**: `activityToSeed`(`utils/inquiryToActivity.ts`) 가 `a.did` 를 무조건 쓰고 있었다.
   화면에서 막은 것을 활동 기록으로 **되살려 내보내는** 경로다.
3. **적재 SQL**: `import-individual-deep-activities.sql` 이 같은 구멍이었고 **이미 새고 있었다** —
   `activity.content` 1,439건 중 **447건이 가림 대상 원문을 그대로** 담고 있었다.
   백업(`activity_content_backup_20260911_did`) 후 그 블록만 안내 문구로 치환하고
   `meta.inquiry_did_withheld` 로 표시했다. 사후 검사 **잔여 0건**.

**깨끗한 것도 확인했다**(전수 검사이므로): 활동 유형·프로그램에서 온 `activity` 150건은 집계 서술만 담아
원문이 없고, 주제군 보고서 401건도 위 표대로 깨끗하다.

### 그리고 화면에서는 아예 빼기로 했다 (2026-09-11 사용자 결정)

사용자 판단: *"데이터에는 한 일과 관련된 부분을 남기지만 실제 프론트에서는 한 일은 표기하지 않는
방법으로 진행. 나머지 내용으로도 충분한 것으로 보임."*

**문턱으로 가르는 것은 경계가 흐리다** — 가린 쪽(≥0.7)과 남긴 쪽의 평균 겹침이 각각 높고 0.594라,
"이건 전재이고 저건 아니다"를 0.7 한 숫자가 정하고 있었다. 아예 내보내지 않으면 그 판정이 필요 없다.

**남는 재료로 충분하다 — 실측**: 탐구 34,180건 중 개념 **100%** · 방법 99.6% · 산출물 98.2% ·
진로 분야 97.8% · 연구 질문 79.3%이고, **셋 다 비어 화면이 빈칸이 되는 활동은 0건**이다.

| 어디 | 무엇 |
|---|---|
| 표 `inquiry_activity.did` | **남긴다** — 판정의 근거이고 재채점·검증의 재료다. `did_overlap` 도 남긴다(측정값) |
| 뷰 `inquiry_activity_public` | `did`·`did_withheld` 를 **주지 않는다** — 클라이언트가 어떤 경로로도 받을 수 없다 |
| 모달 · 씨앗 · 적재 SQL | "한 일" 구획 제거. 대신 연구 질문·방법·**산출물·다룬 개념**·확장 가능성으로 채운다 |
| 이미 적재된 `activity` 1,439건 | did 블록 제거 + 개념 줄 추가(백업 `activity_content_backup_20260911_did2`). 잔여 **0건** |

### ⚠️ 아직 남은 것 — `extension_hint`

같은 자로 재보니 **`extension_hint` 가 `did` 보다 겹침이 높다**: 평균 **0.743**(did 0.594),
표본 2,000건 중 **710건(35.5%)이 원문의 부분문자열 그대로**, ≥0.9 가 832건.

다만 **성격이 다르다** — 길이가 평균 35자이고 실제 값은 `행렬 연산의 활용 범위`·`치매 예방과 관련된
실생활 활용 방안` 같은 **주제구**다. 사용자가 지적한 PNI 사례(서술 6문장)와 달리 개인의 서사가 아니라
탐구 대상의 이름에 가깝고, 이 기능의 목적이 곧 "어떤 주제가 있었나"를 보여 주는 것이다.
반면 `잘못 분류한 사례도 함께 분석하면 성능을 더 높일 수 있으리라는 방향`(38자)처럼 학생의 성찰을
그대로 옮긴 것도 섞여 있다. **보유율이 6.3%(2,158건)** 라 빼도 화면 손실은 작다.

**판단을 미뤄 둔다** — 사용자가 "나머지 내용으로도 충분"이라 했을 때 이 값도 포함된 상태였으므로,
같은 문턱(≥0.7)을 걸지 여부는 별도 결정 사항이다. 걸려면 뷰의 `extension_hint` 를
`case when … then null` 로 감싸는 한 줄이다.

### 남은 것

`0.7` 이라는 문턱은 **뷰 정의와 적재 SQL 두 곳에** 적혀 있다. 한쪽만 바꾸면 화면은 가리는데 기록은
싣는(또는 그 반대) 상태가 **오류 없이** 만들어진다 — 값을 바꿀 일이 생기면 두 곳을 함께 볼 것.

3. **문헌으로 정리한 기전을 `result: cause_narrowed` 로** — 학생 자신의 결과·현상이 먼저 없는데 "원인을 좁혀 간" 것으로 인정

  ⑤구상·기획형은 result·criteria 강한 답 불성립 ⑥정형 문구는 문장 내용으로만 판정.

## 8-9. 판정을 지배하는 것은 활동의 내용이 아니라 **분절 단위**다 (2026-09-09 실측)

23학번 창체 판정(3,613건)이 끝나갈 무렵 **비탐구 48.5%** 로 나왔다. 24·25학번의 40.1% 보다 훨씬 높아
"졸업생 기록이 부실한가"를 의심했는데, **재 보니 데이터가 아니라 분절이 원인이었다.**

### 문장 수가 탐구 인정률을 3배 가른다

| 활동의 문장 수 | 2023 | 2024 | 2025 |
|---|---|---|---|
| 1문장 | 26.1% (1,319) | 31.9% (767) | 46.2% (316) |
| 2문장 | 48.4% (903) | 51.7% (937) | 67.1% (322) |
| 3문장 | 65.3% (675) | 59.8% (831) | 78.7% (328) |
| 4문장 이상 | 78.1% (963) | 77.8% (979) | 84.4% (441) |

(값 = 탐구로 인정된 비율, 괄호 = 활동 수)

**당연하지만 결과가 무겁다** — 근거 7항목과 사고 5문항을 한 문장에서 뽑을 수 없으니 짧은 활동은 구조적으로
비탐구가 된다. 그런데 **23학번은 1문장짜리 활동이 33.6%** 로 24·25학번(21.8%·22.5%)의 1.5배다.
문장 수를 고정하면 23·24학번은 사실상 같다(3문장 65.3 vs 59.8 — 오히려 23이 높다 · 4문장 이상 78.1 vs 77.8).
**23학번의 낮은 탐구율은 기록의 질이 아니라 분절의 잘게 쪼갬이다.**

### 그리고 25학번이 높은 것은 코호트가 아니라 **분절 모델**이다

| 문장 수 | motif | solar-pro3 | solar-pro4 |
|---|---|---|---|
| 1문장 | **42.5%** (353) | 26.5% (1,280) | 32.0% (769) |
| 2문장 | **60.2%** (364) | 50.2% (856) | 51.8% (942) |
| 3문장 | **80.4%** (337) | 64.2% (662) | 59.9% (835) |
| 4문장 이상 | **82.4%** (455) | 78.8% (942) | 78.0% (986) |

**motif 가 모든 버킷에서 높고 pro3·pro4 는 서로 비슷하다.** 그리고 motif 분절은 25학번에 몰려 있다
(1,260 / 1,407 = 90%). 즉 앞 표에서 25학번이 전 구간 +15~20%p 였던 것은 **그 학생들이 탐구를 잘해서가 아니라
그 기록이 motif 로 분절됐기 때문**이다. 같은 문장 수인데도 갈리므로 "문장을 많이 묶어서"가 아니라
**경계를 어디에 긋는가**가 다르다 — 한 활동에 속한 문장을 실제로 한 덩어리로 모으는 정확도의 차이다.

### 그래서 지금 하면 안 되는 것

1. **코호트 간 탐구 수준을 직접 비교하지 말 것.** 분절 모델이 섞여 있어 학생 집단의 차이로 읽으면 틀린다.
2. **주제군별 심화 비율(§8-8)도 이 교란을 받는다** — motif 비중이 높은 주제군이 실제보다 깊어 보인다.
   화면에 낼 때는 코호트·분절 모델 구성을 함께 밝히거나, **같은 분절 모델 안에서만** 견주어야 한다.
3. **판정 프롬프트를 이 숫자로 평가하지 말 것.** v2.2 의 과다·과소는 이미 같은 60건으로 고정 비교해 정했고,
   코호트별 비탐구율 차이는 프롬프트가 아니라 입력 단위가 만든 것이다.

### 근본 해결은 재분절이지만 지금은 하지 않는다

통일하려면 코퍼스 52,268 활동을 한 모델로 다시 분절해야 하는데, motif 는 이 저장소에서 **호출 경로가 없다**(§9-2).
즉 "가장 좋아 보이는 모델"로 통일하는 선택지가 지금은 없다. `solar-pro3`↔`pro4` 는 서로 비슷하므로 그 둘을
통일해도 얻는 것이 적다. **당분간은 교란을 기록해 두고 비교할 때마다 밝히는 편이 정직하다.**


## 8-10. 길이가 천장을 정하고 주제가 높이를 정한다 (2026-09-09, 창체 전량 10,080건)

§8-8 은 "깊이는 잴 것이 있는가로 갈린다"고 했는데, §8-9 에서 **분절 길이가 인정률을 3배 가른다**는 것이 드러나
그 결론이 길이 교란의 부산물일 가능성이 생겼다. 창체가 전량 판정된 지금(10,080건 · 리프 1,482) 다시 쟀다.

**먼저 상관을 보면 길이가 이긴다** — 리프의 심화 비율(L3+L4)과 `활동당 문장 수` 상관 **+0.629**,
`motif 분절 비중` +0.228. 깊은 주제군은 문장 3.0~3.6, 얕은 주제군은 2.1~2.8 이다.

**그런데 문장 수를 고정하면 주제 차이가 사라지지 않고 오히려 커진다**(각 리프에서 그 문장 수의 활동만 재계산,
10건 이상인 리프만):

| 활동의 문장 수 | 리프 수 | 심화 비율 중앙 | 10~90분위 폭 |
|---|---|---|---|
| 2문장 | 31 | 0% | **15%p** |
| 3문장 | 21 | 7% | **42%p** |
| 4문장 이상 | 41 | 36% | **64%p** |

**즉 길이는 천장이고 주제는 그 안의 높이다.** 짧으면 어떤 주제든 깊이가 안 나오고(2문장 중앙 0%),
길어질수록 주제에 따라 0%부터 73%까지 갈린다.

**같은 길이 안에서 갈리는 내용이 일관된다**(4문장 이상 기준):

| | 심화 | 주제군의 개념 |
|---|---|---|
| 상위 | 73% | 피부전도도 · ADHD · 뇌파 · 지각 |
| | 71% | 보건정책 · 국가간협력 · 해양생태계보전 |
| | 70% | 동적평형 · 정량분석 · 요오드적정 · 염화이온 |
| 하위 | 0% | 찬양축제 · 합창 · 연습일정조율 |
| | 0% | 화음 · 가창 · 음정 · 첼로연주 |
| | **0%** | **정밀의료 · 유전자편집 · 신약개발 · 분자구조분석** |

**마지막 줄이 결정적이다** — 길게 적혔고 개념도 첨단인데 심화가 0이다. 길이로도 주제의 화려함으로도 설명되지
않고, **학생이 잰 것이 없다**는 것으로만 설명된다. §8-8 의 결론이 길이 교란을 통과했다.

### 화면이 두 가지를 구분해야 한다

주제군 카드에 심화 비율만 내면 **"깊이가 없는 주제"와 "판단할 재료가 없는 주제"가 같은 0% 로 보인다.**
전자는 하지 말라는 정보이고 후자는 아무 정보도 아니다. 그래서 카드에는 **심화 비율과 함께 활동당 문장 수**를
낸다 — 문장 2 대에서의 0% 는 "이 주제로는 깊이 못 간다"가 아니라 "기록이 짧아 알 수 없다"이다.

같은 이유로 **주제군을 심화 비율만으로 정렬하지 말 것**. 길게 적히는 교과(과학 실험)가 위로, 짧게 적히는
영역(행사·공연)이 아래로 몰리는데 그것은 탐구의 깊이가 아니라 기록 관행의 차이다.


## 8-11. 이 기능이 쓸 그래프는 **창체 전용**이다 (2026-09-09 사용자 질문에서 갈라짐)

세특 판정을 기다리느라 E6 보고서가 막혀 있었는데, 사용자가 **"동시에 창체 데이터를 만들 수 없나"** 고 물어
막힘의 정체를 다시 봤다. 병목은 판정이 아니라 **그래프의 구성**이었다.

**창체는 코퍼스의 19.3% 뿐이다**(10,082 / 52,268 — 세특 61.4% · 세특진로 19.3%). 전량으로 Leiden 을 돌리면
리프가 세특 활동으로 채워지고 창체 활동은 그 사이에 흩어진다. 그래서 "판정 15건 이상 리프"가 1,482개 중
159개(11%)뿐이었고, 그 공백이 세특이라 보고서를 못 썼던 것이다.

**영역을 좁혀 다시 묶으니 모든 지표가 좋아졌다**(`build-graph.py --areas autonomy,club,career --out graph-club`):

| 지표 | 전체(52,268) | **창체 전용(10,082)** |
|---|---|---|
| 노드 · 엣지 | 74,877 · 251,101 | 15,137 · 30,634 |
| 리프 · 상위 | 1,482 · 38 | **438 · 21** |
| **잡탕 리프** | 22.0% | **4.5%** |
| cohesion_lift | 0.202 | **0.219** |
| 교과 순도 | 0.515 | **0.607** |
| 판정 커버리지 중앙 | — | **100%** |
| 고립률 | 3.3% | 8.2% |

**잡탕이 5배 준 것이 핵심이다** — 세특을 섞으면 창체 활동이 세특 개념에 끌려가 무관한 것끼리 묶인다.
고립률만 올라가는데(3.3% → 8.2%), 세특과만 이어져 있던 창체 활동이 홀로 남기 때문이라 **당연하고 감수할 값**이다.

**두 그래프를 모두 유지한다.** 창체 전용(`graph-club`)은 이 기능이 쓰고, 전체(`graph`)는 "이 개념을 세특에서도
다뤘다"는 교차 연결에 쓴다 — §6-1 국소 검색이 그 연결을 보여 줄 자리다. `--areas` 와 `--out` 이 짝이고,
`make-theme-inputs.mts` 도 `--graph` 로 어느 쪽을 읽을지 받는다(고정으로 두면 좁혀 만든 그래프가 있어도
전체 그래프의 주제군으로 보고서를 쓰게 된다).

**E6 보고서는 창체 전용 그래프 위에서 바로 돌았다** — 리프 438개 중 8건 이상인 363개가 대상이고
`solar-pro4 · --expect object`. 파일럿 3건 검토 결과 요약·확장 제안마다 활동 id 를 인용하고(근거 강제 규칙 작동),
`gaps` 가 입력의 근거 비율에서 유도된다(예: 성찰·개선 0.05 가 7항목 중 최저인 것을 정확히 짚었다).

### 9-1. 서브에이전트 경로의 실제 제약은 금액이 아니라 세션 한도다 (2026-09-07 실측)

배치 하나(활동 60건)에 **서브에이전트 토큰 28~30만** — 활동당 4.9K 로 API 직접 호출 추정(0.6K)의 **8배**다.
파일을 읽고 쓰는 왕복마다 컨텍스트가 다시 실리기 때문이고, 그래서 **12개를 동시에 띄우자 세션 한도(429)** 에 걸려
v2 판정 6개와 개념 유형 4개가 한꺼번에 죽었다. 창체 3영역 전량(5,174건 ≈ 86배치)은 이 경로로 25M 토큰이다.

**대응 = 단계마다 공급자를 나눈다.**

| 단계 | 공급자 | 근거 |
|---|---|---|
| 탐구 수준 판정(E1) | **Sonnet 서브에이전트** | 사용자 지시. 자기 일관성·감사로 품질을 측정한 유일한 경로. **Solar 는 재보고 기각**(아래) |
| 개념 유형 분류(E2-4) · 병합 판정(E2-3) · 주제군 보고서(E6) | **Solar(`solar-pro3`)** — `run-batches-api.mts` | 분류·요약이라 판정보다 가볍고, 프로젝트 공용 공급자다. Claude 한도를 쓰지 않는다 |

### 9-3. 판정도 Solar 로 한다 — 단 `solar-pro4` 다 (2026-09-07, 기각 → 번복)

처음엔 "Solar 로는 판정이 안 된다"고 기각했다. **모델을 잘못 골랐던 것이다.** 같은 180건·같은 프롬프트로 여섯 구성을 재니
`solar-pro3` 는 못 하고 `solar-pro4` 는 한다.

| 구성 | 커버리지 | 문장번호 조작 | 어휘 이탈 | 수준 분포 | usefulness 상관 |
|---|---|---|---|---|---|
| pro3 · 60건 | 34% | 37 | 31 | — | — |
| pro3 · 15건 | 87% | 21 | 113 | L2 에 62% | 0.469 |
| pro3 · 15건 · 엄격 스키마 | 82% | **119** | 0 | L2 에 76% | 0.272 |
| pro3 · 15건 · effort medium | 75% | 37 | 67 | 분산 | 0.399 |
| pro4 · 15건 | **100%** | **0** | 25 | 분산 | 0.526 |
| pro4 · 30건 · 엄격 스키마 | 84% | 0 | **0** | **L1 소멸** | 0.519 |
| **pro4 · 15건 · 느슨한 스키마** ★ | **100%** | **0** | **0** | 분산 | **0.588** |
| (참고) Opus · 60건 | 100% | 0 | 0 | 분산 | 0.549 |

**세 가지가 갈렸다.**

1. **배치 크기는 커버리지만 고친다** — pro3 를 60 → 15 로 줄이자 34% → 87%. 하지만 판정 자체는 그대로 나빴다.
2. **엄격 스키마는 근거를 지어내게 만든다** — 모든 근거 키를 요구하니 근거 없는 자리를 채운다. pro3 는 문장번호 조작이
   21 → **119** 로 늘었고, pro4 는 근거 폭이 부풀어 **L1 등급이 통째로 사라졌다**(48·0·75·16·12). 스키마는
   "형식을 지켜라"가 아니라 "빈칸을 채워라"로 작동한다.
3. **그래서 폐쇄 어휘만 강제한다**(`--loose-schema`, `strict:false`) — 어휘 이탈 25 → **0**, 커버리지·수준 분포는 그대로,
   `usefulness` 상관은 오히려 최고(0.588). 근거·사고 구조는 프롬프트와 코드 검증(`gradeResult`)에 맡긴다.

**품질 검증** (`pro4 · 15건 · 느슨한 스키마`):

| | 값 |
|---|---|
| 자기 일관성 — 수준 정확 / ±1 | **76.3% / 93.2%** (Sonnet v2.1 은 80.0% / 100%) |
| Opus 채점과 일치 — 수준 정확 / ±1 | **58.3% / 94.4%** |
| 불일치 방향 | 하향 23.9% · 상향 17.8% (계통 편향 없음) |
| 성격 차이 | Opus 보다 **탐구 인정은 짜고**(75.6% → 60.6%) **근거 항목은 후하다** |

**CLAUDE.md 의 경고가 맞았다** — "pro4 → pro3 교체 시 `pro3 는 미검증`, 배치 전에 한 학생으로 프로브할 것"
(`_harness.mjs` 주석). 그 프로브를 안 하고 pro3 로 판정을 돌렸다가 "Solar 는 못 한다"는 잘못된 결론을 냈다.
**모델을 바꿀 때는 과제마다 다시 재야 한다.**

**규모 문제가 풀렸다** — 창체 3영역 5,174건 = 345배치, 동시 3에서 약 2.7시간. Anthropic API 키 없이 진행한다.

`run-batches-api.mts` 는 **OpenAI 호환이면 무엇이든** 받는다(`--base-url`·`--key-env`·`--model`). Anthropic 키가 생기면
E1 도 이 러너로 옮기면 되고 배치 파일 형식은 그대로다.

**Solar 운용값(실측)**: 개념 유형 분류 배치 400건은 `finish_reason=length` 로 3회 전부 실패했다(추론 토큰이 예산을 먹는다 —
CLAUDE.md 의 "추론 모델은 추론과 출력이 같은 예산을 나눠 쓴다"). **120건 · `max_tokens` 32,000 · `reasoning_effort: none`**
에서 15초/배치로 안정됐다.

### 9-4. 규모를 키워도 판정이 흔들리지 않는다 (2026-09-08 전량 5,168건)

파일럿은 180건이었다. **표본이 30배가 되면 프롬프트가 무너지는가**를 봐야 하는데, 창체 3영역 전량
**5,168/5,170(99.96%)** 을 재니 파일럿과 거의 같은 모양이다. 6.1시간 · 429 **0건** · 실패는 `fetch failed` 29건(전부 재시도 성공).

| 수준 | 파일럿 180건 | 전량 5,168건 |
|---|---|---|
| L0 비탐구 | 39.4% | **40.1%** |
| L1 수행·보고 | 6.7% | 7.8% |
| L2 이해·적용 | 31.1% | **34.3%** |
| L3 분석·해석 | 16.7% | 11.5% |
| L4 설계·확장 | 6.1% | 6.2% |

**문장번호 조작은 9건 / 5,168건 = 0.17%** 다. 파일럿 0건이 표본이 작아서였는지 확인이 필요했는데, 규모를 키워도
사실상 0 이다 — `--loose-schema` + `pro4` 조합의 근거다(엄격 스키마의 pro3 는 같은 자리에서 119건이었다).
코드 검증이 잡은 나머지 = `strong 강등` 319(6.2%) · `근거 중복 상한` 84 · `근거 폐기` 68.
**끝내 판정되지 않은 활동은 2건**이다(모델이 두 배치에서 한 건씩 계속 빠뜨렸다 — 내용에 이상이 없어 원인은 모델 쪽이다).

**영역별로 다른 것은 판정이 아니라 탐구 발생률이다.** 자율활동은 비탐구가 54.8%인데 진로활동은 29.6%다(동아리 36.6%).
행사 참여·학급 운영이 자율활동에 몰려 있으니 당연한 결과다. 반대로 **탐구로 인정된 것 안에서의 수준 분포는 셋이 거의 같다**
(L4 비율 자율 11.1% · 진로 11.4% · 동아리 8.7%) — 특정 영역만 후하거나 짜게 매기는 편향은 없다.

**남은 편중은 `facts`(사실 사이의 관계) 한 문항이다** — 탐구 활동의 절반 가까이가 여기에 걸린다.
v2.2 에서 "관계의 내용(방향·기전)을 요구"로 좁혔는데도 여전히 가장 흔하다. 세특 문장이 원래 "A 때문에 B" 형태로 쓰이기
때문일 수 있고 판정이 후한 것일 수도 있어 **구분이 안 된 상태**다. 다음 감사에서 이 문항만 따로 볼 것.

### 9-5. 동시 호출은 8이 상한이다 — 늘리면 오히려 느려진다 (2026-09-10 실측)

"병렬로 더 많이 돌려도 된다"는 지시에 프로세스를 4개(동시 16)로 늘렸더니 **처리량이 2.7배 떨어졌다.**

| 동시 호출 | 429 | 처리량 |
|---|---|---|
| 8 (프로세스 2 × 동시 4) | **0건** | **216배치/시간** |
| 16 (프로세스 4 × 동시 4) | 14건 | 80배치/시간 |

**429 는 재시도 횟수가 아니라 대기의 문제다**(러너가 `retry-after`, 기본 45초를 지킨다). 한계를 넘으면
늘어난 병렬성이 전부 대기로 바뀌므로 **상한 근처에서 멈추는 것이 가장 빠르다.** 동시 8에서 배치 시간이
155초 → 94~124초로 오히려 짧아진 것도 같은 이유다(경합이 없다).

**프로세스를 늘릴 때는 `--only` 로 샤딩할 것** — 러너는 시작할 때 "결과 파일이 없는 배치"로 할 일을 정하므로,
같은 wave 에 두 인스턴스를 그냥 띄우면 **똑같은 목록을 둘이 나눠 갖지 않고 통째로 중복 실행한다**.
남은 목록을 반으로 잘라 뒤쪽을 `--only` 로 주면 겹치지 않는다(재시작 손실도 없다).

현재 판정 중인 5,174 활동과 맞먹는 양이 더 들어온다.

**그런데 양보다 중요한 것은 이 코호트가 유일하게 3년이 완결됐다는 점이다.** §6-2 경로 검색("이 다음엔?")은

심화 궤적을 실제로 보여 줄 수 있는 재료는 졸업생뿐이다.

**실행 방법은 이미 있다** — `node scripts/ontology-extraction/research/segment-missing.mjs --cohort 23`.
DB 현황을 매번 다시 보고 대상을 정하므로 **중단·재개가 안전**하고 이미 분절된 기록은 건드리지 않는다.
Solar 키를 쓰므로 Claude 한도와 무관하다. 규모는 219명 × 학년별 청크라 **수 시간~하루** 단위다.

**분절 뒤 이어지는 순서** (각 단계는 **증분**이라 앞의 것을 다시 하지 않는다):

```
① npx tsx scripts/inquiry-graphrag/build-corpus.mts          # 새 활동이 corpus.jsonl 에 붙는다
② npx tsx scripts/inquiry-graphrag/embed.mts --kind activities --via edge   # 이미 있는 id 는 건너뛴다
```

**③ 이 창체만이 아닌 이유** — `w2-seteuk` 배치는 23학번 분절 **이전** 코퍼스로 만들어졌다. 그래서 23학번은
창체·세특이 **전부** 새 활동이고, 창체만 골라 판정하면 그 학생의 세특이 통째로 비어 "3년이 완결된 코호트"라는
이 작업의 목적이 반만 채워진다. `--exclude-graded` 는 **쉼표 목록**을 받는다(플래그를 두 번 쓰면 뒤엣것만 남는다).

**⑥ 의 `--graded` 를 반드시 명시할 것** — 비우면 파일럿만 빠지고 세 wave 를 전부 읽는데, 세 wave 는 활동이
겹치지 않으므로 지금은 결과가 같다. 그래도 명시가 낫다(§5-5-2 의 사고가 "겹치지 않겠지"에서 시작했다).

**개인정보** 분절이 저장하는 것은 `sentence_ids`·`title`·`did`·`subject_matter` 이고 **사람 이름이 들어갈 자리가 없다**

`solar-pro4` 의 반복 붕괴다. **오류가 아니라 형식이 멀쩡한 JSON** 이라 그대로 저장되고, 코퍼스·임베딩·판정 비용이
통째로 부풀어도 눈에 띄지 않는다(활동 수가 많은 것이 "기록이 풍부하다"로 읽힌다).

**조치 = 적재 시 접는다** (`upload-segmentation.mjs`) — 같은 기록 안에서 `(제목, 문장 번호)`가 같으면 같은 활동이다.
00-00001 실측: 리포트 336 → **128**, 기록 57건 전부 유지·빈 기록 0(잘림으로 인한 손실이 아니라는 뜻).

`student_segmentation_backup_20260908`(18행) 에 있다. 제목은 같은데 문장 번호가 다른 20건은 **건드리지 않았다** —
같은 활동이라는 증거가 없다.

**교훈: 전량 실행 전에 2명을 먼저 돌릴 것.** 219명을 그냥 돌렸으면 부풀려진 분절이 코퍼스에 섞이고,
그 위에 임베딩·판정을 쌓은 뒤에야 드러났을 것이다.

### 12-3. 동시 실행은 2개까지 — 죽는 이유가 내 프로세스가 아니다 (2026-09-08)

세특 판정 1 + 23학번 분절 2갈래를 함께 돌렸더니 **셋 다 시스템 메모리 부족으로 중단**됐다.
그런데 그때 재 보니 **node 17개가 합쳐 1.39GB** 뿐이었고 큰 소비자는 Memory Compression 4.3GB · 브라우저 ·
다른 Claude 세션이었다. 즉 **내 작업이 메모리를 먹어서가 아니라, 공용 기기의 여유가 얇을 때 배경 작업이
먼저 희생된다.** 여유가 10.5GB 일 때 셋을 띄웠고 6.1GB 에서 잘렸다.

**대응은 최적화가 아니라 개수 제한이다** — 동시 2개, 기기가 바쁘면 1개. 그리고 **모든 러너가 재개 가능해야
이 제약이 비용이 아니게 된다**: 판정 러너는 결과 파일이 있는 배치를 건너뛰고, 분절 러너는 매 학생마다 DB 를
다시 보고 대상을 정한다. 실제로 세 번 잘렸는데 **잃은 작업은 진행 중이던 학생·배치뿐**이었다.

**중단 시점의 진행률을 로그가 아니라 DB 로 확인할 것** — 두 갈래가 각각 86/109·91/108 을 지나 있었고
(예상보다 훨씬 많았다) DB 로 세니 191명·10,858행이었다. 로그만 보고 "처음부터 다시"를 택했으면 하루를 버린다.

**⚠️ "중단됨" 보고를 그대로 믿지 말 것 (2026-09-09)** — 하네스가 세 작업을 메모리 부족으로 중단했다고 알렸는데,
**세특 판정의 node 프로세스는 계속 돌고 있었다**(래퍼만 종료된 것으로 보인다). 중단됐다고 믿고 156/1,543 에서
재시작했으면 이미 끝난 589배치를 다시 돌렸을 것이다 — 실제로는 745까지 가 있었다.

**확인 순서는 ①산출물 개수 ②로그 파일의 mtime ③프로세스 목록**이다.
`Get-CimInstance Win32_Process -Filter "Name='node.exe'"` 의 `CommandLine` 으로 어느 작업인지 가른다.
로그의 마지막 줄만 보면 "멈춘 것"과 "긴 배치가 진행 중인 것"을 구분할 수 없다(배치 하나가 200초다).
