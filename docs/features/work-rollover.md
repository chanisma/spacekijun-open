## 1. 템플릿은 지난 업무 자체다

템플릿 표를 따로 두지 않는다(두 번째 사본이 낡는다). 가져온 업무·할 일에 **계보**를 남긴다.

```jsonc
// work.meta
"rolledOverFrom": { "workId": "<원본 업무>", "year": 2025, "name": "2025년 정보공시" }
// task.meta
"rolledOverFrom": { "workId": "<원본 업무>", "taskId": "<원본 할 일>" }
```

- 업무 상세 머리글이 `원본 ○○` 을 보여 준다 — 가져오지 않은 첨부 파일을 거기서 찾는다.
- **중복 방지**는 이 계보로 한다: 같은 원본을 같은 해로 이미 가져왔으면 [가져오기]가 막힌다
  (`findExistingRollover` — 이름으로 판정하지 않는다, 사람이 이름을 바꾸므로).
- 할 일 계보는 저장 단계에서 **원본 할 일 → 새 할 일 id 대응**을 되찾는 데도 쓴다
  (일괄 INSERT 의 반환 순서에 기대지 않는다).

## 2. `meta` 규칙표 — 목록에 없으면 버린다

`TASK_META_ROLLOVER_POLICY` / `WORK_META_ROLLOVER_POLICY`.

| 할 일 키 | 규칙 | 이유 |
|---|---|---|
| `units` | 유지 | 과제 단위 **정의** |
| `submission` | 유지 | 제출 설정(단 `actionId` 는 재연결 — §4) |
| `deadlines` | 날짜 이동 | 다중 마감 회차 전부 |
| `visibleFrom` | 날짜 이동 | 담당자에게 보이는 날(2026-10-05 — 업무 «대기»를 대신한다). 마감처럼 1년 옮긴다 |
| `assignees` | 재구성 | 재직자만, 상태는 전원 `pending` |
| `unitProgress`·`deadlineProgress` | 버림 | 작년 진척 — 따라오면 **만들자마자 완료** |
| `assignmentIssues` | 버림 | 작년의 '담당자 아님' 표시 |
| `documentAnalysis*`·`files` | 버림 | 출처·첨부 |

**모르는 키는 버리고 보고한다**(`unknownKeys`). 반대 선택(모르는 키를 살림)은 새로 생긴 진척
기록이 조용히 따라오는 사고가 되고, 그건 오류를 내지 않는다. 그 대가로 **새 설정 키를 만들면
여기 `keep` 으로 적어야** 가져오기에 실린다 — 회귀가 `src/types/tasks.ts` 의 `Task.meta` 키 전부와
라이브 실측 키 전부가 분류돼 있는지 정적으로 검사한다.

업무 쪽: `department` 유지, `year`·`managers` 재구성, `files`·`documentAnalysisId` 버림.

## 3. 날짜 — 월·일 그대로 N년

- `shiftDateKey`: 연도만 더한다. 평년의 2월 29일은 28일로.
- **주말 표시**: 요일은 해마다 1~2일 밀린다. 라이브 드라이런에서 84건 중 **18건(21%)** 이 주말 —
  미리보기가 앰버 칩으로 표시하고, 자동 보정은 하지 않는다(당길지 밀지는 업무마다 다르다).
  학사력 역산은 로드맵 §5-1.
- 다중 마감이면 `due_date` = **새 회차 기준 다음 마감**(`effectiveFromDeadlines`).
- 저장은 `YYYY-MM-DD` 문자열(할 일 편집과 같은 경로 — DB 가 서버 타임존 자정으로 캐스팅).

## 4. 실행(Action) 옮기기와 값 제출 재연결

- 원본 할 일의 실행 중 **내가 볼 수 있고**(RLS — 비공개 문서 생성 실행은 안 보인다)
  **레지스트리에 있는 것**만 옮긴다. `created_by` = 가져오는 사람(RLS `task_action_insert_own`).
- `config`(기본 양식 `defaultTemplate` 등)는 그대로 복사한다. 실행 **이력(RUN)** 은 옮기지 않는다.
- (할 일, 유형) 유니크 키가 생성자를 포함하므로 여러 사람이 단 같은 유형은 **하나로 접힌다**.
- **값 제출의 `submission.actionId` 는 원본 할 일의 실행을 가리킨다** — 그대로 두면 새 할 일이
  작년 실행을 쓴다. 새 실행 id 로 다시 잇고(`remapSubmissionAction`), 옮기지 못한 실행(남의 비공개
  실행)은 **연결을 끊는다** — 양식 사본 `submission.template` 은 남으므로 매니저가 업무 편집에서
  다시 고르면 되고, 완료 토스트가 그 건수를 알린다.

## 5. 쓰기와 되돌리기

순서 = 업무 → 할 일(일괄) → 실행(일괄) → `actionId` 재연결. 중간 실패 시 **업무를 지운다** —
`task.event_id`·`task_action.task_id` 가 ON DELETE CASCADE 라 한 번에 사라진다(반쯤 만든 업무가
남으면 사람이 그걸 "가져온 것"으로 믿는다). 지우기도 실패하면 오류 문구가 직접 지우라고 말한다.

매니저는 선택기가 id 만 주므로 **저장 직전에 `resource`(status='active')로 이름·재직을 다시 확인**한다.

**알림은 나가지 않는다** — `task`·`work`·`task_action` 에 알림 트리거가 없다(2026-09-23 확인).
할 일이 15개인 업무를 가져와도 담당자에게 알림 폭탄이 가지 않는다.

라이브 RLS 검증(2026-09-23, 실교사 JWT, 롤백): 업무 INSERT · 할 일 INSERT(제출 설정 트리거
`guard_task_submission_config` 통과) · 실행 INSERT · `actionId` UPDATE 1행 · 업무 DELETE 후 할 일 0건.

## 6. 함께 고친 것 — "다른 업무에서 복사"

업무 만들기 창의 기존 복사 기능이 `meta: task.meta` 를 **통째로** 복사해 원본의 단위·회차 완료
기록·'담당자 아님'·원본 실행 연결이 새 할 일에 따라왔다(라이브 기준 해당 할 일 63건).
같은 규칙표의 `sanitizeTaskMetaForCopy` 로 바꿨다 — 이 경로는 날짜를 옮기지 않는다(원래 동작 유지).
**2026-11-12 이 경로를 없앴다** — «참고해서 시작»의 `reference` 모드가 대신한다(`sanitizeTaskMetaForCopy` 삭제).

## 7. 하지 않은 것

- 첨부 파일 복사 · 업무 흐름 캔버스 배치 · 실행 이력 · 학사력 역산 — 이유는 로드맵 §6.
- 연도 추론은 `meta.year` → 이름의 `YYYY년`/`YYYY학년도` → 생성일. 라이브 30건 중 `meta.year` 없는
  것이 6건이라 이름 경로가 실제로 쓰인다. 이름 교체는 **`년`·`학년도` 앞의 원본 연도만** 바꾼다
  (`2학년`·`1차` 는 그대로). 드라이런 30/30 교체 성공.

## 인계 노트 (2026-09-24)

가져오기가 옮기는 것은 **절차**(할 일·날짜·담당자·실행)인데, 인계에 정작 필요한 것은 **겪은 것**이다 — "공시 자료등록 메뉴는 3월에만 열린다" 같은 것. 그래서 할 일 상세에 「인계 노트」 칸을 두고 **규칙표에서 `handoverNote: 'keep'`** 으로 내년까지 따라가게 했다.

- **저장은 `task.meta.handoverNote` 한 칸**이다. 표를 따로 두지 않은 이유: 이 값의 수명이 할 일과 정확히 같고, 무엇보다 **표로 두면 가져오기 규칙표에 걸리지 않아 내년에 조용히 사라진다**(이 값의 존재 이유가 «따라가는 것»인데).
- `description` 과 칸을 나눈 이유: 설명은 «무엇을 하는 일인가», 노트는 «작년에 뭐가 문제였나». 한 칸에 섞으면 해마다 설명이 길어지다가 아무도 안 읽는다.
- **빈 값은 키를 지운다**(`null`). 빈 문자열로 남기면 «노트가 있다» 판정이 참이 되고 빈 껍데기가 내년까지 따라간다.
- 단일 출처 = `src/lib/handoverNote.ts`, 회귀 = `npx tsx scripts/handover-note-test/run.mts`(19건 — 규칙표 분류가 빠지면 **오류 없이** 사라지고 1년 뒤에야 드러나므로 정적 검사가 방어선이다).
