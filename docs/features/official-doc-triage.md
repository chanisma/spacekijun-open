## 흐름

1. 서버 PC(Linux) 매일 07:50 openclaw cron → `~/.config/winvm/digest.sh`
   → Windows VM 안에서 `klef-daily-digest.js`(인증서 로그인·대장·본문) → 결과 .json 을 서버 PC 로.
2. NEIS_helper `scripts/klef-doc-triage.py` — 엣지 `official-doc-ingest` `knowledge` 로 지식 묶음을 받고,
   문서마다 관련 후보만 골라(글자 2-gram) haiku 에 `--json-schema` 로 판정 → `ingest` 로 원장 + 판정 업로드.
3. 웹 공문 판단함 — 판단 대기 / 처리 필요 / 결정됨 / 전체. 행을 펼쳐 **[결정하기]**.
4. 결정 창(2단계) — 초안은 AI 판정에서(`src/lib/officialDocDecision.ts` `initialDraft`):
   - **기존 업무에 할 일 추가**(공문 한 건 = 할 일 하나, 기한·담당 포함) · **새 업무 만들기**(업무 + 첫 할 일, 저장은 후보 경로 `createWorkFromCandidate`)
     · 후보가 있으면 «후보의 절차로 자세히 만들기» = 결정 창을 닫고 `CandidateWorkDialog`(`onCreated`·`extraWorkMeta`)를 연 뒤 결정을 잇는다(모달을 겹치지 않는다)
   - **다른 사람 일** · **참고만** · **무시**
   - 판단 이유 + **규칙으로 남기기**(발신 포함 + 제목 낱말 모두 포함 → 결정·업무·담당, 바로 `active`). 규칙 목록·끄기 = 머리글 [규칙]
   - 저장 순서 = 할 일/업무 → 결정 행 → 규칙. 결정 행이 실패하면 만든 할 일·업무를 지운다(`saveDecision`)
   - 출처 = 업무·할 일 meta `fromOfficialDoc {doc_no, title, at}` — 연간 가져오기는 버린다(`workRollover.ts` drop)
5. 머리글 «AI 일치 x/y» = 사람이 결정한 공문 중 AI 1순위(할 일 여부·업무 후보)가 맞은 비율(`agreesWithTriage`).
   결정·규칙은 다음 회차 판정의 지식 묶음(`decisions` 300 · `rules`)으로 서버 PC 에 간다.

## 3단계 — 에이전트·데스크·규칙 적중 (마이그레이션 `20261030190000_mcp_official_doc_tools.sql`)

- MCP 허용 **`official.doc`** — 교사 기본 꺼짐, **관리자에게만 사람별 허용**(시드). 도구 `list_official_docs`·`get_official_doc`·`decide_official_doc`.
  할 일·업무는 기존 도구(`create_task`·`create_work`)로 먼저 만들고 그 id 를 `decide_official_doc` 에 넘긴다 — 공문 도구는 할 일을 만들지 않는다(쓰기 경로 하나).
  결정 행은 `via='mcp'`. `rule` 을 주면 같은 모양의 규칙이 바로 active.
- 규칙 적중 셈 — 트리거 `official_doc_decision_rule_hits`: 결정이 남을 때 그 공문에 맞는(`official_doc_private.rule_matches` — 발신 포함 + 제목 낱말 모두, 공백·대소문자 무시) active 규칙마다
  같은 결정이면 `hits`, 다르면 `overturned` +1. 그 결정에서 태어난 규칙은 세지 않는다. 웹 [규칙] 목록이 «적중 · 뒤집힘»을 보인다(뒤집힘이 많으면 빨강).
- 데스크(NEIS_helper) 홈 카드 «공문 판단함» — 판단 대기·처리 필요·3일 안 기한 + 처리 필요 앞 3건, «판단함 열기»(`/tasks/docs`) · «에이전트와 판단»(켜 둔 에이전트 입력칸에 위 도구로 함께 판단하자는 말, 보내지 않음).
  카드 자료는 `official_doc` 를 그대로 읽어 RLS 가 관리자만 — 다른 사람에게는 카드가 없다.

## 스키마 (마이그레이션 `20261030170000_official_doc_triage.sql`)

| 표 | 내용 | 쓰기 |
|---|---|---|
| **official_doc** | 문서번호(유일)·등록일시·제목·발신·결재권자(= 실제 접수 담당)·처리상태·본문(앞부분)·`body_status`(stored/private/none/failed) | RPC `official_doc_ingest`(service_role ← 엣지, 실행기 키) |
| **official_doc_triage** | 판정 이력 — 요약 칸(nature·needs_action·deadline·confidence·question) + `result` 원본. `(doc_id, result_hash)` 유일 = 같은 판정 재삽입 없음 | 같은 RPC |
| **official_doc_decision** | 사람의 결정 이력(마지막 행이 현재) — ignore/info/link_work/link_task/create_work/reassign | 관리자 INSERT 만(`decided_by = auth.uid()`), 고치기·지우기 없음 |
| **doc_rule** | 결정에서 나온 규칙·용어(proposed → active 만 판정에 쓰임) | 관리자 |

- 지식 묶음 RPC `official_doc_knowledge` = 업무 후보(`work_candidate` kind=work, 접수 근거 제목 6개) · 올해 활성 업무 · 분장 자리 + 현재 담당 · active 규칙 · 최근 결정 300 · 최근 60일 LLM 판정이 있는 문서번호(`known` — 다시 판정하지 않는다).
- 실행기 키 = 자동화 업무 `automation_runner` 와 같은 키(같은 서버 PC). 엣지는 sha256 만 넘긴다.

## 목록 받기 — 접수 기간·최신 판정만 (2026-11-04, 마이그레이션 `20261104140000_list_official_docs.sql`)

- **2026-11-13 속도 — 가벼운 목록 `p_slim` + RLS 한 번 평가**(마이그레이션 `20261113110000_official_doc_list_speed.sql`, 운영 적용). 사용자 «한번에 너무 많은 문서가 로드되는 듯». 관리자 30일 치 444건이 RPC 계산 ≈5초 + 1.53M자였다.
  - 원인 ① RLS — 공문 «owner read» `official_doc_is_mine(approver_name)` 이 행마다 ≈1ms(관리자도 OR 앞 항이라 먼저), «admin read» `is_admin()` 도 행마다, 판정·결정 «owner read» 는 행마다 공문 표(그 정책 포함)를 다시 봤다. → admin read 셋 = `(select is_admin())`, 공문 owner read = `btrim(approver_name) = any((select official_doc_my_names())::text[])`(이름 배열을 문장당 한 번). ⚠️ `= any((select f()))` 는 «서브쿼리 행»으로 읽혀 `text = text[]` 오류 — `::text[]` 캐스트가 스칼라 서브쿼리로 만든다. `official_doc_is_mine` 은 결정 insert 정책 등이 그대로 쓴다. 드라이런: 보이는 공문·판정·결정 수 전후 동일(관리자 444·1448·2, 담당 교사 52·180·0), 관리자 5,376 → 136ms · 교사 2,635 → 35ms.
  - 원인 ② 양 — 판단함은 `p_slim: true` 로 받는다: `meta = null`, 판정 `result` 는 목록 행·필터·정렬·정확도·결정 기본값이 쓰는 칸만(`work_candidates` 는 id·name·score), `question` 뺌, 행에 `slim: true`. 1.53M → 0.58M자. **펼친 행·결정 창**은 `getOfficialDocDetail(id)`(meta + 최신 판정 전체, 표 직접 읽기 — RLS 그대로)로 채운다(`useOfficialDocFull` · `openDecision` 이 `fetchQuery`). 업무노트(`mine`)는 종전 모양.
  - ⚠️ 목록 판정(`officialDocInbox.ts`·`officialDocDecision.ts`)이 판정 원본의 새 칸을 읽기 시작하면 가벼운 목록의 칸 목록에도 넣을 것 — 빠지면 오류 없이 필터·건수가 틀린다(회귀 `official-doc-test` ③ 이 대조).
- **2026-11-12 `p_mine`**(마이그레이션 `20261112120000_list_official_docs_mine.sql`, 운영 적용) — `true` 면 «결재권자 이름 = 내 이름(명단 연결 교직원) · 결정 없음»만(total·pending_outside 도 같은 범위). 업무노트 «공문 제안»이 쓴다 — 관리자 60일 치 424건·1.4 MB·6.6초 → 17건·52 KB·1.1초. 넘기지 않으면 종전과 같다(판단함). 인자를 더해 DROP + CREATE.
- 화면은 RPC **`list_official_docs(p_from, p_to, p_limit)`**(INVOKER — RLS 그대로) 하나로 받는다: 접수 등록일 기간(한국 날짜, 양끝 포함, null = 끝 없음) 안 공문을 최신순으로, **본문 없이**, 최신 판정·결정 1건씩. 본문은 행을 펼칠 때 `getOfficialDocBody(id)`.

## 함정

- 받는(접수) 공문엔 학생 개인정보가 들지 않는다 — 개인정보 정규식으로 본문을 거르지 않는다(2026-10-30 사용자 결정, odt-2). 생산(기안) 공문은 주의가 필요하지만 정규식으로 가를 수 없어 다루지 않는다. `private` 은 odt-1 시절 값이 남은 것.
- 의무 여부도 정규식(제목 낱말 → 의무/선택)으로 매기지 않는다 — «제출·실시»라도 희망·해당 학교만인 경우가 많다. haiku 가 본문의 대상·조건으로 `result.obligation`(의무 / 해당 시 / 선택 / 없음) + `obligation_why`(근거 문장)를 낸다. 긴급은 제목 꼬리표에 적힌 경우만. 판단함은 제목 줄 칩과 펼친 칸 «의무 여부»로 보인다.
- ⚠️ haiku 는 빈 임시 폴더에서 `--setting-sources ''` · 도구 금지로 부른다 — 폴더의 안내 파일을 따라가 글로 답하는 일을 막는다(데스크 2026-10-30 실측).
- 본문은 digest 가 자른 앞부분(1,500자)만 저장된다.
- ⚠️ 이미 판정한 문서는 다시 판정하지 않는다(`known`) — 규칙을 새로 만들어도 지난 공문의 판정은 그대로다(다음 공문부터).
- 할 일을 만들면 담당자에게 보통의 할 일 배정과 같은 효과가 난다 — 결정 창이 «정해지면 그 사람에게 할 일이 배정됩니다»라고 말한다.
- 1차 실측(2026-10-30, 10/27~10/30 접수 113건): 업무 80 · 기회 18 · 지침 7 · 홍보 6 · 무관 2, 업무 후보 제시 96, 질문 113, 평균 확신 0.63, 개인정보 의심 11, 6분 40초(4병렬).
- 2차(odt-2, 같은 113건 재판정 `--rejudge`): 업무 60 · 기회 32 · 홍보 11 · 지침 8 · 무관 2, 할 일 있음 85→52, 의무 26 · 해당 시 38 · 선택 40 · 없음 9, 본문 110(열람 불가 3), 8분 25초.

## 성격 2판 (odt-3, 2026-10-30 사용자 결정, 마이그레이션 `20261030210000_official_doc_nature_v2.sql`)
- «업무» 하나에 안내·요청·계획이 섞여 넓었다 → 목적별 9종: **제출**(자료·현황·의견·보고·회신) · **추천**(표창·위원·대상자) · **설문**(조사·만족도 응답) · **참석**(회의·연수·행사에 사람을 보냄) · **실시**(학교가 운영·시행·점검·게시) · **지침** · **기회** · **홍보** · **무관**. «업무»는 1판 이력에만 남는다(CHECK 은 받되 결정 창·MCP 는 안 쓴다).
