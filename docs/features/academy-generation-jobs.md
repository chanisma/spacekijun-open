# 단계별 탐구 생성과 서버 작업 큐 (2026-09-14)

## 사용자 동작

Academy 새 별 찾기의 기본 모델은 GPT-6 Luna(`gpt-6-luna`)다. 관리자에게만 루나/Solar Pro 4 선택이 표시되며 작업 접수 RPC에서도 실제 관리자 역할을 검사한다. 교수와 설계 대화도 선택한 모델을 사용한다. 일반 탐구설계 화면의 기본값도 루나이며 모델 선택 UI는 관리자에게 표시한다.

생성은 자료 접수 → 탐구 내용 작성 → KG 연결 → 검증/초안 보관으로 진행한다. AI 호출은 내용 작성/연결의 두 단계이며 각 단계가 별도 스키마를 사용한다. 두 공급자의 시스템 지시와 데이터, 단계 스키마는 동일하다. 루나는 medium, Solar는 low, 단계별 토큰 한도는 12,000으로 설정했다. Solar 사용자 메시지에 전체 JSON 스키마를 중복 삽입하던 방식을 제거했다.

Academy에서는 접수가 완료되면 창을 닫거나 다른 장소로 이동해도 서버에서 처리한다. 연구대로 돌아와 진행 상태와 완성된 설계도를 확인한다.

**의뢰 현황의 자리 (2026-09-14 사용자 지시)**: 종전엔 패널 **맨 아래**에 의뢰마다 단계 목록·경과·설명문·먼저 완성된 내용까지 펼친 카드가 쌓였고 **연구 수첩에서도** 떴다. 지금은 **연구대 오른쪽 작성란 밑에만** 놓이며(`GenerationBrief`, `GameObservatory` 의 design 뷰 `<section>` 끝) 의뢰당 **한 행** — 표시 · 제목 · 단계와 상태와 경과 · 동작 하나(설계도 펼치기 / 멈춘 단계부터 다시 시도). 상세 단계는 하단 대기 화면(`ResearchProgress`)이 이미 맡고 있어 되풀이하지 않는다. 행은 3열 grid 라 동작 버튼이 제 칸(3열, 2행 걸침)을 갖고 작성란의 확정·되돌리기 버튼과 섞이지 않는다. 보일 의뢰가 없으면 아무것도 그리지 않는다. **2차(같은 날)**: 작성란 밑이 아니라 **연구대 오른쪽 아래 오버레이**(`deskWorkspace` 안 `position:absolute`, 설계지 위 z-index 45)로 옮겼고 머리글 클릭으로 접힌다(접으면 제목 + 진행/멈춤 건수 한 줄). 하단 대기 화면(`localBusy`)이 뜰 때는 숨겨 겹치지 않는다. 의뢰에서 펼친 설계도는 **접을 수 있다** — 의뢰 행의 버튼이 펼침 상태에서 [설계도 접기]로 바뀌고 작성란에도 [설계도 접기 · 나중에 다시 펼치기]가 있다(`closeGeneration`: 초안은 그대로라 행의 [펼치기]로 다시 열린다. 종전의 [다른 방향으로 다시 생각하기]와 결과 상태는 같지만 뜻이 달라 따로 둔다). 회귀 = `npx tsx scripts/inquiry-new-node-placement-test/run.mts` §9(정적 검사). 연결이 실패해도 먼저 만든 탐구 내용을 펼쳐 읽을 수 있고 실패한 단계부터 재시도한다. 자동 보관은 draft이며, 본인이 이유를 적어 확정하는 흐름과 챕터 완료/50코인 보상은 유지한다.

일반 inquiry-design의 기존 분석 API도 두 단계 생성 함수를 공유한다. 다만 해당 화면은 기존 동기 요청/초안 저장 흐름을 유지한다. 창 종료 후 자동 진행/복구는 이번 Academy 작업 큐 경로에 적용했다.

## 탐구 설계도 같은 큐를 쓴다 (2026-09-18)

위 문단의 "별도 범위"였던 숙제를 마쳤다. `/inquiry-design` 의 «설계하기» 도 이 큐로 간다 — 상세는 `docs/features/inquiry-design.md` §«설계를 서버 작업 큐로».

**워커·claim/checkpoint RPC·cron·표를 전부 공유하고 접수 RPC 만 다르다.** 워커는 이미 완전히 범용이었다(`job.student_id`·`job.provider` 만 보고, 완료 시 `experience=false` 면 `student_inquiry_designs` 에 draft 를 넣는다 = 탐구 설계의 자동 초안과 같은 자리·같은 모양). `academy_generation_start` 는 학생 범위를 호출자에게서 강제로 유도하므로(학생=이메일 prefix, 교직원=고정 체험 학생) 교사가 임의 학생을 고르는 화면을 표현할 수 없어, `inquiry_generation_start` 를 따로 두고 `inquiry_design_can_access_student()` 로 판정한다.

**⚠️ `surface` 컬럼이 두 기능을 가른다. 빠뜨린 곳에서 조용히 섞인다.** 이 함수의 «계정당 활성 작업 1개» 규칙은 *활성 작업이 있으면 그 행을 그대로 돌려주는* 방식이라, surface 를 안 걸면 교사가 탐구 설계 의뢰를 낸 동안 연구대에서 새 의뢰를 눌렀을 때 **탐구 설계 작업이 돌아온다**(오류가 아니라 "낯선 설계도가 열림"). 그래서 ①`academy_generation_start` 의 활성 조회·일일 한도 ②`readGenerations()` 조회 ③탐구 설계 쪽 조회 세 곳 모두에 건다. 작업 행 타입도 한 벌로 합쳤다(`InquiryGenerationJob`, academy 쪽은 별칭 유지). 회귀 = `npx tsx scripts/inquiry-prior-design-test/run.mts` §12.

탐구 설계 쪽만 다른 것: 활성 제한·잠금이 **(계정, 학생)** 단위이고(교사는 여러 학생의 설계를 나란히 맡는다), 하루 한도 20 은 **학생 기준**이며, 근거 상한이 40(그래프에서 직접 고르는 화면이라 20 보다 여유를 둔다)이다.

## 저장/재시도

- `academy_generation_jobs`가 영속 DB 작업 큐다. owner_id + request_key 고유 키와 계정별 접수 잠금으로 중복 클릭/응답 유실을 처리한다. 한 계정에 동시에 활성 작업 하나, 한국 날짜 기준 하루 신규 의뢰 20개다.
- 사용자는 본인 작업만 조회하며 상태/결과를 직접 수정할 수 없다. 서버가 입력의 학생 범위와 KG 버전 소유권을 검사한다. 학생은 자신의 학생 데이터, 교사/관리자는 00-00001 읽기 자료와 본인 체험 저장소를 사용한다.
- 단계마다 최대 자동 시도 3회, 실패한 작업의 수동 재개는 최대 3회다. 재개는 새 의뢰/초안/챕터 보상을 만들지 않는다. HTTP 400/401 및 설정 오류는 무조건 파라미터를 삭제해 재호출하지 않고 중단한다.
- 작업자는 150초 lease와 고유 토큰으로 처리권을 확보한다. AI 요청 제한은 110초다. 만료/교체된 토큰의 늦은 응답은 저장하지 않는다. 중단된 작업은 15초 주기 cron이 재개한다.
- 각 단계 결과와 usage는 체크포인트에 저장한다. 설계 작성 성공 후 연결 실패 시 설계를 재생성하지 않는다. 저장 실패 시 save 단계만 재실행한다.
- 최종 초안 삽입과 completed 전이는 한 DB 트랜잭션이다. 같은 완료를 다시 전달해도 초안은 하나다. 학생은 기존 student_inquiry_designs, 직원 체험은 academy_experience_records에 저장한다.
- 기존 학생 KG의 ID는 작업자가 검증된 버전에서 읽는다. 그래프를 저장하기 전에 스키마, 중복 노드, 기존 ID, 관계 끝점, planned Activity를 검증한다. 기존 시간 방향/출처 주입/새 Thread 방지 규칙을 공통 모듈로 옮겼다.

## 작업자 인증과 운영

`academy-generation-worker`는 DB가 보내는 전용 임의 비밀값으로 인증하며 일반 무인증 요청은 401이다. JWT gateway 검증은 이 함수에서만 끄고 함수 내부 인증을 사용한다. 비밀값은 academy_private.generation_worker_config에 생성하며 코드/클라이언트/로그에 출력하지 않는다. service_role만 비밀값 조회·claim·checkpoint RPC를 사용할 수 있다. 사용자 JWT를 작업 DB에 보관하지 않는다.

`pg_net`이 접수/체크포인트 후 즉시 작업자를 깨우고 `pg_cron`이 15초마다 누락/만료 작업을 다시 깨운다. 다른 Supabase 환경으로 배포할 때 private config의 url을 해당 프로젝트의 함수 URL로 맞춘다. 이력에는 단계·시도·공급자·시간·오류 분류를 기록하고 질문/생성 본문은 성능 로그에 출력하지 않는다.

## 배포/검증

- `20260914140000_academy_generation_jobs.sql` 연결 DB 적용, migration history 등록 완료.
- academy-generation-worker, openai-proxy 배포 완료. DB에서 인증된 pg_net 호출에 HTTP 202, 무인증 호출에 401 확인. cron 활성/15초 주기 확인.
- SQL 통합 검사: 모델 권한, 계정 분리, 중복 접수, 유효하지 않은 처리 토큰, 연결 단계 재시도, 초안 1회 저장, 학생/체험 저장 경로 통과. 테스트 레코드는 롤백.
- Node 테스트 36개, Edge Deno 검사, 변경된 프론트엔드 lint 통과.
- 브라우저: 앱 문서가 없는 동안 서버 fixture가 완료된 후 복구, 관리자 Solar 선택, 실패한 연결 단계 재개, 프롤로그 및 제1~4장 회귀 통과.
- Vite 프로덕션 빌드 통과. 전체 tsc에는 기존 프로젝트 오류가 남아 있으며 변경된 프론트엔드 파일에서는 오류가 검출되지 않았다.
- 실제 공급자 결과 품질/속도 비교는 수행하지 않았다. 브라우저의 AI 데이터는 fixture다. 일반 탐구설계 화면의 창 종료 복구는 별도 범위다.

## 그래프 단계의 활동은 하나 (2026-10-03)

Solar 가 실행 계획의 단계마다 Activity 를 그려 한 설계에 활동 노드가 5개 생겼다(라이브 실측). 프롬프트(«새 Activity 는 정확히 하나, label = 설계 title»)와 코드 가드 `collapsePlannedEntities`(설계 제목과 가장 비슷한 활동 하나로 합치고 관계를 옮긴다, Concept 4·Interest 1 상한)를 함께 둔다. 설계 단계는 고른 재료가 없을 때 `studentRecords`(기록 이름 30개)를 받아 절차가 아니라 **구체 탐구 하나**를 세운다. `validateStage(stage, value, input, design)` 의 네 번째 인자가 그래서 생겼다. 접기가 일한 횟수는 `academy_generation_collapse` 로그. 측정·근거 = `docs/features/academy.md` 2026-10-03, 하네스 = `scripts/academy-test/generation-live.mts`.
