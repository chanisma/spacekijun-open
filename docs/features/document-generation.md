# document-generation

> CLAUDE.md 에서 분리한 상세 문서. 스키마·마이그레이션은 `docs/database/*.md` 참조.

**문서 생성 독립 메뉴 (2026-08-16 신설, `/document-generation`, [도구] 섹션 업무 관리 아래, FACULTY_ROLES=staff 포함)** — task-workflow의 HWPX 스펙 기반 문서 생성(`document.spec_fill`)을 task 연결 없이 쓰는 메인 UI.

**새 테이블 없음**: '생성 방식' 한 건 = **`task_work` 행**(`work_type='document.spec_fill'`, 마이그레이션 `20260816090000` — task_id nullable + `start_task_work_run` 공유 실행 게이트를 RLS와 같은 `is_staff_teacher_or_admin`으로 정렬). 이 메뉴에서 만든 것은 `task_id=NULL` + `config.origin='docgen'` 이다. 러너·이력 서랍·완성 문서는 `TaskWorkRunnerDialog`→`SpecFillWorkRunner` 그대로 재사용(복제 금지 원칙).

**에이전트(MCP)로도 만든다 (2026-10-20)** — 허용 `docgen.create` 를 받은 사람의 에이전트가 한글 양식을 올리고 채울 자리를 직접 골라 같은 모양(`origin='docgen'` + 기본 양식 고정 + 양식 v1)으로 저장한다. 웹 목록에 그대로 서고 [채울 자리 고치기]로 다듬는다. 자리 검사는 이 문서 엔진을 묶은 사본(`_shared/docgenAgentSpec.bundle.js`)이 하므로 **`document/spec/*` 를 고치면 다시 묶을 것** — `docs/features/mcp-agent.md` «문서 생성 방식 만들기». 반대로 허용 `docgen.fill` 이면 에이전트가 기존 생성 방식의 칸을 채워 **문서를 만든다** — 실행 기록(이력 서랍)과 완성 문서(완성 문서 모달)가 웹에서 만든 것과 같은 모양으로 남는다(같은 문서 «생성 방식으로 문서 만들기»).

## 목록은 spec_fill WORK 전부다 (2026-09-08 사용자 결정)

같은 종류의 방식이 **업무 관리에서도** 만들어진다 — 워크플로 캔버스의 노드(`bindTaskWork`, `origin` 없음)와 업무 제출 양식(`ensureSubmissionWork`, `origin='submission'`). 그것들이 문서 생성 메뉴에 안 보이면 "생성 방식을 모아 두는 자리"라는 말이 사실이 아니게 된다. 지금은 **읽을 수 있는 spec_fill WORK 전부**가 한 목록에 선다(`listDocGenWorks`).

- **새 권한이 생기는 것이 아니다.** `task_work_select_teachers` 가 `내가 만든 것 OR (교직원 AND (origin ≠ 'docgen' OR visibility='public'))` 이라 업무 쪽 WORK 는 **원래부터 전 교직원이 읽고 공유 실행**할 수 있었다. 화면이 그것을 드러낼 뿐이다.
- **조회에 소유·공개 조건을 다시 걸지 말 것** — 종전의 두 조회(`listMyDocGenWorks`/`listSharedDocGenWorks`)는 그 정책을 클라이언트에 복제한 것이라, 정책이 바뀌면 화면만 조용히 어긋난다. 지금은 `work_type`·`archived_at` 만 걸고 **분류는 받은 뒤**(`lib/docGenWorkList.buildDocGenRows`) 한다. `listMyDocGenWorks` 는 **공지 링크 픽커 전용**으로 남았다(`[[docgen:id]]` 는 내 방식을 남에게 권하는 링크라 업무에 매인 WORK 를 섞으면 안 된다).
- **세그먼트는 전체의 분할이다** — `내 방식`(내가 문서 생성에서 만든 것) / `업무`(업무 관리에서 만들어진 것, 내 것이든 남의 것이든) / `공유받음`(남이 문서 생성에서 만들어 공개한 것). 기준은 **누가 만들었나가 아니라 어디서 만들어 어디서 관리하는가**이고, 그래야 항목 하나가 정확히 한 칸에 든다. 건수를 칩에 함께 적는다.
- **제목이 유형 이름뿐인 행을 그대로 나열하지 않는다.** 캔버스는 노드에 이름을 묻지 않고 `workRegistry` 의 유형 제목을 넣으므로 라이브 4행이 전부 `HWPX 스펙 기반 문서 생성` 이다 — 그대로 두면 제목이 같은 카드가 여러 장 선다. `docGenWorkLabel` 이 **연결된 업무 제목 → 양식 이름** 순으로 대신하고, 셋 다 없으면 원래 제목을 그대로 둔다(지어내지 않는다). 서랍·완성 문서 모달도 **같은 라벨**을 받는다(`workLabels`) — 한 화면에서 이름이 갈리면 안 된다.
- **서랍·완성 문서의 범위도 목록 전체**다. 두 조회 모두 `created_by = 나` 로 좁히므로 남의 실행·문서는 오지 않고, 목록만 넓히고 여기를 두면 업무 쪽 방식으로 만든 **내 문서가 이력에서 조용히 빠진다**.

## 업무 연결은 업무 관리에서만 한다 (2026-09-08 사용자 결정)

종전에는 카드의 `[업무 연결]` 이 같은 행의 `task_id` 를 채웠다(`setDocGenWorkTask` + `DocGenTaskLinkDialog`). **삭제했다** — 연결을 만드는 자리가 둘이면 어디서 끊는지가 흐려지는데, 실제로 그 경로의 연결성은 얕았다. 문서 생성은 연결 상태를 **배지로 보여 주기만** 한다.

### 관리 권한은 소유자에게 있다 (2026-09-08 사용자 결정, 종전 결정 뒤집음)

처음에는 "업무에서 만들어진 방식은 여기서 실행만"으로 두었다(지우는 자리를 한 곳으로). **사용자 결정으로 되돌렸다** — 서버는 원래부터 소유자에게 열려 있었고(`task_work_update_own`/`delete_own`), 삭제가 업무에까지 미치는 것은 **감출 일이 아니라 삭제 전에 말할 일**이다. 판정 단일 출처 = `canManageDocGenWork` = **내가 만들었는가**(출신 무관).

**삭제는 카드 하나를 지우는 일이 아니다** — `deleteTaskWork` 는 행을 **하드 삭제**하고 `listTaskWorks` 는 `archived_at is null` 만 거르므로, 지우면 **연결된 업무의 WORK 목록에서도 사라진다**(사용자 요구사항이자 이미 그렇게 동작하던 것). 그래서 `window.confirm` 을 버리고 `DocGenDeleteDialog` 가 **숫자로** 말한다(전자서명 요청 삭제와 같은 규약). 조회 = `fetchDocGenWorkImpact`, 수치마다 정확도가 다르므로 문구도 그대로 반영한다:

| 알리는 것 | 근거 | 정확도 |
|---|---|---|
| 연결된 업무에서도 사라짐 | `task_id` | 정확 |
| **이 업무의 값 제출 양식** — 담당자가 제출할 수 없게 됨 | `task.meta.submission.workId` | 정확 (업무 편집에서 다시 저장하면 복구) |
| 실행 이력 N건 삭제 (남이 실행한 M건의 **결과 파일은 남음**) | `task_work_run` | 정확 (SELECT 가 교직원 전체) |
| 완성 문서는 **지워지지 않지만 목록에서 찾을 수 없게 됨** | `task_work_document.work_id` = **SET NULL** | **내 것만** (RLS `select_own`) — 문구도 "내가 저장한" |

- **⚠️ `deleteTaskWork` 가 남의 RUN 을 만나면 반쯤 삭제됐다 (2026-09-08 수정)**: 이 WORK 의 RUN 을 **전부** 돌며 `delete_task_work_run` 을 불렀는데 그 RPC 는 `created_by = 나` 가 아니면 **P0002 로 거부**한다. `document.spec_fill` 은 공유 실행 유형이라 남의 RUN 이 흔하고, 그때 **내 RUN 만 지워진 채 예외가 나 WORK 는 그대로 남았다**. 루프의 역할은 애초에 행 삭제가 아니라 **Storage 파일 정리**뿐이고(행은 CASCADE) 남의 파일은 버킷 정책상 지울 수도 없다 → **내 RUN 만** RPC 로 지운다.

### 공개 토글이 정하는 것 — 출신에 따라 다르다

판정 단일 출처 = `isListedForOthers`. **기본값이 반대인 것은 양쪽 모두 현행 동작을 보존하기 위해서**다.

| 출신 | 값 없음 | 무엇이 바뀌나 |
|---|---|---|
| `docgen` | **비공개** | 서버 RLS 가 행 자체를 감춘다(공지 링크도 죽는다) |
| 업무 쪽 | **공개** | **이 목록에 세울지**만. 서버 접근은 그대로 — `task_work_select_teachers` 가 `origin ≠ 'docgen'` 행에 visibility 를 묻지 않는다 |

**업무 쪽 행을 감춰도 담당자는 종전대로 쓴다. 그래야 한다** — 못 쓰게 되면 업무가 깨진다. 그래서 이것은 **접근 권한이 아니라 목록 노출**이고, 카드 툴팁·토스트가 그 차이를 그대로 말한다. 저장은 키 삭제가 아니라 **`'private'` 명시**다(업무 쪽은 키가 없는 것이 곧 공개라 삭제로는 감출 수 없다). RLS 는 `= 'public'` 만 보므로 docgen 행에서는 둘이 같은 뜻이고, 두 출신이 **한 코드 경로**를 쓴다.

**감춘 내 방식은 나에게는 계속 보인다** — 되돌릴 유일한 자리다(관리자 미리보기 컨트롤을 `isRealAdmin` 으로 남겨 두는 것과 같은 이유).

**러너의 시작 단계는 '연 화면'이 정한다** — `TaskWorkRunnerDialog docGenMode` → `SpecFillWorkRunner docGenHost`. 종전에는 러너가 `config.origin==='docgen'` 으로 스스로 판단했는데, 두 출신이 한 목록에 서면 **같은 화면의 카드 절반만 양식 단계에서 열린다**(사용자가 볼 수 없는 이유로 흐름이 갈린다). 같은 실수를 모델 선택에서 이미 한 번 겪었다 — `specFillService.ts` 의 origin 분기 제거 주석 참조. 다만 **스펙 저장 후 기본 양식 자동 고정은 `origin` 기준을 유지**한다(`isDocGenWork`): 업무에 매인 WORK 에 그걸 하면 업무 관리 쪽 노드의 양식이 조용히 바뀌고, 거기서는 핀이 명시적 행동이다.

### 기본 양식은 문서 생성 경로에서 스스로 잡힌다 (2026-09-08)

핀 버튼(`이 생성 방식의 기본 양식`)은 **지정하는 수단이 아니라 바꾸는 수단**이다. 세 창구가 모두 기본 양식으로 끝난다: ①한글 양식 첨부 → 스펙 저장 시 고정 ②기존 양식 선택 → `createDocGenWork` 가 생성 시점에 담음 ③**둘 다 비우고 나중에 목록에서 고르기** → 스펙 저장 시 고정. ③은 2026-09-08에 메운 구멍이다 — 종전에는 `saveSpec` 의 **새 양식 분기만** 고정해서 그 경로로 만든 방식만 매번 양식 단계로 떨어졌다(라이브 4건은 ①·②로 만들어져 드러나지 않았다).

- **이미 지정된 기본 양식은 덮어쓰지 않는다**(`!defaultTemplate` 가드) — 다른 양식을 잠깐 열어 본 것일 수 있고, 그때 조용히 바꾸면 이 생성 방식이 무엇을 만드는 자리인지가 달라진다. 바꾸는 것은 핀 버튼이라는 **명시적 행동**이 맡는다.
- **문구는 화면에 따라 갈린다**(`DEFAULT_TEMPLATE_OWNER_LABEL`) — 문서 생성 메뉴에는 `노드` 가 없다. 같은 버튼이 화면에 따라 없는 개념을 가리키면 읽는 사람은 자기가 다른 것을 건드리는 줄 안다.
- 양식이 새 버전으로 갈리면 핀한 id 가 보관본이 되는데, `findPinned` 가 `familyId` 로 현재 버전을 되찾으므로 다시 지정할 필요가 없다.

**회귀** = `npx tsx scripts/docgen-list-test/run.mts`(72건 — 분류·라벨·정렬·검색 + 소스 규약: 연결 경로 부활, 조회에 소유·공개 조건 재도입, 러너 흐름 판정)

**공지 연결**: 내부 링크 타입 `docgen`(`[[docgen:id|라벨]]` → `/document-generation?entry=<id>` 딥링크가 러너 자동 오픈) — 받은 교사는 spec_fill 공유 실행 규칙대로 **남의 생성 방식으로 각자 자기 문서**를 만든다(산출물은 실행자 소유). 목록은 내 것만(`listMyDocGenWorks`), 딥링크는 단건 조회 폴백(`getDocGenWork`). 기본 양식 = `config.defaultTemplate`(캔버스 핀과 동일 키라 러너가 그대로 인식).

**공개/비공개(2026-08-16)**: `config.visibility`(`'public'` | 없음=비공개 기본), **정본 = task_work SELECT RLS 한 곳**(마이그레이션 `20260816120000` — start RPC 조회·RUN 정책 EXISTS가 전부 이 RLS를 거치므로 정책 하나로 열람·공유 실행이 함께 막힌다. origin≠'docgen'인 워크플로 WORK는 교직원 전체 읽기 유지). 화면 판정 = `isDocGenPublic()`, 토글 = 카드 Globe/Lock, 공지 픽커는 비공개 항목 삽입 차단(죽은 링크 방지).

**공개 항목은 다른 사용자의 문서 생성 목록에도 노출**('공유받음' 세그먼트, 공유 카드는 만든 사람 배지 + 실행 버튼만). `visibility` 는 **`origin='docgen'` 행에만 뜻이 있다** — 그 외 행은 정책이 visibility 를 보지 않는다(그래서 업무 제출 양식이 `origin='submission'` 이다. `taskSpecSubmissionService` 주석 참조).

## 문서 생성 메뉴의 흐름 (2026-09-04 개편)

워크플로 캔버스와 **의도적으로 다르다**. 캔버스에서는 노드가 "어떤 양식을 쓰는 자리"인지
보여 주는 것이 의미가 있지만, 문서 생성 메뉴에서는 생성 방식 = 양식이 이미 정해진 것이라
그 화면이 한 단계 낭비다. 갈림 지점은 `config.origin === 'docgen'` 하나(`isDocGen`).

- **새 생성 방식 모달에서 한글 양식을 직접 첨부한다**(주 경로). 종전에는 이미 등록된 양식
  목록에서 고르는 것만 있어 처음 쓰는 사람은 "내 양식은 어디서 올리지?"로 막혔다 —
  업로드가 러너 안쪽 '양식' 단계에만 있었다. 기존 양식 연결은 접이식 **옵션**으로 남겼고,
  둘은 **배타**다(둘 다면 어느 쪽으로 시작할지 모호해진다).
- **첨부 파일로 여기서 템플릿을 만들지 않는다** — 채울 자리를 확정하는 스펙 검수를 거쳐야
  하기 때문. 파일은 `initialFile` 로 러너에 넘어가 **스펙 검수부터** 시작한다.
- **만들면 바로 러너가 열린다.** 스펙을 저장하면 그 양식이 **이 생성 방식의 기본 양식으로
  자동 고정**된다(`setTaskWorkDefaultTemplate`) — 안 하면 다음에 '문서 만들기'가 양식
  단계로 떨어져 방금 등록한 양식을 한 번 더 고르게 된다. 워크플로는 핀 버튼이 명시적
  행동이라 손대지 않았다.
- **기본 양식이 있으면 계획 검토부터** 연다. 되돌아갈 길은 계획 검토 헤더의
  **[채울 자리 고치기]**(docgen 전용 — 워크플로는 이미 양식 단계를 지나왔다).
- **양식 단계를 건너뛸 수 있게 된 대가**로 그 화면에 얹혀 있던 두 가지를 밖으로 뺐다.
  종전 코드 주석이 "건너뛰면 이어서 작업할 문서를 찾을 길이 사라진다"고 그 제약을 적어 뒀다:
  - **실행·검수 이력** → 페이지 우측 **서랍**(`DocGenHistoryDrawer`, 기본 열림).
    러너 쪽 서랍은 `hideHistory` 로 감춘다 — 같은 목록이 두 곳에 있으면 어느 것이 최신인지
    알 수 없다. 범위는 **내 전체 + 서랍 안 선택기로 방식별 필터**(카드에는 넣지 않는다 —
    카드는 문서를 만드는 자리이지 이력을 조작하는 자리가 아니다).
    조회 = `listTaskWorkRunsForWorks(workIds)` 한 번(방식마다 부르면 방식 수만큼 왕복).
  - **완성 문서** → **헤더**의 [완성 문서] 모달(`DocGenDocumentsDialog`).
    **생성 방식과 무관하게 전부** 모은다(`listSpecDocumentsForWorks`) — 사람이 찾는 것은
    "그 방식으로 만든 문서"가 아니라 "지난번에 만든 그 문서"이고, 어느 방식이었는지는 대개
    기억나지 않는다. 방식 이름은 줄마다 붙인다.
- 서랍의 [이어서]·완성 문서 모달의 선택은 각각 `initialResumeRun`·`initialDocumentId` 로
  러너에 1회 전달된다(러너가 소비 후 비운다).

## AI 모델·프롬프트 (2026-09-02)

**`gpt-6-luna`(OpenAI) 단독 — fallback 없음**(2026-09-02 변경) — 문서 생성 경로 전용이다. 워크플로 캔버스의 같은 `document.spec_fill` WORK는 종전대로 Solar 단독이고, 갈림 지점은 `specChatForWorkConfig(work.config)` 하나(`config.origin === 'docgen'`). 상수·fallback 구현 = `services/specFillService.ts`.

- **Solar fallback을 제거했다**(2026-09-02). 한때 luna 실패 시 `solar-pro3`로 넘어갔지만 **되레 해로웠다**: Solar는 추론 모델이라 응답이 126~151초에 이르고 엣지 게이트웨이 한계에 걸려 **504 Gateway Timeout**이 났다(실사용 보고). fallback이 "느리게 실패하는 경로"를 하나 더 붙였을 뿐이고 사용자는 이미 실패한 요청을 2분 더 기다려야 했다.
- **견고함은 공급자 교체가 아니라 요청 크기에서 얻는다**(같은 날 보강): 파싱 실패 재시도 · 출력 예산을 되돌려 쓸 양에 맞춰 확대 · 씨앗을 행 단위로 분할. 되살릴 일이 생기면 `makeSolarProxyChat`이 그대로 있으니 감싸면 되지만, 벽시간 문제를 먼저 해결할 것.
- **LLM 파라미터는 모델마다 다르다** — `temperature`는 **모델별로 따로 정한다**(luna `DOCGEN_SPEC_TEMPERATURE` = 0.7 / solar-pro3 `DOCGEN_FALLBACK_TEMPERATURE` = 0.5). 갈라 둔 대가로 **fallback이 탄 문서만 문체가 달라질 수 있다** — "가끔 결과가 다르다"가 보이면 fallback 로그부터 확인할 것. 토큰 예산은 **의도적으로 다르다**: OpenAI는 `max_completion_tokens` 12,000 하한(추론 토큰이 예산을 나눠 써 빈 응답이 나오는 것을 막는 *하한*), Solar는 `solar-proxy`가 `max_tokens`를 아예 보내지 않아 상한 자체가 없다. 부작용으로 **`ChatFn`의 `maxTokens` 인자는 Solar 경로에서 무시된다**. `reasoning_effort`는 pro3 미측정이라 지정하지 않는다(엣지 기본 `'low'` 적용 — 미전송 ≠ 미적용).

**프롬프트는 모델별 방언을 갖는다** (`document/spec/promptMode.ts`). `ChatFn`의 `systemPrompt`/`userPrompt`는 문자열 **또는 `(dialect) => string`**이고, 각 프록시가 자기 방언(`'luna'` / `'solar'`)으로 **시도 시점에** 해석한다.

- **왜 시점이 중요한가**: 프롬프트를 미리 문자열로 굳히면 luna 실패 후 solar로 넘어갈 때 **luna용 지시문이 그대로 실린다**. 문서는 나오므로 아무도 눈치채지 못한다.
- 프롬프트를 **읽는** 쪽(프록시 구현·회귀 스텁)은 반드시 `resolvePrompt()`를 거칠 것 — 함수를 문자열처럼 다루면 `sys.includes is not a function`으로 죽는다.
- 현재 방언 차이 = 출력 계약 문구 + luna 전용 마무리 체크리스트. **미측정 가설이므로** 실측 후 조정할 것. 방언은 **표현**의 문제이지 **계약**의 문제가 아니다 — 두 방언이 서로 다른 것을 요구하게 만들지 말 것.

**작성 모드 2종** (`SpecFillMode`, 기본 `'strict'`):

| 모드 | 화면 표기 | 동작 |
|---|---|---|
| `strict` | 알려준 내용만 | 설명·자료에 없는 사실을 만들지 않는다. 빈 칸이 남을 수 있다 |
| `generate` | 설명 기반 생성 | 사용자 설명을 바탕으로 빈 곳을 채운다. 설명에 없는 부분도 문서 목적에 맞게 만든다. 화면에 확인 경고 표시 |

기본이 strict인 이유 = 학교 공문서라 지어낸 값이 그대로 발송될 수 있다. **두 모드 모두 `_fabricated`에 지어낸 키를 남긴다** — 모드는 "만들지"를 정하지 "숨길지"를 정하지 않는다. 모드는 `generateSpecFillPlan`·`runSpecFillPipeline`의 `mode` 인자로 흐르고 계획·행 서술 열·서술 구역 프롬프트 3곳에 반영된다. **분할 생성 루프에도 전달해야 한다** — 빠뜨리면 큰 양식에서만 조용히 strict로 동작한다.

## 계획 검토 화면 (2026-09-02 개편)

①**AI로 초안 작성** 카드(부각) → ②**문서에 들어갈 내용** 폼 → ③**실행** 순서. 각 묶음은 테두리 있는 `<section>`으로 분리한다.

- **설명 입력이 맨 위 파란 카드로 올라왔다** — 종전에는 폼 아래 회색 상자라 "AI에게 무엇을 말할 수 있는지"가 보이지 않았다. 표기도 `컨텍스트` → **"어떤 문서를 만들지 설명해 주세요"**(일반 사용자 용어). 프롬프트 안 라벨도 `[사용자 설명]`으로 맞췄다.
- **사람 필드를 맨 위로 뽑지 않는다** — 2026-08-22에 전용 블록으로 올렸으나, 그러면 계획 검토의 입력 순서가 **스펙 검수에서 본 타깃 순서와 어긋난다**. 이제 `PlanForm`이 `derivePlanSchema` 순서(= `spec.targets` 순서) 그대로 렌더하고 사람 필드는 제자리에서 구분된다. "고른 사람이 AI에 함께 전달된다"는 요약만 AI 카드에 남는다.
- **실행 버튼은 필수 + 사람 필드가 다 차야 눌린다**(`missingPlanInputs`). 못 누르는 이유를 버튼 위에 목록으로 적는다 — 비활성만 두면 원인을 찾을 수 없다. **숫자 0은 입력된 값으로 본다**(병합용 `isEmptyPlanValue`와 의도적으로 다르다 — 예산 0원을 정말 입력한 사용자가 영구히 막히면 안 된다). 사람 필드는 스키마상 `optional`로 강제돼 있지만(AI 생성 검증 통과용) 게이트에서는 필수로 되돌린다. `(선택)` 필드와 서술(prose) 필드는 검사하지 않는다(prose는 "비우면 AI가 작성"이 설계된 동작).
- 헤더 문구를 실제 동작에 맞췄다 — 종전 "(서술형은 실행 시 AI 작성)"은 AI 계획 생성을 거친 뒤에는 사실과 달랐다(그때는 계획에 실린 본문을 그대로 쓴다).

- **설명 입력 예시는 양식마다 다르다**(`WorkSpec.contextExample`) — 러너에 하드코딩된 예시는 어떤 양식에서든 같은 문장을 보여 줘 "무엇을 적어야 하는지"를 알려 주지 못했다. 스펙 검수의 `설명 입력 예시` 칸에서 직접 쓰거나 **AI 라벨 보완**이 채운다. 비어 있으면 러너의 범용 기본 예시(`PLAN_CONTEXT_PLACEHOLDER`)로 폴백한다 — 스펙에 없다고 입력칸이 맨 얼굴이 되면 안 된다. `buildSpecBundle`이 spec 전체를 담으므로 내보내기/불러오기에 자동으로 따라온다.

### 원본 문서의 기존 내용은 프롬프트에 넣지 않는다 (2026-09-03)

**설계가 뒤집혔다.** 종전에는 각 타깃 자리의 원문을 `[양식 예시]`로 실어 "표기 형식만 참고"하게 했다. 실제로는 그 **내용**이 결과에 계속 새어 나왔다(다른 문서의 날짜·사업명·활동 내용이 그대로 채워짐).

고치려는 시도를 여러 번 했다 — 문구를 부정형("복사하지 마라")에서 긍정형("가져올 것은 표기 형식뿐")으로 바꾸고, `[사용자 입력값]`과 모양·위치를 갈라 혼동을 줄이고, 엄격 모드에 "빈 칸으로 두라"는 탈출구를 주었다. **그래도 반복됐다.** 근본 이유는 하나다: **형식과 내용이 한 문자열에 붙어 있는 한, 절반만 쓰라는 요구는 지켜지지 않는다.**

그래서 사용자 결정으로 **원문을 아예 넘기지 않는다**(2026-09-03). 남는 것은 **분량 숫자뿐**:
- 서술 구역: `약 N자(공백 제외)·M문단 분량이다 — 그 수준(±30%)으로`
- 행 서술 열: `보통 공백 제외 N자 안팎이다`

숫자는 파생된 값이라 내용이 샐 수 없고, 이것마저 없애면 생성물이 칸 크기와 전혀 맞지 않는다.

**제거 범위**: `generatePlan`·`generatePlanChunked`에서 `regionExamples` 인자 자체를 없앴다(시그니처로도 막힌다). `planPromptExamples`·`subsetExamples`도 함께 삭제. **`collectRegionExamples`는 남는다** — 분량 통계와 스펙 번들 내보내기가 쓴다(읽기 자체를 막은 것이 아니라 프롬프트에 안 싣는 것이다).

**엄격 모드 탈출구는 그대로 필요하다**: 근거가 없을 때 "빈 칸으로 두라"는 길이 없으면, 모델은 ⓐ모든 키를 채워라 ⓑ지어내지 마라를 동시에 만족할 수 없어 아무 값이나 만든다. 빈 칸은 실행 게이트(`missingPlanInputs`)가 사람에게 채우게 하므로 빈 채로 나가지 않는다.

회귀 = `check-region-examples.mts`(원문 미포함·분량 유지 11건). 되살리려는 시도는 여기서 걸린다.

## 최종 결과 화면 (2026-09-02 개편)

**완료 안내 → 검증 요약 → ①내려받기(주행동) → ②보관(부차) → ③이력(접힘)** 순. 종전에는 다섯 덩어리가 **같은 시각적 무게로 평평하게** 놓여 있었다.

- **진짜 문제는 요소 수가 아니라 이름이 비슷한 두 저장의 차이가 안 보이는 것이었다.** `최종 수정본 다운로드`(에디터 현재 상태 → 내 PC, **서식 포함**)와 `완성본 저장(값)`(실행 확정 값만 → DB, **서식 빠짐**)은 *어디로·무엇이·무엇을 위해* 세 축에서 동시에 다른데, 그 설명이 아무도 읽지 않는 회색 11px 문단 하나에 있었다. 지금은 이름을 결과 기준으로 바꾸고(`문서 내려받기` / `이 문서 보관하기`) **설명을 각 행동 바로 밑 한 줄로** 옮겼다. `(값)` 같은 내부 용어는 UI에서 뺐다.
- **검증 결과는 전부 통과면 한 줄로 접는다**(`CheckSummary`). 이상이 없는 흔한 경우에 8~10줄이 주행동 위를 차지하던 것을 없앤다. **실패·경고가 하나라도 있으면 접지 않는다** — 접어 두면 못 보고 내려받는다(사용자의 접힘 선택보다 우선).
- **이력 불러오기는 최종 단계로 간다**(`resumeFromRun`). 이력을 여는 사람은 대개 "그때 그 문서"를 다시 받으려는 것이지 계획부터 다시 보려는 것이 아니다. 계획에 **서술 본문까지 이미 실려 있어**(`fillProseTargets`가 계획 단계에서 확정한다) 같은 파이프라인을 태워도 **LLM을 새로 부르지 않고** knowledge는 정상 해석돼 그때와 같은 문서가 나온다. **RUN은 새로 만들지 않는다** — 실행이 아니라 열람이다. 그래서 헤더 문구와 이력 안내가 `runRecorded`로 갈린다("검수 대기로 기록되었습니다"가 사실이 아니게 되므로). 고쳐서 다시 실행하려면 `계획 수정` 버튼이나 단계 헤더로 돌아간다.
- **이력은 기본 접힘 + 건수 배지**(`spec-runner-history-open`). **지우지 않는 이유는 "이어서 진행"(`resumeFromRun`)의 유일한 진입점**이기 때문이다. `검수 대기(needs_review)` 안내도 서랍 안으로 옮겼다 — 워크플로 거버넌스 개념이라 문서를 만들러 온 사람에게는 지금 필요한 정보가 아니다. 건수 쿼리는 `step === 'final'`에서만 켠다.

## 맥락 정보(context) — 2026-09-02 신설

AI 초안 작성에 함께 넘길 **배경 설명**을 재사용 가능한 항목으로 모아 둔다(학교 개요·교과 편성처럼 매번 반복해 설명하게 되는 것).

**소유·공개 규칙(사용자 결정)**
1. 맥락은 **사용자 소유**, 수정·삭제는 소유자만
2. 읽기는 **기본 공개** — 교직원이면 남의 맥락도 골라 쓸 수 있다
3. 소유자가 `hidden`으로 지정한 것만 비공개
4. **스펙(양식)에 연결된 맥락은 숨길 수 없다**

**④는 양방향 트리거로 강제한다.** 한쪽만 막으면 순서를 바꿔 깨진 상태를 만들 수 있다(숨긴 뒤 연결 / 연결한 뒤 숨김). `docgen_context_link_requires_visible`(연결 시 검사) + `docgen_context_hide_requires_unlinked`(숨김 시 검사). **UI에서만 막으면 낡은 클라이언트가 그 상태를 만든다** — 서버가 정본이다.

**연결을 JSONB가 아니라 링크 테이블로 둔 이유**: 스펙 참조를 `task_work_document_template.spec` JSONB 배열에 넣으면 ④를 **CHECK 제약으로 강제할 방법이 없다**(JSONB 배열을 가로질러야 함). 관계형이면 ⓐ트리거로 강제되고 ⓑ"이 맥락을 쓰는 스펙" 역방향 조회가 공짜이며 ⓒ스펙 삭제 시 CASCADE로 정리된다. 스키마 = `docs/database/task-workflows.md`.

**분류(category, 2026-09-02)**: 선택 항목이고 **자유 텍스트**다(enum·별도 표 아님 — 사용자가 그때그때 만드는 라벨이라 새 분류에 마이그레이션이 필요하면 안 된다). 편집 폼은 `datalist`로 **이미 쓰인 값을 제안**해 오타로 분류가 갈리는 것을 막으면서 새 값도 허용한다. 목록은 분류 칩으로 거른다(`전체` / 각 분류 / `분류 없음`, 분류가 하나도 없으면 필터 줄 자체를 만들지 않는다). 저장은 빈 문자열이 아니라 **NULL** — 둘이 섞이면 "분류 없음" 필터가 갈린다.

**세 진입점**
| 화면 | 하는 일 |
|---|---|
| 문서 생성 목록 헤더 `맥락 관리` | 만들기·수정·삭제·숨김 토글 (연결은 안 함 — 양식을 모르는 자리다) |
| 스펙 검수 `맥락 연결` | 이 양식에 연결(연결해 두면 계획 검토에서 기본 선택) |
| 계획 검토 `맥락 연결` | 같은 다이얼로그를 **선택 모드**로 열어 복수 선택 + 선택분만 펼쳐 **이번 생성에만** 본문 수정 |

- **계획 검토도 스펙 검수와 같은 버튼 방식**(2026-09-02 변경) — 종전에는 체크박스 목록을 카드에 통째로 폈는데, 맥락이 100개를 넘으면(성취기준 118개) 카드가 목록에 잠식된다. 지금은 `맥락 연결 (N)` 버튼이 같은 다이얼로그를 **선택 모드**로 열고, 카드에는 고른 것만 접힌 목록으로 남는다. **양식 연결과 이번 생성 선택은 체크박스가 따로다** — 합치면 "다음에도 쓰려고 연결한 것"과 "이번만 고른 것"을 구분할 수 없다.
- **계획 검토의 선택은 저장하지 않는다** — 실행마다 다른 값이라 스펙·WORK에 남기면 다음 사람이 남의 선택을 물려받는다. 양식에 연결된 맥락만 기본 선택으로 들어오고(양식이 바뀔 때만 다시 시드), 사용자가 빼면 되살아나지 않는다.
- **본문 수정도 이번 실행 한정**(`contextOverrides`) — 라이브러리 원본은 그대로다. "수정됨" 배지와 `원래대로` 버튼으로 드러낸다.
- 프롬프트 합성 = `composeContextText` — **맥락이 앞, 사용자가 쓴 설명이 뒤**(배경이 먼저 오고 이번 문서의 요구가 뒤에 와야 뒤엣것이 앞엣것을 덮어쓰는 순서로 읽힌다). 제목을 `## `로 함께 실어 맥락 사이 경계를 남기고, 상한을 넘으면 **잘린 양을 문장으로 알린다**(조용히 사라지면 왜 반영이 안 됐는지 알 수 없다). 본문이 빈 맥락은 제외한다 — 합성 블록으로 거르면 제목 때문에 항상 통과해 **제목만 프롬프트에 실린다**(회귀가 잡은 실제 결함).

**중첩 Dialog**: 러너가 이미 `TaskWorkRunnerDialog` 안이라 맥락 라이브러리는 **2중**이다. 편집까지 별도 Dialog로 열면 3중이 되므로 **한 다이얼로그 안에서 목록↔편집을 모드로 전환**한다(`ui/dialog.tsx`의 `DialogContainerContext` 주석이 Radix 레이어 충돌 사례를 기록하고 있다). 편집 중(dirty)에는 `onEscapeKeyDown`·`onPointerDownOutside`·`onInteractOutside`를 막아 **작성하던 글이 조용히 사라지는 사고**를 방지하고, 닫히면 목록 모드로 되돌린다.

**첨부 파일은 따로 보관하지 않는다** — md·txt를 읽어 본문에 이어 붙이고 **본문이 정본**이다. 파일을 별도 저장하면 "파일과 본문 중 무엇이 정본인가"가 생기는데, 프롬프트에 실리는 것은 결국 텍스트라 둘로 나눌 이유가 없다.

**WORK 연결은 규칙에서 제외**: 숨김 금지는 스펙에만 적용된다. 공개 WORK에 숨김 맥락이 걸리면 남은 못 읽으므로, 읽히지 않는 맥락은 조용히 건너뛴다(`placeNavItem` 선례).

## 성취기준 맥락 일괄 적재 (2026-09-02)

2022 개정 교육과정 성취기준을 **과목별 맥락**(`{과목명} 성취기준`, category=`성취기준`)으로 넣어 둔다. 스크립트 = `scripts/achievement-context-import/`.

- **원본의 `subject` 필드는 과목명이 아니다** — 교과(군) 이름이고(`과학`·`사회`) 일부는 `고등학교 교양 교`처럼 잘려 있다. 진짜 과목 식별자는 **코드 안의 약칭**이다(`12물에01-01` → `물에` → 물질과 에너지). 매핑 = `subjectNames.ts`, 전부 **성취기준 본문을 읽어 확인**했다(추측 금지). 특히 뒤집히기 쉬웠던 것: `12생활`=생활과학 탐구 vs `12아동`=아동발달과 부모(둘 다 가정 계열), `12지구`=지구과학 vs `12지시`=지구시스템과학.
- **코드 형태가 3종이고 뒤쪽을 놓치면 과목이 뭉친다**: `12물리01-01`(평범) / `12체육1-01-01`(**과목번호** — 체육1·체육2가 갈린다) / `06자율-1`(영역·순번 없음). 처음에 과목번호를 놓쳐 공통국어1·2, 체육1·2, 스포츠 생활1·2가 한 덩어리였다.
- **검증을 통과해야 결과를 낸다** — 매핑에 없는 약칭이 하나라도 있으면 예외로 중단한다. 조용히 건너뛰면 그 과목만 맥락이 안 생기는데 눈으로 확인할 방법이 없다.
- **고등학교만 담는다**(`DEFAULT_LEVELS = ['high']`, 사용자 결정) — 우리 학교는 고등학교라 초·중 성취기준은 목록의 잡음이다. 원본 JSON은 전 학교급을 담고 있으므로 **스크립트에서 거른다**(원본을 손대면 되돌릴 수 없다).
- 본문은 **영역별로 묶는다** — 평평하게 늘어놓으면 수십 개가 한 덩어리가 되어 AI가 어느 영역 것인지 구분하지 못한다.
- **재실행 안전**: (소유자, 제목)이 같으면 본문만 갱신. 원본에 없어진 맥락 삭제는 `--prune`을 줬을 때만 — 사람이 손으로 만든 맥락이 같은 분류에 섞여 있을 수 있다.
- **SQL 파일이 아니라 REST 직접 적재**인 이유: 생성 SQL이 1.3MB라 옮기기에 지나치게 크다. 서비스 롤 키(`.env.local`)를 쓰되 소유자를 **명시적 인자로** 받는다(서비스 롤은 RLS를 우회한다).

실행: `npx tsx scripts/achievement-context-import/apply.mts <json> --owner=<uuid> [--levels=high] [--prune] [--dry]`
현재 적재: **고등학교 118과목 / 성취기준 1,611건**(전부 공개)
