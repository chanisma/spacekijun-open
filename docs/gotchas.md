## Gotchas / 주의사항

- **⚠️ 배포 파일 이름은 ASCII 여야 한다 — Lovable 호스팅은 한글 이름 파일을 404 로 준다 (2026-10-12)**: Vite 는 지연 import·`import.meta.glob` 청크를 원본 파일 이름으로 짓는데 `neis-kb/` 는 폴더·파일이 한글이라 청크 1,599개가 한글 이름이었고, 운영에서 `/neis-guide` 가 «Failed to fetch dynamically imported module» 로 죽었다(의존 청크 216개 중 215개 404 — 할 일 NEIS 카드의 지연 로더 `neisKnowledgeLoader` 도 같은 처지였다). **빌드·로컬 미리보기는 멀쩡하다.** `vite.config.ts` 의 `sanitizeFileName: asciiFileName` 이 막는다 — 지우지 말 것. `public/` 은 Rollup 을 거치지 않으니 한글 이름 파일을 두지 말 것. 회귀 = `npm run build && npx tsx scripts/build-asset-names-test/run.mts`
- **⚠️ `seat_reservations` 를 만지는 SQL 테스트는 claims 에 `email` 을 넣을 것 (2026-10-09)**: 그 표의 학생 정책이 `auth.jwt()->>'email'` 로 본인을 판정해, `sub` 만 넣으면 본인 행이 0건이라 «남의 행이 안 보인다»는 검사가 **잘못 통과**한다. 같은 이유로 출석 열은 `protect_attendance_columns` 가 교사 claims 일 때만 통과시킨다(고정 자료를 postgres 로 넣어도 claims 가 없으면 거부된다).
- **⚠️ 같은 번호의 마이그레이션 두 개는 이력에 하나만 남는다 (2026-10-01 실제 사고)**: 두 세션이 같은 날 `20261001160000` 을 각각 만들었다. `migration repair` 는 **버전 번호로만** 기록하므로 한쪽(`task_submission_physical`)이 이력에서 가려졌다(둘 다 적용은 돼 있었다). 커밋 안 된 쪽 번호를 `20261001170000` 으로 바꿔 다시 기록해 풀었다. **새 마이그레이션을 만들기 전에 `ls supabase/migrations | grep <날짜>` 로 번호를 확인할 것** — 겹쳐도 오류가 없다.
- **⚠️ `supabase db push` 를 쓰지 말 것 — 로컬에만 있는 마이그레이션이 153건이다 (2026-09-18 실측)**: 이 프로젝트는 그동안 마이그레이션을 **MCP·수동 SQL 로 적용하고 파일명만 동기화**해 왔다. 그래서 `supabase migration list` 기준 로컬 전용 파일이 890건 중 **153건**이고, `db push` 는 그것을 **전부 다시 적용하려 든다**(대부분 이미 DB 에 있어 중복 생성 오류로 죽거나, 더 나쁘게는 일부만 적용된다). 한 건만 적용하는 안전한 절차는 **`MIGRATION_EXECUTION_ORDER.md` 머리글**에 있다 — ①`begin … rollback` 전체 드라이런 ②`begin … commit` 적용 ③**`migration repair --status applied <버전>`**(③을 빠뜨리면 그 파일이 다음 `db push` 대상으로 남는다). 실행은 `npx supabase db query --linked -f <파일>` 이고, **여러 문장은 하나의 암묵 트랜잭션**이라 중간 실패 시 전부 되돌아간다(단 결과로 오는 것은 **마지막 문장의 행**뿐이라 확인용 SELECT 를 맨 뒤에 둘 것). Windows 에서 `-f` 는 **Windows 경로**여야 한다(Git Bash 경로를 주면 CLI 가 자기 설치 위치에서 찾아 `NotFound`). Docker 는 필요 없다 — `functions deploy` 도 경고만 내고 API 로 번들한다. **MCP 가 인증되지 않을 때 CLI 가 대안**이다(`npx supabase` 2.117, 이미 linked·로그인 상태).
- **아래 5종은 전자서명에서 드러났지만 전역 규칙이다 (2026-09-12 이동 — 맥락은 `docs/features/e-signature.md`)**:
  - **⚠️ Supabase 는 `storage.objects` 직접 DELETE 를 막는다 (2026-09-04)**: `storage.protect_delete()` 트리거가 `Direct deletion from storage tables is not allowed. Use the Storage API instead` 로 거부한다. **SQL 만으로는 파일을 못 지운다** — 서비스 롤로 Storage API 를 쓰는 **엣지 함수**(`purge-signature-files`)가 필요하다. pg_cron 도 없으므로 **목록 조회가 방아쇠**이고 DB 의 `should_run_signature_purge()` 가 `system_settings` 로 **1시간 1회** 스로틀한다. 정리는 **2단계** — `list_signature_purge_targets()`(변경 없음) → 파일 삭제 → `finalize_signature_purge(ids)`. **순서가 안전장치다**: 파일을 지운 뒤 표시하므로 중간 실패 시 아무것도 표시되지 않고 다음에 다시 잡힌다(반대면 표시만 되고 파일이 남는 고아가 생긴다)
  - **⚠️ `DialogContent` 에 `overflow` 를 주면 안쪽 팝오버가 잘린다 (2026-09-04, 반복되는 문제)**: 이 저장소의 `usePortalContainer`(`ui/dialog.tsx`)는 팝오버·셀렉트를 **DialogContent 안으로** 포털한다(Radix 중첩 포털의 포커스·pointer-events 문제를 피하려는 기존 패턴). 그래서 Content 에 `overflow-hidden` 이 있으면 이름 검색 드롭다운이 **모달 경계에서 잘린다**(실사용 확인). `overflow-y-auto` 인 모달들이 멀쩡해 보이는 건 Radix 충돌 감지가 위로 뒤집어 겨우 들어가기 때문이지 해결된 게 아니다. **규칙: 피커를 담는 모달은 `DialogContent` 에 overflow 를 주지 말고 안쪽 패널에 준다.** 모서리는 헤더·푸터의 `rounded-t-lg`/`rounded-b-lg` 로 처리한다
  - **`system_settings` 는 운영 설정 전용이다 — 자동화 상태를 넣지 말 것 (2026-09-04)**: 정리 스로틀을 여기 넣었다가 컬럼명(`setting_key`/`setting_value`)과 **`created_by` NOT NULL** 로 **두 번 연속 500** 이 났다. 학사력이 사는 표에 기계 상태를 섞은 것이 애초에 틀린 자리였고, 그 INSERT 는 기능에 본질적이지도 않았다. 지금은 **클라이언트가 페이지 로드당 1회**로 스로틀한다(정리 함수는 대상이 없으면 인덱스 조회 몇 번으로 끝난다). 조용히 삼키는 실패를 만들 때는 **어디서 확인하는지도 함께 정할 것** — 엣지 함수는 실패 시 `step` 을 함께 남긴다
  - **⚠️ SQL 3값 논리로 권한 가드가 뚫린다 (2026-09-04 실제 구멍)**: `if not (col = auth.uid()) and not exists(...)` 형태는 **익명 호출에서 통과한다** — `auth.uid()` 가 NULL 이면 `col = NULL` 이 false 가 아니라 **NULL** 이고, `not NULL`=NULL → `NULL and x`=NULL → `if NULL then` = 거짓이라 **예외를 안 던진다**. 로그인 사용자에게는 정상 동작하므로 눈에 안 띈다. 실측: `get_signature_sign_links` 가 익명에게 **전 서명자 토큰**을 돌려줬다(요청 id 만 알면 전원 명의 서명 가능). **로그인 필수 함수는 맨 앞에 `if auth.uid() is null then raise` 를 둘 것**, 비교는 `coalesce(a = b, false)` 로 감쌀 것. `can_view_signature_request` 처럼 `exists(... auth.uid() ...)` 형태는 NULL 이 false 가 되어 원래 안전했다
  - **⚠️ 새 함수의 EXECUTE 는 `anon` 과 `PUBLIC` 양쪽을 봐야 한다 (2026-09-04, 2026-09-17 보강)**: 공개돼선 안 되는 RPC 는 `revoke execute ... from public, anon` 을 **둘 다** 명시할 것 — 한쪽만 쓰면 조용히 아무 일도 하지 않는다. 2026-09-04 사례는 `revoke ... from public` 이 PUBLIC 롤에서만 빼서 `anon` 의 직접 권한이 남은 것이었고, **2026-09-17 사례는 정확히 그 반대**였다: 새로 만든 DEFINER 함수 3종의 ACL 이 `{=X/postgres, …}`(주체가 **PUBLIC**)이라 `revoke ... from anon` 이 무효였고 보안 자문만 계속 "anon 이 실행 가능"으로 표시했다. **그런데 전부 회수하면 기존 동작이 바뀔 수 있다**: 정책식 안의 함수는 **호출자 권한으로** 실행되고 SQL 은 OR 의 단축 평가를 보장하지 않아, 그 함수를 쓰는 표의 익명 조회가 **"0행"에서 "42501"로** 바뀐다(실제로 `department_notice` 가 그렇게 됐다 — 데이터가 새진 않지만 기존 동작 변경이다). 결론: **인자 없이 `auth.uid()` 만 보는 신원 함수는 함수 안에 `auth.uid() is null` 가드를 넣고 anon 에 열어 두고, 인자로 uuid 를 받는 판정 함수(오라클)는 회수한다.** 검증은 `set local role anon` 으로 실제 호출해 보는 것뿐이다(권한표만 봐서는 3값 논리 구멍을 못 잡는다)
  - **⚠️ 남에게 보내는 알림 insert 에 `.select()` 를 붙이지 말 것 (2026-09-17 실측)**: `notification_events` 의 INSERT 정책은 `with check (true)` 라 누구에게든 넣을 수 있지만 SELECT 정책은 `owns_notification_resource(resource_id)`(내 것만)다. `INSERT ... RETURNING` 에 SELECT 정책이 추가로 적용되면서 **행이 정상적으로 들어가고도 `42501` 로 전체가 롤백된다** — 실측: RETURNING 없음 = 성공 / RETURNING 있음 = 42501. 한 문장이므로 오류가 없으면 전부 들어간 것이다(기존 `NotificationService.createNotification` 도 같은 이유로 `.select()` 를 쓰지 않는다)
- **⚠️ task·work 의 담당자·매니저는 트리거가 지킨다 (2026-09-27, 적대적 검증)**: 종전엔 task·work UPDATE 정책이 «로그인만 하면 누구나»라 **학생도 PostgREST 로 자기를 담당자·매니저로 써 넣을 수 있었고**, `is_work_manager`·담당자 판정에 기대는 모든 권한(입력 받기·메시지 보내기·산출물)이 그 순간 무너졌다. 지금은 `guard_task_structure`·`guard_work_structure` 가 직접 쓰기에서 **담당자 id 집합 변경·업무 이동·담당자 든 할 일 INSERT·삭제·매니저 변경**을 그 업무의 매니저·**만든 사람(`work.created_by`, 서버가 정함)**·관리자에게만 허용한다. 담당자 **상태**만 바뀌는 쓰기와 DEFINER RPC 는 통과한다. **새 클라이언트 코드가 담당자·매니저를 직접 쓰면 비매니저에게 42501 이 난다** — 담당자 본인이 바꿀 일은 DEFINER RPC 로. ⚠️ 트리거 함수를 **DEFINER 로 바꾸지 말 것**(안에서 current_user 가 소유자가 되어 직접 쓰기를 가를 수 없다). 상세 = `docs/database/core.md` §20.

  **검증 md5는 2종이고 정렬은 `collate "C"`다**: `verify-tally.mts`의 tally md5는 (슬롯순번, 과목, 학기)별 **총계**라 두 학생이 선택을 맞바꾸면 못 잡는다 → 학생 단위 md5를 함께 본다(DB 쪽 대조 SQL은 그 파일 헤더 주석에 있다). **JS 기본 문자열 정렬은 코드포인트 순인데 Postgres 기본 collation은 한글을 다르게 정렬**하므로, 데이터가 같은데 md5만 어긋나면 `collate "C"` 누락부터 의심할 것. 이 검증이 의미가 있는 이유는 **적용은 순번, 검증은 과목명**이라는 서로 다른 경로를 쓰기 때문이다.

- **`section` 테이블은 학기 키가 없고 자동으로 채워지지 않는다 (2026-08-14)**: 학년/반·`section_id`의 정본이지만 `academic_year`/`semester` 컬럼이 없어 **새 학기 분반은 누가 만들어 주지 않으면 그냥 없다**(2026-2에 216개 누락 → 수업 교체 후보 0건). 시간표 업로드가 `ensureSectionRows()`로 생성하지만 SQL·MCP로 시간표를 직접 넣었다면 `section`도 함께 채울 것. 그리고 **`meta.grade`/`meta.class`는 JSON 숫자**다 — 문자열로 가정하고 `!==` 비교하면 조용히 전부 걸러진다
- **무제한 select는 조용히 잘린다 — distinct 학기를 전체 스캔으로 구하지 말 것 (2026-08-11)**: PostgREST가 요청당 행 수를 **상한 1000행**으로 자르는데, 오류가 아니라 **부분 결과**로 온다. `student_enrollment`처럼 학기당 수천 행인 테이블에서 `.select('academic_year, semester')`를 범위 없이 날리면 상한이 첫 학기에서 다 소진돼 **새 학기가 통째로 누락**된다(실측: 2026-1이 6,285행이라 1000행을 전부 채웠고 2026-2 6,286행은 스캔에 단 한 건도 못 들어와 관리 화면 드롭다운에 항목조차 안 생김). 학기 목록은 **`fetchDistinctTerms(table)`**(`src/lib/academicTermScan.ts`) 하나만 쓴다 — 최신 학기부터 `limit(1)`로 내려가며 모아 왕복이 행 수가 아니라 학기 수에 비례한다(index-only 역방향 스캔, 실측 0.8ms). 현재 사용처 = `student_enrollment`·`student_timetable`·`teacher_timetable`·`course_offering` 4개 훅. **이 잘림은 데이터가 늘수록 조용해진다** — 작을 땐 우연히 전부 들어와 정상 동작하다가 임계점을 넘는 순간부터 새 학기만 안 보이기 시작하므로, 지금 증상이 없어도 같은 함수를 쓸 것. 대량 행을 실제로 읽어야 하면 count + `.range()` 페이징(`useEnrollments` 패턴)
- **관리 화면 기본 학기는 학사력(`useAcademicTerm`)**: 데이터에서 뽑은 `terms[0]`을 기본값으로 쓰면 안 된다 — 정렬이 학기 오름차순이라 2학기 데이터를 올려도 항상 1학기가 잡히고, 미래 학기를 미리 올리면 진행 중인 학기 대신 그쪽이 잡힌다. `academicTerm?.year ?? terms[0]` 순으로 폴백하고, 드롭다운 목록은 `mergeTermOptions(terms, academicTerm)`로 만들어 **데이터가 아직 없는 학사력 학기도 선택 가능**하게 한다(새 학기 업로드 대상). 적용처 = 학생 편성/학생 시간표/교사 시간표 관리
- **편성·시간표 데이터는 `resource.status`를 검사하지 않는다**: `student_enrollment`에 자퇴·전출 학생 행이 남아 있어도 `student_resource_id`만 있으면 시간표 생성기의 충돌 그래프에 그대로 들어간다(`fetchTimetableSourceData`는 학기로만 필터, `buildInput`은 id non-null만 확인). 편성 업로드 **후에** 자퇴한 학생이 이 경우이며 화면에 경고도 뜨지 않는다(미매칭 경고는 xlsx가 `(미재학)`으로 표기한 행만 잡음). 학적 상태를 바꿀 땐 해당 학기 편성 행도 함께 정리할 것 — 2026-2는 2026-08-11에 자퇴생 3명 17행을 삭제해 정리 완료(2026-1 이력 행은 보존)
