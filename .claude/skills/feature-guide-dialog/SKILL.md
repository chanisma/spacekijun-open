# Feature Guide Dialog — 기능 사용법 안내 모달

절차 안내를 글머리표로 쓰면 죽는다. "서명자를 추가하고 위치를 지정한 뒤
요청합니다" 를 읽고 나서도 **어디를 눌러야 하는지 모른다.** 반대로 시연만 있으면
화면은 흘러가는데 **왜 그렇게 하는지**가 남지 않는다.

그래서 한 단계에 둘을 나란히 놓는다 — **왼쪽에서 손이 어디로 가는지 보고,
오른쪽에서 그 행동의 의미를 읽는다.**

- **레퍼런스 구현 3종** (읽고 시작하면 빠르다):
  - `src/features/e-signature/components/guide/` — 4단계, 창 릴레이·모달 확장·드래그
  - `src/features/purchase-requests/components/guide/` — 3단계, **클릭 없는 상태 설명 씬** 포함
  - `src/features/document-generation/components/guide/` — 3단계, 폼 채우기·AI 대기
  - `src/features/task-workflow/components/neis/` — **씬을 손으로 그리지 않고 데이터에서 생성**하는 변형
    (나이스 화면 수백 개 — 수집본 box 가 곧 `Rect`, 화면이 무대보다 크면 카메라가 대상마다 따라간다).
    대상이 수백 개인 안내가 필요하면 이 방식을 본다(`docs/features/neis-screen-knowledge.md`)
- **역학 원본**: presentation 프로젝트의 `software-walkthrough-builder` 스킬.
  씬 문법(포인터·타이핑·창 크롬)이 같으므로 저쪽 씬 코드를 거의 그대로 옮길 수 있다.

## 뼈대 — 새로 만들지 말고 조립한다

| 필요 | 부품 | 위치 |
|---|---|---|
| 모달 껍데기(단계 표시줄·이전/다음·다시 재생) | `WalkthroughDialog` | `src/components/walkthrough/` |
| 씬 무대(960×540 고정 캔버스 + 색 토큰) | `WalkthroughStage` | 〃 |
| 좌표 도구(`Rect`·`centerOf`·`boxOf`·`inWindow`) | `stageCoords.ts` | 〃 |
| 목업 원자(`Btn`·`Field`·`Pill`·`Stub`·`Band`·`Hi`) | `atoms.tsx` | 〃 |
| 씬 역학(`Pointer`·`typed`·`AppWindow`·`popIn`·`dimAfter`) | `@/lib/walkthrough` | `src/lib/walkthrough/` |

파일 배치는 `src/features/<기능>/components/guide/` 에 **둘**:

```
guide/
├── scenes.tsx              # 씬(왼쪽 시연) — 단계마다 export 하나
└── <기능>GuideDialog.tsx   # 단계 정의(오른쪽 설명) + WalkthroughDialog 조립
```

## 절차

### 0. 실물 확인 (BLOCKING — 기억으로 목업을 그리지 않는다)

시연 대상이 **우리 앱**이므로 실물은 코드가 정본이다. 기억으로 라벨을 쓰면
화면에 없는 버튼을 안내하게 된다.

- 그 기능의 **페이지·다이얼로그 컴포넌트를 열어 실제 문구를 채집**한다
  (버튼 라벨·탭 이름·상태 표기·placeholder·빈 상태 문구).
- 상태 라벨은 **단일 출처 파일**에서 가져온다(예: `purchaseRequestStatus.ts` 의
  `제출됨·검토중·승인·완료·불가`). 화면마다 다르게 적으면 안내가 거짓이 된다.
- `docs/features/<기능>.md` 에 **왜 그렇게 만들었는지**가 있다 — 오른쪽 설명의
  재료가 여기에 있다(사용자 결정·오해하기 쉬운 규칙).
- 씬 파일 상단 주석에 **어느 컴포넌트에서 라벨을 가져왔는지 적는다.**
  화면 문구가 바뀔 때 같이 고칠 수 있어야 한다.

### 1. 단계 나누기

**3~4단계.** 그보다 많으면 아무도 끝까지 안 본다.

**탭이 여러 개인 기능은 탭마다 안내를 따로 만든다**(업무 관리가 그 예 —
내 업무 3 · 이벤트 관리 3 · 업무 흐름 3 · 타임라인 2단계). [사용 방법]은
**지금 보고 있는 탭의 안내**를 연다(`<Guide tab={activeTab} …>`).

한 모달에 탭을 몰아넣으면 ①지금 쓰지도 않는 탭의 단계를 넘겨 가며 봐야 하고
②정작 그 탭에서 알아야 할 것이 한 단계로 압축돼 빠진다. 탭이 여러 개인 화면은
탭 하나하나가 사실상 **다른 기능**이다.

- **억지로 3단계로 늘리지 않는다** — 3~4단계는 상한이지 하한이 아니다.
  타임라인처럼 "보는 것"뿐인 탭은 2단계가 정직하다.
- **모든 씬이 같은 탭 줄을 이고 있어야** 자기가 앱의 어느 자리에 있는지 잃지 않는다.
  탭 줄을 그리는 작은 공통 부품을 하나 두고 `active` 만 바꾼다.
- 파일은 탭마다 `<탭>Scenes.tsx` 로 가르고 공용 조각만 `shared.tsx` 에 둔다.
  **상수는 컴포넌트 파일과 갈라 놓는다**(`tabs.ts`) — 한 파일이 컴포넌트와 상수를
  함께 내보내면 fast-refresh 가 깨진다.

단계는 화면이 아니라 **사용자의 목적**으로 나눈다:
`요청 만들기 / 위치 지정 / 서명하기 / 보관` 은 목적이고,
`목록 화면 / 모달 화면 / 상세 화면` 은 화면이라 나누는 축으로 틀렸다.

**마지막 단계는 "끝난 뒤 어떻게 되는가"** 로 잡는다 — 파일이 지워지는 기한,
승인 후 무엇이 남는지처럼 **모르면 손해 보는 것**이 여기 들어간다.

### 2. 씬 저작 (왼쪽)

`scenes.tsx` 에 단계마다 컴포넌트 하나. 모든 모션은 `useSceneTime()` t 의
**순수 함수**여야 한다(같은 t = 같은 화면).

```tsx
// ① 자리를 Rect 상수로 한 번만 적는다 — 목업과 포인터가 이걸 함께 참조한다
const W1: Rect = { x: 32, y: 60, w: 420, h: 250 };
const BTN = inWindow(W1, { x: 324, y: 19, w: 74, h: 24 }, CH);

// ② 국면 시각도 이름 있는 상수로 모은다 — 페이스 조정이 한 곳에서 끝난다
const S = { W1_IN: 0.25, CLICK: 1.5, W2_IN: 2.1, DONE: 8.4 };

export const SceneFoo: React.FC = () => {
  const t = useSceneTime();
  return (
    <>
      <Band t={t}>① 무엇을 하는 단계인지 한 줄</Band>
      <AppWindow kind="browser" url="spacekijun / 기능" badge="①"
        style={{ ...boxOf(W1), ...popIn(t, S.W1_IN), ...dimAfter(t, S.W2_IN) }}>
        <Btn rect={{ x: 324, y: 19, w: 74, h: 24 }} label="＋ 만들기"
             flash={clickFlash(t, S.CLICK)} />
      </AppWindow>
      <Pointer path={[
        { t: 0.9, x: pctX(300), y: pctY(60) },
        { t: S.CLICK, ...centerOf(BTN), click: true },
        { t: S.DONE, ...centerOf(BTN), hide: true },
      ]} />
    </>
  );
};
```

**포인터 좌표를 손으로 계산하지 마라.** 원래 walkthrough 문법은 좌표를 산수로 구한 뒤
캡처 스크립트로 눈으로 확정하라고 하지만(±2% 오차가 흔하다), 여기서는 `Rect` 상수를
`boxOf`(목업 배치)와 `centerOf`(포인터)가 **함께 참조**하므로 포인터가 대상 위에 오는
것이 **구성으로 보장**된다. 배치를 옮겨도 포인터가 따라온다.

`AppWindow` 안에 그리는 목업은 창 기준 좌표라, 창 밖 절대좌표(`inWindow` 결과)를 쓸 때는
`{ x: R.x - W.x, y: R.y - W.y - CH }` 로 되돌린다.

**⚠️ 절대배치 원자를 흐름(flow) 안에 넣지 마라.** `Btn`·`Field`·`AssigneeChip` 처럼
`boxOf(rect)` 를 쓰는 부품은 `position:absolute` 라, **가장 가까운 위치 지정 조상**을
기준으로 그려진다. 표 셀이나 카드 안쪽처럼 흐름 자리에 그대로 넣으면 셀·카드가 아니라
**바깥 컨테이너의 좌상단**에 찍혀 다른 내용을 덮는다(구매 신청의 품목명 칸, 업무 카드의
담당자 칩이 실제로 이렇게 깨졌다). 그 자리에는 `inline` 모드를 쓴다 — 좌표는 버리고
크기만 쓴다.

**카드처럼 안쪽 구조가 있는 목업은 기하를 상수로 뽑아라.** 패딩·체크박스 크기·간격을
객체 하나에 모으고 `checkboxOf(card)` · `titleColW(card)` 같은 파생 함수를 만들어
**목업과 포인터가 함께** 참조하게 한다. 손으로 적으면 어긋난다 — 실제로 체크박스
좌표를 눈대중으로 적었다가 16px 빗나갔다.

### 3. 설명 붙이기 (오른쪽)

`WalkthroughStep` = `{ id, label, title, body, points, scene }`.

- `label` — 단계 표시줄에 들어가는 **2~5자**
- `title` — 한 줄 문장
- `body` — **한 문단.** 이 단계에서 무엇을 왜 하는지
- `points` — **3~4개.** 화면에 보이는 것과 1:1로 대응시킨다

**글은 시연을 되풀이하지 않는다.** "버튼을 누릅니다" 는 왼쪽이 이미 말했다.
글이 맡을 것은 셋뿐이다:
1. **왜 그렇게 되어 있는지** (예: 상태가 품목마다 따로 가는 이유)
2. **오해하기 쉬운 것** (예: 승인 ≠ 완료)
3. **모르면 손해 보는 것** (예: 7일 뒤 파일 삭제, 비공개면 담당자에게 안 보임)

### 4. 진입점

기능 페이지 헤더 **액션 묶음의 맨 왼쪽**에 `ghost` 버튼으로 단다.
**이 버튼 왼쪽에는 아무 버튼도 두지 않는다**(탭 전환기도 오른쪽에 — 2026-09-04 사용자 규약):

```tsx
<Button variant="ghost" size="sm" onClick={() => setGuideOpen(true)}
        className="h-8 shrink-0 gap-1.5 px-2 text-xs text-slate-500 hover:text-slate-700"
        title="사용 방법">
  <HelpCircle className="h-3.5 w-3.5" />
  <span className="hidden lg:inline">사용 방법</span>
</Button>
```

처음 온 사람만 필요하므로 **무게를 낮추되 늘 같은 자리**에 둔다. 좁은 화면에서는
아이콘만 남긴다.

**헤더가 없는 화면**(`Layout fullWidth` 로 캔버스를 꽉 채우는 앱형 화면)에서는 헤더 대신
**그 화면의 유일한 액션 줄 왼쪽**에 붙인다 — 탐구 설계가 그 예로, 캔버스 상단 중앙의 모드
토글(탐구 설계 / AI 종합 분석 / 분석 이력)을 감싸는 flex 행의 첫 항목이다. 규칙은 같다:
**그 버튼 왼쪽에는 아무 버튼도 없다.**

### 5. 검증

- `npx tsc -p tsconfig.app.json --noEmit` 후 **새 파일만** 걸러 본다
  (이 저장소엔 기존 타입 오류가 많아 전체 통과를 기대하면 안 된다)
- `npx eslint <새 디렉터리>` · `npm run build`
- **브라우저로 실제 재생해 볼 것** — 창이 겹치는지, 포인터가 화면 밖으로 나가는지,
  글자가 잘리는지는 코드로 알 수 없다. 코드 통과 ≠ 픽셀 통과.

## 수칙

- **총 8~12초.** 그보다 길면 단계를 쪼갠다. 국면 사이 최소 0.4초 홀드.
- **창은 3개까지.** 넘으면 단계를 나눈다. 2개 이상이면 배지 ①②③ 로 순번을 말한다.
- **지나간 창은 `dimAfter` 로 물리고 현재 창만 밝게** — 시선 유도.
- **목업은 랜드마크만.** 로고·핵심 버튼·주소·구분되는 구조 하나. 나머지는 `Stub`.
  실물 스크린샷을 베끼려 들면 유지 못 한다.
- **마지막 국면은 성공 판정 화면**(✓ · 완료 배지)으로 끝낸다.
- **클릭이 없는 단계도 있다.** 사용자가 *할 일*이 아니라 *보게 될 것*을 설명하는
  단계(상태 흐름 등)에서는 포인터를 두지 말고 시간에 따라 상태가 바뀌게 한다
  — 구매 신청 2단계가 그 예다.
- **글자 크기 하한 10px** (캔버스 기준). 무대가 약 0.9배로 축소돼 렌더된다.
- **가짜 데이터는 그럴듯하게.** '홍길동'·'테스트'는 안내의 신뢰를 깎는다.
  실제 업무에 나올 법한 이름·품목·문서명을 쓴다.
- **자동으로 다음 단계로 넘기지 않는다.** 읽는 속도는 사람마다 다르다.
